# /wpw:brd <需求描述>

接收客户需求描述，自动生成英文 kebab-case 需求名并创建 BRD（业务需求文档）。这是六阶段流程的入口。
**hybrid 输入**：有客户需求描述则结构化整理，无则交互问答。

> **联动 Skill**：`@brainstorming`（需求模糊时辅助澄清，可选）· `@humanizer-zh`（落盘后去机器腔）

## 角色定位（重要）

BRD 面向**业务方**（通常非技术背景）。AI 在本阶段：

- **聚焦业务**：理解"做什么 / 为什么 / 值不值"，用业务语言沟通
- **判断完整性**：评估需求是否完整清晰；不完整则用 AskUserQuestion 澄清——但**只问业务问题**（目标、范围、优先级、约束），不问技术实现
- **不主动谈技术文件**：除非用户主动问及技术实现，否则**不**讨论具体技术文件/模块/框架（如"修改 src/auth.ts""用 Redis"）。技术方案留给 Explore / Design
- **独立估算成本**：AI 自行分析实现该需求的技术成本，按业务可理解的步骤拆分，估算每步所需**人力（人）与时间（人日）**，填入"成本评估"表。这是给业务方决策用的，**不要问用户**——用户非技术背景，答不了；AI 凭自身分析给出

## 执行流程

### 阶段一：需求命名与查重

**步骤 1：生成英文需求名**

根据用户输入的需求描述，AI 生成一个 kebab-case 英文需求名：

- **命名规则**：`<domain>-<action>` 结构，2-4 个单词，全小写，短横线连接
- **长度限制**：2-30 字符
- **示例**：购物车批量删除 → `cart-batch-delete`、用户资料更新 → `user-profile-update`
- **无需用户确认**：AI 直接决定名称

**步骤 2：精确重名检查**

```bash
wpw new <生成的英文名> --dry-run  # 若不支持 dry-run 则直接尝试创建，利用其重名检查
```

若名称已存在（active 或 archived），在原名称后追加后缀区分（如 `-v2`、`-redesign`），或重新生成更精准的名称。

**步骤 3：语义查重**

调用知识图谱检索，检测是否存在语义相似的已有能力：

```bash
# 先确保图谱是最新的（如果存在）
wpw graph update

# 用英文关键词检索 C 层能力节点
wpw graph search "<english-keywords-from-description>" --level C --limit 5 --json
```

- **冷启动处理**：若图谱不存在或 C 层为空（首次使用/项目尚未沉淀能力规范），**跳过语义查重**，只做精确重名检查
- **高相似度（≥ 0.85）**：报错终止，向用户说明已有高度相似的能力，并列出相似能力名及相似度
- **中相似度（0.7 ~ 0.85）**：输出警告，列出相似能力，但继续创建流程
- **低相似度（< 0.7）**：无动作，正常继续

### 阶段二：CLI 准备

```bash
wpw new <生成的英文名>                 # 幂等创建需求（kebab-case 格式校验）
wpw check brd -c <生成的英文名> --json  # 依赖检查（BRD 无前置，必通过）
wpw template brd -c <生成的英文名>      # 取 BRD 模板路径
```

读取返回的模板路径文件，按其结构填充。BRD 文档标题为中文（从需求描述提取或整理）。

### 阶段三：AI 生成（hybrid 输入）

- **若用户提供了客户需求描述**（口述/邮件/会议纪要）：结构化整理为 BRD 大纲
- **若无输入**：用 **AskUserQuestion** 逐项询问**业务**问题：
  - 业务背景（当前痛点）
  - 业务目标（可量化）
  - 用户故事（作为...我希望...以便...）
  - 成功指标
  - 约束与假设

**完整性判断**：若关键业务信息缺失（目标不清/范围模糊/无成功指标），追加澄清问题；信息齐全后进入下一步。**澄清只问业务，不问技术。**

### 阶段四：AI 成本估算（独立分析，不问用户）

AI 基于需求自行拆解实现步骤（业务可理解的粒度，如"登录""下单""支付对接"，而非"搭 JWT 中间件"），估算每步人力与时间，填入"成本评估"表。

- **不向用户征询技术细节**——用户非技术背景；AI 凭自身分析给出
- 表末附"粗略估算，最终以 Design / Plan 为准"声明

**知识图谱辅助估算**（可选，AI 内部参考，不输出给用户）：

```bash
wpw graph update   # 增量更新图谱
# 了解相关模块规模（节点数），辅助判断改动量级
# ⚠️ 检索词必须使用英文（从需求描述翻译为英文关键词）
wpw graph context "<english-keywords>" --token-budget 1000 --level L1 --json
```

- 图谱不存在 -> 跳过，纯凭 AI 分析估算（不影响流程）
- 命中相关模块 -> 参考其文件/函数规模，让成本估算更贴近实际
- ⚠️ 图谱上下文仅作 AI 内部参考，**不向业务方输出技术文件/模块名**（BRD 面向业务方）
- ⚠️ **强制英文检索**：调用 `wpw graph context` 和 `wpw graph search` 时，检索词必须为英文

### 阶段五：确认大纲

输出 BRD 大纲（含成本评估表），等用户确认。**🛑 禁止静默落盘**。
若用户对成本有疑问，可解释估算依据（仍用业务语言，不展开技术文件）。

### 阶段六：落盘 + CLI 收尾

确认后写入 `wpw/active/<英文名>/BRD-<英文名>.md`，然后：

```bash
wpw done brd -c <生成的英文名>
```

BRD 文档标题为中文（需求的中文名称/描述），目录名和文件标识使用英文 kebab-case。

### 阶段七：AI 后处理

执行 `after_brd` hook，用 `@humanizer-zh` 去机器腔。

输出「已落盘 → [文件路径]」，提示下一步可执行 `/wpw:prd <英文名>`。
