# /wpw:xx 命令集成知识图谱上下文 - 实施计划

## 目标

将 `wpw graph` 的上下文生成与依赖查询能力注入到 8 个 /wpw:xx 命令中，替代手动 grep/读文件获取代码上下文的方式，实现：
- **降低 Token 消耗**：结构化压缩上下文替代整文件读取（预期省 60-80%）
- **提升检索准确性**：语义匹配 + 依赖遍历替代文件名猜测
- **加快速度**：一次 CLI 调用拿到结构化上下文，减少多轮文件扫描

## 统一改造模式

所有命令遵循统一的注入模式：

### 注入位置
在「阶段二：读取上下文」或「AI 生成」之前，插入一个图谱上下文获取步骤。

### 注入内容
```bash
# 1. 确保图谱新鲜（增量更新，~100ms）
wpw graph update

# 2. 生成结构化上下文（按命令特性选 query / anchors / 参数）
wpw graph context "<需求/任务相关关键词>" --token-budget <N> --json
```

### 降级策略（所有命令统一）
- **图谱不存在** -> 强提示「⚠️ 未构建知识图谱，建议先执行 `wpw graph build` 以获得精准上下文。本次将回退到手动读取文件方式。」但仍允许继续，不硬阻断
- **向量索引缺失** -> 自动降级为 `--anchors` 模式（用需求名/模块名匹配），并提示「向量索引缺失，语义检索不可用，建议 `wpw graph rebuild`」
- **context 返回 0 锚点** -> 回退到原有手动读文件方式，提示「图谱未匹配到相关节点，回退手动读取」

### 图谱新鲜度（所有命令统一）
相关命令开始时**自动增量更新**图谱：
```bash
wpw graph update   # 增量，约 100ms，保证代码上下文最新
```
若 update 检测到无图谱，则触发上面的降级流程。

## 各命令具体改造

### 1. /wpw:apply （P0 - 最高收益）

**改造位置**：阶段二「逐任务编码」中，每个任务开始前。

**现状**：每个任务编码前，AI 手动读相关文件理解上下文，靠文件名猜，易漏读多读。

**改造**：
```bash
# 每个任务开始前
wpw graph context "<任务描述 + 相关需求关键词>" --token-budget 4000 --depth 2
```
将返回的结构化子图作为该任务的代码上下文，替代逐文件读取。

**预期收益**：Token 降 60-80%，检索更准（语义 > 文件名）。

### 2. /wpw:cr （P1 - 影响面分析）

**改造位置**：步骤 1「确定改动范围」之后，步骤 4「审查」之前。

**现状**：只看 diff 文件，缺乏全局视野，不知道改动影响哪些上游。

**改造**：
```bash
# 对每个改动文件，查上游依赖（影响面分析）
wpw graph query --upstream <文件节点ID> --depth 2 --json
# 或生成改动区域的整体上下文
wpw graph context --anchors <改动文件ID列表> --depth 2
```

**预期收益**：审查更全面（看影响面），Token 增加少。

### 3. /wpw:explore （P2 - 架构理解）

**改造位置**：阶段一 CLI 准备之后，阶段二「AI 生成候选方案」之前。

**现状**：探索方案需扫代码了解现有架构，靠 grep + 猜。

**改造**：
```bash
# 了解现有相关模块和依赖
wpw graph context "<需求关键词>" --token-budget 3000 --depth 2
# 了解特定模块上下游
wpw graph query --downstream <模块ID> --depth 3
```

**预期收益**：探索更快更准，减少逐文件阅读 Token。

### 4. /wpw:design （P2 - 现状理解）

**改造位置**：阶段二「读取上下文」中，补充代码上下文。

**现状**：设计需了解现有模块边界、接口、数据结构。

**改造**：
```bash
wpw graph context "<需求关键词>" --token-budget 3000 --level L2,L3,L4
```
了解相关模块边界和接口定义，确保设计不脱节。

**预期收益**：设计更贴合现状，减少返工。

### 5. /wpw:test （P3 - 回归范围）

**改造位置**：阶段二「AI 生成」中，确定回归范围环节。

**现状**：识别回归测试范围靠人工梳理依赖。

**改造**：
```bash
# 查受影响的上游（需要回归测试的范围）
wpw graph query --upstream <改动模块ID> --depth 2 --json
```

**预期收益**：回归范围更准，不遗漏不扩大。

### 6. /wpw:sync （P3 - 文档关联）

**改造位置**：步骤 2「扫描受影响文档」。

**现状**：靠文件名关联或人工判断改动影响哪些文档。

**改造**：
```bash
# 用业务映射边反向找改动代码关联的需求文档
wpw graph query --upstream <文件ID> --depth 3 --type business_map --json
```

**预期收益**：定位更准，不漏同步。

### 7. /wpw:plan （P3 - 任务切分）

**改造位置**：阶段二「AI 生成」之前。

**现状**：拆任务时对模块边界理解依赖经验。

**改造**：
```bash
wpw graph context "<需求关键词>" --token-budget 2000 --level L2,L3
```
了解模块边界，辅助任务粒度切分。

**预期收益**：任务拆分更合理。

### 8. /wpw:brd （P3 - 成本估算参考）

**改造位置**：阶段三「AI 成本估算」。

**现状**：AI 凭空估算，无现有代码规模参考。

**改造**：
```bash
# 可选：了解相关模块规模（节点数）辅助估算
wpw graph context "<需求关键词>" --token-budget 1000 --level L2 --json
```

**注意**：BRD 面向业务方，图谱上下文仅作 AI 内部参考，不输出技术文件给用户。

**预期收益**：成本估算更准（参考现有规模）。

## 不改造的命令
- `/wpw:init` - 初始化，无代码上下文需求
- `/wpw:archive` - 归档，纯状态操作
- `/wpw:exp` - 经验沉淀（独立，非编码上下文）
- `/wpw:skills` - Skill 管理
- `/wpw:prd` - 产品文档，面向产品非代码（可小幅参考，但优先级最低，暂不改）
- `/wpw:map` - 已是图谱命令本身

## 实施顺序
1. apply（P0）
2. cr（P1）
3. explore + design（P2 并行）
4. test + sync + plan + brd（P3 批量）
5. 更新 SKILL.md 配套说明
