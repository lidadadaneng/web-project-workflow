## Context

当前知识图谱构建系统存在三项基础质量问题（详见 proposal.md）。本次改动均为图谱构建模块内部的纯规则优化，不引入 AI 能力，不新增外部依赖，零 token 成本。

涉及核心文件：
- `src/graph/parsers/requirement-parser.ts` — 需求解析器
- `src/graph/builders/graph-builder.ts` — 图谱构建/增量更新主流程
- `src/graph/types.ts` — 节点属性类型定义
- `src/graph/builders/node-builder.ts` — 节点 ID 生成（已存在，仅调用方变更）
- `src/graph/meta/*` — 元数据存储（需新增 schema 版本字段）

## Goals / Non-Goals

**Goals:**
- 归档后需求节点 ID 稳定，关联边不断裂
- `updateGraph` 能正确检测和同步需求变更
- 需求节点携带结构化功能条目，提升检索质量
- Schema 不兼容时明确提示，而非静默出错

**Non-Goals:**
- 不引入 AI 生成能力（纯规则解析）
- 不修改 CLI 命令接口（`wpw archive`、`wpw graph update` 等接口不变）
- 不做功能条目级别的独立图谱节点（首版仅作为 L1 属性）
- 不做需求间引用网络
- 不做自动重建（仅提示，由用户手动触发）

## Decisions

### 决策 1：需求 ID 从 path-based 改为 name-based

**方案：** `generateNodeId('req', [dirPath, name])` → `generateNodeId('req', [name])`

**理由：**
- 需求名是业务唯一标识，归档不应该改变节点身份
- ID 稳定后，归档只是属性变化，所有关联边自动保留
- 与「需求是业务能力的持续迭代」这一定位一致

**备选方案：**
- 归档时做节点迁移（更新 ID 并迁移所有边）：实现复杂，容易漏边，且每次归档都要做
- 用 UUID 作为需求唯一标识：需要额外存储映射关系，增加复杂度

**风险：** 已有图谱数据不兼容（所有需求节点 ID 变化）→ 通过 schema 版本检测 + 提示重建解决。

### 决策 2：需求变更检测采用「全量重解析 + 差异对比」策略

**方案：** `updateGraph` 每次都重新解析所有需求（active + archived），与图谱中现有需求节点对比，计算差异（新增 / 删除 / 属性变更），然后应用差异。

**理由：**
- 需求数量通常很少（几十到几百个），全量解析成本可忽略
- 实现简单可靠，不容易漏检
- 可以同时检测状态变化、文档内容变化等

**备选方案：**
- 基于 .wpw.yaml 文件哈希检测变更：更快，但检测不到文档内容变化
- 基于目录列表对比（仅检测新增/删除/归档）：更简单，但检测不到状态/内容变更

### 决策 3：功能条目仅作为 L1 节点属性，不做独立节点

**方案：** 提取的功能条目存储在 `node.attrs.features` 数组中，向量化时加入文本，但不生成独立的图谱节点，也不建立边关系。

**理由：**
- 首版保守实现，先验证价值
- 作为属性足够提升检索质量
- 后续如果需要功能条目级别的追踪和映射，再升级为独立节点（数据结构可平滑演进）

**备选方案：**
- 生成 L1.5 功能条目节点 + contain 边：节点数量膨胀，检索和展示都更复杂
- 仅用于向量化，不存结构化数据：浪费解析成果，无法展示

### 决策 4：Schema 版本不兼容时降级为全量构建

**方案：** 检测到 schema 版本不兼容时，`updateGraph` 自动降级为 `buildGraph`（全量构建），并输出提示信息。

**理由：**
- 用户体验更好（不用手动跑一遍 rebuild）
- 全量构建虽然慢一点，但结果正确
- 避免用户卡在「更新失败」的状态

**备选方案：**
- 拒绝执行并提示手动重建：更保守，但用户体验差
- 做数据迁移脚本：实现成本高，schema 变更频率低，不值得

## Risks / Trade-offs

- **[风险] 需求名冲突** → 全局唯一检查（active + archived），创建时拦截。若用户确实需要同名迭代，建议用 `-v2`、`-redesign` 后缀区分。
- **[风险] 全量重建耗时** → 仅在 schema 不兼容时触发，频率极低。日常增量更新不受影响。
- **[折中] 功能条目仅做属性** → 牺牲了功能条目级别的边关系和独立检索，但首版够用，后续可升级。
- **[折中] 需求变更检测用全量重解析** → 牺牲了一点性能（需求多的话可能慢几毫秒），但实现简单、不易错。

## Migration Plan

1. 升级代码后，首次执行 `wpw graph update` 或 `wpw graph build`
2. 系统检测到旧 schema 版本不兼容，自动降级为全量构建
3. 全量构建完成后，新 schema 版本写入 meta
4. 后续增量更新正常进行

**回滚：** 降级代码版本后，旧代码无法读取新 schema 的图谱，但 `wpw graph rebuild` 可以用旧规则重新构建。
