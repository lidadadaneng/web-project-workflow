## Context

见 proposal.md — Why。

当前知识图谱的调用方式：各阶段命令使用单次语义检索（`wpw graph context "<keywords>"`）获取代码上下文。存在以下问题：

1. **L1 模块层召回率低**：L1 节点向量文本少（name + description），区分度低于 L2/L3，导致单查询扁平检索时模块层排不到前面
2. **单查询覆盖有限**：一个检索词只能覆盖一个语义角度，同义词/相关概念容易漏
3. **没有分层意识**：把 C/L1/L2/L3 混在一起排序，浪费了图谱的层级结构信息
4. **Apply 阶段过度依赖语义检索**：明明 task 已经明确了文件路径，还要绕一圈语义检索，慢且不准

## Goals / Non-Goals

**Goals:**
- 提升 L1 模块层的召回率（核心痛点）
- 用纯 AI 层策略优化实现可感知的召回质量提升，零 CLI 代码改动
- 各阶段命令检索策略差异化，匹配各自的信息需求
- Apply 阶段改为锚点优先，减少语义检索的不确定性

**Non-Goals:**
- 不改 CLI 层代码（语义检索算法、向量模型、图谱构建等均不动）
- 不引入迭代式多轮检索（控制复杂度，轻量级方案）
- 不做 LLM-based rerank（额外 Token 开销过大，性价比低）
- 不改变图谱数据结构或存储格式

## Decisions

### 决策 1：L1 优先分层检索策略

**做法**：先只搜 L1（模块层）定位业务区域，再根据命中情况决定后续动作。

```
第 1 步：L1 定位
  wpw graph search "<business-keywords>" --level L1 --limit 10 --threshold 0.45

第 2 步：分支处理
  ├─ 命中 ≥ 2 个相关模块 → 用模块 ID 做锚点，--depth 向下扩展
  ├─ 命中 1 个相关模块 → 模块做锚点 + 补充 L3 语义检索
  └─ 命中 < 1 → 降级到多词扩展 + L3 反推 L1
```

**为什么（vs 扁平检索）**：
- L1 是业务语义和代码结构的交汇点，先定位模块符合人类找代码的方式
- 用 `--level L1` 过滤后，候选集小，阈值可以调低（0.45），宁滥勿缺
- 模块数量少（通常 5-20 个），错判 1-2 个影响不大，后续子图扩展会自然过滤

**替代方案**：
- 扁平检索后再从结果中提取 L1 → 不如直接搜 L1 精准，L1 可能已经被 L3 挤到后面了

### 决策 2：多词扩展 + --multi 并行查询

**做法**：每次检索生成 4-6 个不同角度的英文检索词，用 `--multi` 一次性传给 CLI。

检索词生成策略：
- 核心业务概念（1-2 个）
- 同义词/近义词（2 个）
- 技术术语/代码命名风格（1-2 个）
- 缩写形式（1 个，如果适用）

**为什么（vs 单查询）**：
- 一次 CLI 调用，开销几乎不变（多个查询的向量计算是毫秒级）
- 召回率显著提升（多个角度覆盖不同语义空间）
- `--multi` 是 CLI 已有能力，零成本使用

**替代方案**：
- 多次调用 `wpw graph context` → 更慢，子图合并也需要自己做
- 用更长的查询串 → 向量会被稀释，多义词干扰更大

### 决策 3：Apply 阶段锚点优先

**做法**：Apply 阶段每个 task 执行前，先判断是否已知文件路径：

```
已知文件路径（task 描述明确，或从 plan 继承）
  → wpw graph context --anchors file:xxx.ts --depth 2
  → 跳过语义检索，直接从已知节点扩展

未知文件路径（task 较模糊）
  → 退化为 L2/L3 语义检索
  → 检索到文件后仍可转为锚点模式
```

**为什么（vs 用语义检索找代码）**：
- Plan 阶段已经拆解好 task，每个 task 对应哪些文件应该是明确的
- 锚点模式更快（跳过 embedding + 相似度计算）
- 锚点模式更准（不受 embedding 质量影响，不会跑偏）
- 符合"图谱是导航工具"的定位——plan 已经导航好了，apply 直接下钻

**替代方案**：
- 保持语义检索 → 慢、且有召回失败的风险，而此时我们其实已经知道在哪了

### 决策 4：低召回降级三级方案

**做法**：首轮检索命中质量差时，按以下顺序降级：

```
Level 1（轻）：降低阈值
  threshold 从 0.6 → 0.45
  适用于：有结果但数量少

Level 2（中）：多词扩展
  补充同义词/相关词，--multi 查询
  适用于：检索词太窄导致漏召回

Level 3（重）：L3 反推 L1
  搜 L3 找到相关函数 → 看它们属于哪个模块
  → 模块里有 ≥2 个相关函数 → 整个模块算相关
  适用于：L1 完全查不到，但 L3 有零星命中
```

**为什么（vs 一步到位全量检索）**：
- 渐进式降级，避免过度召回导致噪音过多
- 大部分场景 Level 1-2 就够了
- Level 3 是兜底，需要 AI 做一点推理（判断函数是否属于同一模块）

## Risks / Trade-offs

| 风险 | 缓解 |
|------|------|
| 多词扩展导致子图过大、Token 超预算 | 配合 `--token-budget` 控制；CLI 层已有迭代压缩机制 |
| L1 低阈值召到无关模块，污染上下文 | 模块数量少（通常 5-20 个），AI 可以快速判断相关性；锚点模式下 AI 可手动筛选 |
| 各阶段策略不同，增加 AI 理解成本 | 在 SKILL.md 集中总结策略，并在各命令文档中给出具体命令模板，直接照抄 |
| Apply 锚点模式需要准确的文件路径 | Plan 阶段的任务拆解必须落到文件级；如果拆得不够细，退回语义检索也不损失什么 |
| 策略复杂了，debug 困难 | 每次检索输出都带统计信息（锚点数、相似度分布），AI 可据此判断问题在哪 |
