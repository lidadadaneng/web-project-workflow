# 第 6 章 系统测试与结果分析

第 5 章把第 3 章的上下文工程方法实现成 WPW 系统。本章检验这套系统和这套方法的实际表现，验证分三步进行。第一步做一组功能测试，检查实现在工作流管理、图谱构建、上下文生成、增量维护和可视化控制台上是否按预期运行。第二步让 WPW 与 OpenSpec 从同一个前置版本出发完成三个相同的开发任务，比较任务完成情况、模型 Token 消耗和执行耗时。第三步把范围收窄到上下文获取这一环：在同一个代码快照上提出二十个代码定位问题，同一个智能体分别在启用图谱上下文和只做普通检索两种条件下作答，比较必要文件的覆盖情况和模型 Token 消耗。

这一步比一步问得更具体。功能测试问的是实现能不能跑起来，开发任务对比问的是在实际开发任务上两套方法配置分别表现如何，上下文获取对比问的是图谱增强有没有让智能体更省地找到必要代码。三组结果回答的问题不同，因此分开陈述，不合并成一个总结论。

## 6.1 测试与实验环境

### 6.1.1 统一实验载体

本章三个层面的验证都放在同一个项目上进行，即一套借助大模型辅助开发完成的美食推荐系统。系统采用前后端分离结构，包含普通用户和管理员两类角色。普通用户可以注册登录、浏览和搜索美食、查看详情、接收个性化推荐、维护收货地址与收藏、发表评论、浏览资讯，并在购物车中下单；管理员维护用户、美食分类、美食信息、资讯和订单。主要业务流程是：用户注册登录后进入首页，系统结合用户行为和美食信息生成推荐结果；用户在详情页收藏、评论、加入购物车或直接购买；订单在待付款、待发货、配送中和已完成之间流转，完成后的评价行为回到偏好计算里。

协同过滤算法在这里只用来构成真实的开发任务和业务场景。本章衡量的是智能体完成任务时消耗了多少 Token、能不能找到必要的代码，不比较推荐算法的准确率，也不评价页面样式和数据库设计。这些内容属于被开发的那个系统本身，不是本文的研究变量。

移动端用 Uni-app 编写，可编译为微信小程序；管理端是 Vue 组件化页面；后端用 Spring Boot 提供 REST 接口，组织用户、美食、推荐、购物车和订单等业务服务；业务数据存放在 MySQL 中，Redis 可用于缓存热点数据。按图谱构建的统计口径，项目包含 12 个模块、393 个源文件和 1,369 个代码元素；完整条件下的实验图谱另有 25 个能力节点和 300 条业务—代码映射边。项目同时存在多个功能模块、跨端代码和多轮需求迭代，符合本文关注的长期演化项目特征。表6-1 汇总实验载体的业务与代码规模。

## 6.2 WPW 系统功能测试

### 6.2.1 测试范围与判据

本节检查 WPW 的实现是否符合第 4 章提出的需求，只判断功能有没有按预期运行，不比较它与其他方法的优劣。测试按第 4 章的模块划分组织，覆盖工作流管理、图谱构建、上下文生成、增量维护和可视化控制台五个模块，另加一组异常与恢复用例，共 12 个，每个模块或分组各 2 个。

判定依据是命令输出、状态变化和持久化文件，而不是智能体自称"操作成功"。这一点和第 4 章提出的可验证性要求一致：一次操作是否生效，要看返回的 JSON 里字段有没有按预期变化、状态文件里的阶段标记有没有真正改写、磁盘上的图谱文件和元数据有没有真正写入。系统内置了综合验证脚本 `src/graph/__verify__.ts`，它在独立临时项目里执行图谱构建、查询、更新和重建检查，配套的单元测试与集成测试覆盖解析器、映射器、存储模块和命令接口，这些输出与终端日志一并作为测试证据。

可视化控制台的两个用例按实际完成的版本报告。控制台目前从本地状态和模拟数据渲染页面，数据形态与命令行 `--json` 输出一致，但页面操作尚未全部接回命令行的写回链路。因此这两个用例只验证页面展示和交互是否正常，不能据此认定命令行一侧的写回已经通过。

## 6.3 典型开发任务的效果与成本对比

### 6.3.1 任务选取与前置版本

本节比较 WPW 与 OpenSpec 在相同需求和验收条件下完成开发任务的情况。三类任务沿用前文已经提出的划分：T1 基础搭建、T2 业务核心和 T3 迭代增强，每类选一个边界清楚、能独立验收的任务。T1 从项目初始骨架出发完成一项基础页面与接口的接入；T2 完成一个明确的业务功能点；T3 修改一项已有业务行为，改动涉及两个及以上关联模块。三类任务的具体内容在正式运行前依据真实仓库确定，不是先把整个系统从零开发一遍。

每个任务准备一个固定的前置版本，两种方法都从这个版本开始。三类任务不接着彼此生成的代码继续往下做，否则前一个任务留下的实现差异会混进后一个任务的比较里。WPW 一侧的初始图谱只由该任务开始之前已经存在的代码和规范生成，不包含任务完成后的实现，这样图谱不会提前把答案交给智能体。

两种方法使用相同的需求描述、相同的验收清单和相同的人机确认规则。需要人工确认的环节对两组一视同仁，也不向任何一组额外提供实现提示。

### 6.3.2 评价指标与统计口径

本节记录三个指标。

任务完成情况按运行前确定的验收清单判断，检查目标功能有没有实现、必要的异常场景有没有覆盖、已有功能有没有受到影响。每个任务分别报告两次运行是否通过，不以智能体的自述结论判定。

累计模型 Token 统计从接收任务到完成收尾、或失败与超时终止期间全部模型调用的输入和输出用量，不只统计最终答案，也不只统计某一次上下文包的长度。失败的运行同样计入。

执行耗时记录任务运行的净时间，人工确认的等待时间单独登记，不混入自动执行时间。图谱初始化和额外规范准备的投入单独列明，本次任务触发的图谱更新计入该任务。这样在线任务开销和前期知识准备开销可以分开看，预处理不会因为不单独记账而显得没有成本。WPW 相对 OpenSpec 的变化按同一任务的 OpenSpec 用量为基准：

$$
\mathrm{Reduction} = 1 - \frac{\mathrm{Token}_{\mathrm{WPW}}}{\mathrm{Token}_{\mathrm{OpenSpec}}}. \tag{6-1}
$$

再看 Token。T1 和 T3 上 WPW 分别少用 0.44% 和 1.65%，T2 上多用 10.96%。按式(6-1)，三个任务的 Token 下降率落在 −10.96% 到 +1.65% 之间。其中 T2 的 +10.96% 是三个任务里最大的一处差异，但需要放在重复次数的前提下来看：同一方法在同一任务上的两次运行本身就能差出 12,000 Token（T2 的 54,939 与 67,008），因此这个幅度不足以支撑"某一方更省 Token"的结论。真正稳定的是任务的量级差异：T1 的 Token 是 T2 的约四倍，因为 T1 要从零写出一条完整的接口与页面链路，而 T2 只是在既有控制器上加一个查询接口。

执行耗时的方向与 Token 不同：T1 上 WPW 快 74 秒（−15.4%），T3 快 30 秒（−12.9%），T2 慢 33 秒（+53.4%）。把耗时按来源拆开可以看到，十二次运行的本地工具耗时都在 7 秒以内，执行时间几乎全部由模型往返构成。逐次记录显示，WPW 每次模型调用的平均等待低于 OpenSpec（T1 为 6.9、6.1 秒对 11.1、8.7 秒；T2 为 2.4、2.6 秒对 2.7、3.2 秒；T3 为 3.8、3.1 秒对 4.1、4.5 秒）。两种方法调用的是同一个模型，两组运行又是先后成对执行的，这个差别更可能来自服务端的排队波动而不是方法本身，因此耗时一列只作为同批次运行下的观察值，不据此断言某一方在速度上有稳定优势。另一项可归因于方法的开销是本地命令：WPW 每次运行有 5.3 至 6.4 秒花在 `run_wpw` 调用的阶段推进与任务勾选上，OpenSpec 一侧几乎为 0（0.0 至 0.8 秒）。T2 的整体耗时被拉开，主要来自它多出的约 15 次模型往返，再加上 WPW 每次运行约 5.5 秒的本地阶段开销——这两项在短任务上摊不薄。

调用次数的差别则与方法有关。T2 上 WPW 的模型调用次数明显偏多（37、35 次对 25、18 次），与它多出的 Token 一致，说明在"只加一个接口"这类小任务上，走完整六阶段流程的准备动作相对任务本身偏重；到了 T1 和 T3，两者的调用次数接近得多（T1 为 53、60 次对 46、52 次；T3 为 56、59 次对 47、60 次）。

有一点需要在这里说清楚：这一组比较的是 WPW 与 OpenSpec 两套方法配置的整体表现，两组之间同时存在流程约束、图谱供给和上下文生成方式上的差别，因此它不能证明差异全部来自知识图谱。要说明图谱在其中的作用，需要把范围收窄，这也就是下一节再做一次上下文获取对比的原因。

## 6.4 图谱增强的上下文获取对比

### 6.4.1 题集与标准答案

本节把范围收窄到代码定位，回答一个更具体的问题：在同一个智能体、同一个代码库上，启用图谱上下文之后，能不能用更少的模型 Token 找到必要的代码。这一节不修改代码，也不做长篇的项目问答，只完成定位。

题集由二十个问题组成，十个是功能定位问题，例如"某项业务功能的后端处理入口在哪里"；另外十个是跨模块定位问题，例如"调整购物车中收藏状态的展示，需要关注哪些前后端文件"。跨模块问题要求同时涉及两个以上有关联的模块，用来观察只靠关键词搜索容易漏掉的那一类文件。

每题在运行前由人工根据源码和规范标注必要文件，只保留必要文件不超过五个的问题，避免问题本身把答案摊得太开。标准答案不向智能体开放，也不能反过来把 WPW 的检索结果当作标准答案，否则两组条件会失去共同的比较基准。相关判断由人工完成，不交给自动评分；检索增强生成领域已有的评测工作也指出，自动评测结果要先与人工判断对齐才能使用[68]。

两组输出被统一要求为：最多返回五个关键文件，每个文件附一句相关性说明。这个限制既挡住"把整个项目都列出来"的做法，也免去对长篇回答评分的工作量。

### 6.4.3 评价指标

每题每组运行两次；正文报告的条件在四个独立批次中各运行两次，合计每题八次，四个批次使用同一版引擎。同一条件在实现配置的另一档上也运行过两个批次（表6-13），用于分辨配置差别与批次波动。6.4.6 节的消融用于比较若干落地形态，批次数见该节。各次运行使用相同的终止规则，记录两个主要指标。

关键文件覆盖率为返回结果中命中的必要文件数占人工标注的必要文件总数的比例：

$$
\mathrm{Coverage}(q) = \frac{|R_q \cap C_q|}{|R_q|}, \tag{6-2}
$$

其中 $R_q$ 为问题 $q$ 人工标注的必要文件集合，$C_q$ 为该次运行返回的关键文件集合。二十个问题的平均覆盖率为：

$$
\overline{\mathrm{Coverage}} = \frac{1}{N}\sum_{q=1}^{N} \mathrm{Coverage}(q). \tag{6-3}
$$

累计模型 Token 统计从收到问题到输出最终文件清单期间全部模型调用的输入和输出用量。图谱查询即使在本机完成，送入智能体的图谱上下文和随后读取的内容也要计入，不能漏掉。本地查询耗时与模型 Token 分开记录，不合并成一个数字[67]：本地查询耗时只统计本机进程的墙钟（增强组即 `wpw graph context` 这一次调用及其图谱加载），检索词生成这类模型调用的等待时间归模型侧，不计入本地耗时。

每个问题先算两次运行的结果，再汇总二十题的平均覆盖率和平均 Token。两次重复用来观察运行波动，不当作四十个独立问题。

## 6.4.5 两项实现配置的对照

增强组的实现里有两项配置会直接改变注入上下文的内容：业务映射边在子图扩展里使用的权重阈值，以及压缩文本里是否保留文件路径。本节对这两项各做一次对照，并给出报告配置下的离线可达性读数。阈值一项用同一条命令在两档取值下各跑一次（不调用模型），再在二十题上按两档各测一轮；压缩一项在两档配置下逐臂对照（6.4.6 节表6-10 的 A1 与 A2）。两项都先量出差别，再据此选定报告取值；选定之后端到端指标上的表现记在 6.4.4 节表6-7 与本节表6-13。

### 6.4.5.1 业务映射边的权重阈值：统一取值与按类型取值

阈值这一项的第一个观察来自端到端。按统一阈值配置运行时，增强组平均覆盖率低 6.9 个百分点，累计 Token 低 4.0%，平均 4.7 轮就收手（普通检索组 6.4 轮）。覆盖率与 Token 同时下降，说明节省来自"读得更少"，而漏掉的文件也是这么丢的：表6-8 的 QF-06 一题里，两次增强运行都没有打开过必要的实现类，只是按包名猜了一个路径提交，而那个路径在仓库里并不存在。把增强组的任务说明改成「上下文是起点，覆盖不足则补齐」（变体 E）之后，轮次升到 5.6、平均 Token 反而比普通检索高 23.4%，覆盖率却仍停在 0.808。让智能体多读补不回缺口，说明缺口不在提示语，而在注入的上下文本身。

沿着这条线索去查注入上下文的内容，可以找到一个可测的结构性质。本章实测了 `default` 图谱三种边的权重分布：结构性的包含边权重恒为 0.900（1,599 条）、导入边恒为 0.750（535 条），而业务映射边（business_map）的权重是语义相似度，取值在 0.329 到 0.431 之间（300 条，中位数 0.374）。子图扩展默认使用 0.7 作为最小边权重（`minWeight`），这个阈值是按结构边的量级定的；两类边的权重并不在同一量纲上——构建侧给业务映射边的权重上限本来就是 0.7（注释写明这是间接证据，权威性低于文档提取的 0.85），实测又全部落在 0.43 以下。于是一个 0.7 的阈值把 300 条业务映射边全部挡在扩展之外：C 层锚点只能返回自身，无法沿业务—代码映射走到它对应的模块和文件，实际发生扩展的地方都在结构层。也就是说，统一阈值下的"图谱增强"更接近"结构图增强"，而从业务概念出发的那条通路——恰恰是设计上期待图谱补充普通检索的部分——是断的。

按类型取值这一档就是这样来的：裁剪配置中新增 `minWeightByType`，为 business_map 单独指定 0.3（与构建侧过滤业务映射边时的最低权重一致），其余边仍用统一的 `minWeight`。改动落在子图裁剪的过滤点上（正向与反向 BFS 各一处、子图边收集一处），配置合并时按键合并，使实验可以在不改默认值的前提下单独调这一类。配套补了一组单元测试，验证同一张图在统一阈值下 C 层锚点只返回自身、在按类型给阈值后能扩展到模块与文件，且该覆盖不影响其它边类型。同一条命令在两档之间的对比可以直接看到差别。用 QF-06 一题的英文检索词（`authentication interceptor, global request interceptor, login auth filter, token validation, authorization annotation`，`--multi --token-budget 3000 --depth 2`）查询时，把 business_map 的阈值在 0.7 与 0.3 之间切换各跑一次，其余参数不变：0.7 的子图为 105 节点、175 条边，业务映射边一条都进不来，C 层只有锚点自身 1 个；0.3 的子图为 192 节点、364 条边，其中业务映射边 131 条，C 层节点增至 14 个，估算 Token 由 1,139 升到 1,769。两次运行的完整 JSON 输出见 `ab-before.json` 与 `ab-after-fidelity.json`。

表内"按类型阈值 0.3"一列的 C 行是本节余下部分所说的不含路径形态（预置上下文、压缩文本不含文件路径）；它同时也是 6.4.6 节消融里的臂 A1，而正文报告的条件是在此基础上再接上压缩保真的臂 A2。可以看出把阈值改成按类型取值之后，"读得更少"变成了"读得更多"：三种检索配置的覆盖率缺口都收窄了 2.7 至 6.0 个百分点，其中中文检索那一档追平普通检索组（0.00 个百分点），但没有任何一档把 Token 降下来——表现最好的那一档也多花 8.6%。两档的读数取自两次构建批次（表内其余参数相同），因此这里只读同一检索配置在两档之间的方向与幅度，不与表6-7 的绝对水平直接比较。

### 6.4.5.2 压缩文本是否保留文件路径

阈值这一项配好之后，增强组能在 4 到 5 轮内收手，覆盖率却仍低于普通检索，说明注入的内容还有别的差别。把压缩文本原样打印出来看，差别很清楚：按不含路径的压缩配置，**整份上下文里一个文件路径都没有**。压缩序列化输出的身份是节点名称，模块节点写作 `interceptor-layer`、文件节点写作 `TokenServiceImpl.java`、代码元素写作 `AuthorizationInterceptor`，而本节二十道题的答案格式全部是 `src/main/java/com/service/impl/TokenServiceImpl.java` 这样的仓库相对路径。

于是智能体拿到的是"有哪些东西"，而不是"东西在哪里"：它只能按模块名与文件名拼路径。QF-06 那两次运行的错误路径 `src/main/java/com/service/TokenServiceImpl.java` 正是这么来的——正确位置在 `service/impl/` 下。压缩比做到 25 倍，代价是把答案本身压掉了。

保真这一档按"路径属于节点身份、不属于细节"来做：

1. 骨架抽取为节点补上 `path` 字段（文件与其下元素取 `filePath`，模块取 `dir`），并且不受 loose/standard/extreme 三档影响——细节可以随压缩等级增减，身份不行；
2. 模块与文件节点在层级树里直接用路径代替名称（文件的名称本来就是路径末段，写全路径不丢信息）；
3. 能力层的业务映射关联改为按所在文件归并后输出路径，取代原来一串没有位置信息的元素名，顺带把同名元素（`R.ok` 出现三次、`EIException.EIException` 出现四次）合并；
4. 依赖关系段里只有重名的文件才补目录（仓库中 `.vue` 文件重名普遍），不重名的仍只写名称，避免整段变成路径堆叠。

同一条命令在不含路径的一档，压缩文本里的路径出现次数是 0；在保真一档为 85 处，而 QF-06 的答案 `src/main/java/com/service/impl/TokenServiceImpl.java` 就在文本开头前十五行之内。配套补了一组单元测试，覆盖路径在三个压缩等级下都保留、能力层关联不重复占行、同名叶节点合并、依赖段只对重名文件补目录。对照输出见 `ab-after-fidelity.json`。

这处配置对端到端成本的作用可以读 6.4.6 节表6-10 里 A1 与 A2 两行的差别：两臂的阈值、检索词、提示与扩展范围都相同，只差压缩文本是否保留路径。覆盖率缺口由 2.71 个百分点收到 1.56 个百分点，Token 变化由 +22.3% 降到 +3.6%，平均轮次由 5.2 降到 4.3，本地查询耗时中位数由 1,313 ms 降到 1,086 ms。A2 两个独立批次的 Token 增幅分别是 +2.2% 与 +5.0%（普通检索为基线），方向一致，因此**路径保真在"不让智能体多绕一轮"这一点上的作用是本节最确定的一项**。报告配置按 6.4.5.3 节把扩展范围放大之后，表6-7 的本地查询耗时中位数回到 1,136 ms、Token 增幅回到 +11.2%。

### 6.4.5.3 报告配置的离线可达性

前两项配置定下来之后，覆盖率仍低于普通检索组，因此这一节把"上下文给了却没有被用上"的情形逐题拆开量，按三段归因：金标文件有没有进子图（检索够不够得着）、有没有进压缩文本（序列化有没有丢）、有没有被最终提交（智能体有没有用）。前两段离线量，第三段取已有运行记录。二十题一共 62 个金标文件：报告配置下三段上是 55、55、58。这个量法指出丢文件主要发生在第一段和第二段，而第一段的丢失又集中在跨模块题上（37 个金标只够到 28 个）。

沿着第一段往下查，找到一个可以精确复现的性质：扩展通路对锚点位置敏感。子图扩展用的是双向 BFS，而按方向固定的走法，路径只能沿包含边向上或沿导入边向下，一次折向都不允许。而跨模块问题要的恰恰是折一次的路：锚点常常是能力节点或类节点，先沿包含边向上回到它所在的文件，再沿导入边向下到被依赖的文件。用 QM-10 一题验证：锚点为地址控制器时，`AddressEntity` 在子图里查不到（距离为 undefined），而两者之间明明有一条权重 0.75 的导入边；改成从该控制器所在文件出发查询，`AddressEntity` 立刻出现。差异只来自锚点的位置，与阈值、深度都无关。

报告配置的做法是让每一跳都可以沿出边或入边、路径允许中途换向，并把节点上限由 100 提到 200——原先上限并不紧（实际平均 86 个节点），换向之后可达节点变多，上限反而先被撞满，把新够得着的节点又裁掉，离线复测里 6 题中有 4 题的子图恰好停在 100 个节点上。这带出第三处配置差别：层级树输出只走包含关系，父文件被节点上限裁掉、而元素本身是够得着的节点，这类节点走不进树、整条从上下文里消失。用 QM-08 验证：`CommonServiceImpl.java` 确实在子图里，文本里却搜不到它。报告配置给这类节点单开一段"其他可达节点"，按所属文件归并后带上完整路径输出。

### 6.4.6 注入形态与压缩保真的消融

6.4.5 节的两项配置决定了上下文里有什么：阈值决定有没有业务通路，路径保真决定有没有位置信息。本节把压缩这一项与另外两处落地形态放在同一批二十道题上逐臂比较，普通检索组 P 作为共同基线。6.4.7 节再换一维——输出的形态本身（交给智能体的是"组织好的上下文"还是"候选路径清单"），并把图谱的介入时机一并收紧。

- **P 普通检索**：不接触图谱，只用目录列举、搜索与读取。
- **A1 前缀注入 + 不含路径的压缩**：即 6.4.5.1 节表6-9 中变体 C 在按类型阈值下的配置，压缩文本不含文件路径。
- **A2 前缀注入 + 保真压缩**：即 6.4.4 节表6-7 报告的条件。
- **A3 工具调用 + 保真压缩**：上下文不预置，由智能体自行调用图谱工具按需获取。
- **A4 前缀注入 + 保真压缩 + 覆盖核对提示**：在 A2 基础上要求智能体先核对覆盖了问题的每个环节，缺哪一边就补齐再提交。

**压缩保真是这几臂里唯一带来成本改善的一项。** A1 与 A2 的检索与提示相同，A1 用的是不含路径的压缩，覆盖率基本相同（0.842 对 0.853），Token 增幅却从 +22.3% 降到 +3.6%，平均轮次从 5.2 降到 4.3。原因在表6-10 最后两列：前缀注入的上下文会留在对话历史里，每多一轮就重发一次；路径缺失迫使智能体多花一轮去猜位置、验证、再改口，那一轮的重发成本远大于上下文本身多出的两百多个 Token。这也解释了为什么 A1 的覆盖率没有明显更差却贵得多——它靠多读把它补"平"了。

**把上下文改成按需调用的工具，没有让结果更好。** A3 的覆盖率与 A2 持平（0.856 对 0.853），Token 增幅却高出一截（+19.4% 对 +3.6%），平均轮次反而更多（6.1 对 4.3）。预置上下文省掉的那一次检索决策，在工具形态下变成了智能体额外的探索：它需要用图谱工具取一次、判断够不够、不够再补，而工具返回的上下文与预置的那段一样会留在历史里反复重发。也就是说，工具形态并没有省下 Token，它只是把"一开始就给的上下文"换成了"自己取一次、并且往往还要再取一次"。这一条的结论是明确的：至少在本实验的提示与步数设定下，注入形态不构成收益来源。

**在提示语里要求核对覆盖，是负向的。** A4 在 A2 的全部配置上只改一句提示，覆盖率反而降到 0.848，Token 增幅升到 +32.8%。逐题看，代价集中在跨模块题（0.767，五臂最低），QM-06 一题从 0.563 掉到 0.250——按要求去"补齐每个环节"让智能体在同一个问题上反复扩大搜索，读得更多却没有更准，"多读"与"更准"之间没有稳定的相关性。

**综合起来，跨模块问题是所有增强臂共同的短板。** P 在跨模块题上是 0.825，五臂里最好的 A1 也只有 0.821，其余在 0.767 到 0.783 之间；而在功能定位题上，带保真的三臂（A2/A3/A4）都在 0.925 以上，稳定高于 P 的 0.912——A2 两个批次的这一项都是 0.925，A3 两批分别是 0.942 与 0.917。也就是说，注入图谱上下文对"这个功能的后端入口在哪里"这一类问题是有效的，对"改这个功能还要动哪些文件"这一类的效果为负。这一分化与 6.5 节的判断一致：本项目图谱目前的边覆盖的是静态结构（包含、导入、调用），缺少"这些文件总是成组变更"这一类共变关系，而跨模块问题的答案恰恰依赖这类关系。要改善这一项需要动图谱构建而不是注入形态——本轮据此补上了"同属一个能力的文件互相可达"这一类边，见 6.4.8 节；改良之后跨模块类的可达性确实动了一点，但前排次序与提交清单没有变化，原因见该节的讨论。

最后登记两处会影响读数的边界。一是批次间的波动：A2 两个独立批次的覆盖率分别是 0.867 与 0.840，A3 是 0.873 与 0.840，同一配置两批之间相差约 2.7 至 3.3 个百分点，方向也不总是一致（A3 第一批的覆盖率差为正、第二批为负）。因此"覆盖率差 1 个百分点以内"这样的差别不足以支撑结论，本节的可主张项限于三处：路径保真对 Token 的作用（两批分别是 +2.2% 与 +5.0%，方向一致）、注入形态不构成收益（工具形态的 Token 增幅在两批中分别高出保真形态 23 与 8.7 个百分点）、以及功能定位类问题上的覆盖率优势（两批方向一致）。二是评价范围：本节评价必要代码的定位和获取开销，不据此宣称模型已经理解了实现，也不推断映射、裁剪和压缩各自贡献了多少。二十个问题、每题的人工标注必要文件、各臂的逐次运行结果见附录 C 表C-1 至表C-3。

### 6.4.7 导航形态：图谱在哪两种情况下才介入

6.4.6 节比较的四种形态有一个共同点：都假设图谱应当替智能体把上下文组织好再交过去——A2 与 A4 是组织好后预置一次，A3 是组织好后等智能体来调。本轮把这一用法纠正过来：图谱在本方法里的位置是**搜索辅助件**，它应当把搜索空间缩小到若干条路径，读哪些文件、读多少由智能体自己决定，不该由图谱代它把上下文组织好。按这一用法落成的输出形态称为导航形态（`wpw graph context --mode nav`）。

与形态一并收紧的是**介入时机**：智能体已有上下文时（任务或计划已指明文件、本会话已经读过这个模块、制品里写了路径），应当直接用那份上下文，不去绕图谱；只有当它不知道代码在哪——改动落在新模块、陌生区域——时，才用导航形态代替对该模块做一轮检索。也就是说，导航形态是**对新模块检索的替代**，不是对所有代码阅读的替代。

导航形态与上下文正文形态走同一条管线（语义检索出锚点 → 加权双向 BFS 扩展子图 → 排序），只换最后的序列化：正文形态输出层级树、元素名、签名与跨节点依赖的压缩文本；导航形态输出锚点（层级、类型、相关度）、候选位置（路径、类型、元素数、是否锚点所在）以及每条候选**是由哪种关系够到的**（锚点所在、包含、导入、调用、业务映射，附权重），不含任何代码内容。

**先看检索侧。** 同一批二十题、同一批运行时检索词、同一套参数下的离线可达性测量里（表6-12 第三行），两种形态进入子图的必要文件都是 55 个（共 62 个），进入输出文本的也都是 55 个，而导航形态的平均估算 Token 为 1,459，是正文形态（1,988）的 0.73 倍。也就是说，导航形态用约七成的体积给出了同样完整的可达路径，且每条路径附带"由什么关系够到"的解释。这一层是可离线量到的、与智能体行为无关的性质。

导航形态里还有一项会影响读数的配置：候选位置是否截断。把候选截断到 20 条的那一档，同一张子图里够得着的 55 个必要文件在输出文本里只出现了 34 个——二十题里丢了 21 个金标文件。对搜索辅助件来说，**漏掉一条路径就等于没搜到**，截断的代价与正文形态漏掉内容是同一量级。报告配置因此改为不截断（前 25 条附"是怎么够到的"，其余只列路径），可达性回到 55/62；截断档的批次保留备查。

**导航形态在覆盖率上没有改善，成本更高。** 两臂覆盖率 0.840 与 0.852，与 A2 的 0.853 落在同一批次噪声带（1.3 个百分点）以内，也都没有超过普通检索的 0.869；Token 增幅却分别升到 +34.1% 与 +57.9%，本地查询耗时中位数也更高（1,225 ms、1,983 ms）。原因在轮次一列：导航形态把"选好的材料"换成"一张地图"，智能体必须自己按候选路径去打开文件，两臂平均 5.0 与 6.0 轮，而 A2 在 4.1 轮就收手。前缀上下文每轮重发，多出的轮次比多出的上下文本身更贵——这与 6.4.6 节从 A1/A2 对照里得到的机制是同一条，只是方向更极端。

**导航的价值不在端到端这一步，而在检索这一步。** 把两件事分开看就清楚了：作为端到端方案，导航形态与预置形态一样换不来覆盖率，而且更贵；作为检索辅助件，它用 0.67 倍的体积给出同等完整的可达路径，每条路径还带着到达方式。本节的结论是"图谱该以什么形态介入、在什么时候介入"，它的收益要由检索侧的完整性来量，不能由本章这个定位指标来量——后者的分辨力不足，这一点在 6.4.5.3 节已经说明。

**为什么不占优：瓶颈不在检索，而在选择。** 把四臂的运行轨迹按工具调用拆开看，差别只出现在"去哪里看"，不出现在"挑得准不准"（脚本 `tmp_ch6/harness/why_nav.js`）：普通检索每次运行 grep 4.0 次、读 3.2 份文件；导航两臂把 grep 压到 2.2 次与 2.9 次、把读文件提到 4.8 份与 4.5 份——图谱确实把"找"换成了"读"，这一点在行为上是实打实的。但提交清单的长度与精度在四臂上几乎一样：每次提交 4.4、4.4、4.1、4.4 个文件（清单上限 5 个），其中命中金标的比例分别是 60%、59%、61%、59%。覆盖率大致就是这两项的乘积，而两项都与臂无关，覆盖率也就与臂无关。换言之，图谱不论取哪种形态，改变的都是智能体**往哪里看**，没有改变它**从看过的文件里挑出正确那几个**的概率；这与 6.5 节三段归因的结论一致——62 个金标里 55 个进得了文本，缺口在"给了没被用上"。

还有一个方向值得记下来。逐题取各臂全部运行的并集，普通检索漏 5 个金标文件、A2 漏 3 个、两臂导航分别漏 6 个与 10 个。A2 的运行合起来"看见"得最多，可它的单次平均覆盖率（0.853）并不高于并集漏检更多的普通检索（0.869）——两臂的差别在每次运行的取舍，而不在检索能看见多少。导航形态那一侧还有一处分化：它给的是一份候选清单，智能体更依赖它、grep 更少（2.2 次对普通检索的 4.0 次），于是清单之外（图谱够不着）的文件更容易整批丢掉，并集漏检数最高的一臂正是"预置导航 + 工具"。

**图谱该在什么时候介入。** 导航形态还带出一条使用边界，本轮把它一并写进命令文档与工作流 Skill：图谱不必是每个任务都要过的一道关。**已有上下文时优先用上下文**——任务或计划已指明文件、本会话已经读过这个模块、制品里写了路径，就直接读那几份文件；只有当**不知道代码在哪**（改动落在新模块、陌生区域）时，才用导航形态介入，替代对该模块做一轮检索（RAG 或大范围 grep）。此外，已知文件但要它的依赖关系（影响面、调用链、模块边界）时，由锚点或 `query` 取关系，这属于结构化查询，与"找代码"是两件事。换句话说，导航形态是对**新模块检索**的替代，不是对所有代码阅读的替代；正文形态仍然只留给"通读一个模块、建立全局认知、写设计文档"的场合。

这一条边界与本章这批测量是同一场景：二十道题每次都从零开始找代码，没有任何先验上下文，因此**全部落在"新模块检索"这一情形**里，表6-14 量的正是导航形态在本该由它出场的场景下的表现——结果是不优于普通检索、且更贵。也就是说，导航形态的意义限于检索侧那一条（同等可达路径、0.73 倍体积），把它当作端到端方案的做法在本轮被证否，用户侧的使用约定也随之收紧为上段所述。

分问题类别看，两个导航臂仍呈现 6.4.6 节的分化：功能定位类 0.908 与 0.925，跨模块类 0.771 与 0.779，后者低于普通检索的 0.825。逐次运行数据见 `retrieval-nav-full.jsonl`（报告配置，默认不截断）与 `retrieval-nav.jsonl`（截断档，候选截断到 20 条，保留备查），汇总见数据目录的 `nav-form.txt`，附录表C-6 给出同一张对照表。本节把形态与时机都收紧了，但跨模块那一类仍然低——缺口在图谱的结构上，下一节回到图谱本身。

### 6.4.8 图谱侧改良：共能力边及其效果

前面几节的缺口指向图谱的结构而不是注入形态：跨模块题上所有带保真的形态都落在 0.767 至 0.783，低于普通检索的 0.825，而图谱原有的边只有两类——结构边（包含、导入、调用）说明"谁依赖谁"，业务映射边说明"一个能力落在哪个文件"。跨模块题的答案要回答"改这个功能还要动哪些文件"，这类关系（同属一个能力、常成组变更）两类边都表达不了。离线测量印证了这一点：二十题一共 73 对同题金标文件，能在子图里查到直接边的只有 3 对。

更直接的依据本来是提交历史里的文件共现（co-change），但本项目实验仓库不可用：实验副本不含 `.git`；`.eval-snapshot.json` 记录的原始工程路径已不存在；实际的原始工程只有 11 次提交，其中 4 次是 933 至 1407 个文件的批量初始化、6 次是 12 至 38 个文件的样式更新，剩下一次 102 个文件——在"同现频次不少于 2 次"的门槛下统计不出有意义的文件对。本轮据此把同一意图换成可计算的替代：**两个文件被同一个 C 层能力够到，就认为它们同属一个改动集**。这一替代有明确的局限——它继承业务映射本身的精度，映射把噪声文件也映射到某能力时，噪声文件会一起连进来；这一点在下文的读数里可以直接看到。

实现上，共能力边从**已落盘的** business_map 边派生，不重跑语义检索，从而保证"图谱里看到的同能力关系"与边本身严格一致：按能力分组、把映射目标归并到文件粒度、按权重取前 K 个文件两两相连、权重取两侧较弱的一侧（这条边的依据是"两者都属于该能力"这一合取式，下限由较弱的一侧决定）、双向各一条；边类型为 `sibling`，来源记为 `semantic`，并在边上记下共享的能力名——导航输出因此写得出 `← 共能力 0.39 ← C:database-schema`，而不是"由某个文件够到"。它在构建流程里是 business_map 之后、完整性校验之前的一个独立阶段（`wpw graph build` 的阶段输出中可见"构建文件耦合"）。子图裁剪这一侧把它登记为**低优先边**：额度分配时不与结构边竞争，只花剩余槽位——缘由与实测见下文。

**这处改动一开始在一个形态上是变差的，值得单独记下来。** 共能力边把同一能力下来的文件直接连起来，而这些文件与锚点语义高度相似、综合得分也高。节点上限一旦收紧（Token 预算不够时，裁剪的降级阶梯会把节点上限逐级折半：200 → 100 → 50 ……），它们就会占满剩余槽位，把原本靠包含/导入边够得的节点挤出去：节点上限 100 时，同一测量由补边前的 52/62 掉到 49/62。这不是实验室里的边角形态——预算降级正是上下文生成真正吃紧的时候。为此给这类边加了"低优先"规则：**额度分配按不含共能力边的得分来判**（去掉这些边再跑一遍扩展，那时就够得着的节点先占位，共能力边带来的新节点只花剩余槽位），而**清单位次仍用含共能力边的得分**——它确实说明"这些文件有关联"，抬高位次是合理的。现行实现因此保留两份分值：一份用于排序显示，一份只用于分配额度。中途试过把两份都按不含共能力边来算，结果是收紧额度那一档回到 53/62，但 Recall@10 从 0.546 掉回 0.521——清的位次信号一起丢了；分开处理之后两处都保住（表6-17 第三行与"补边后"列）。

**在线试点：看不出差别。** 另做了 8 题 × 2 次的小样本配对（同一批题、同一条件，只切换共能力边，`tmp_ch6/harness/pilot-cmp.js`）：两态平均覆盖率都是 81.8%，配对差平均 0.00 个百分点（2 次改善、12 次持平、2 次变差）。这与本节的判断一致——1 个金标文件、两个多百分点的 Recall@10 远小于在线指标的分辨力，端到端这一步量不到它。

**一处反向实验，需要记下来。** 与补边同时试的还有一处排序改动：锚点原先一律记满分，于是锚点块（候选清单的开头几条）内部落到按路径字母序排。改成按各自的检索相似度排序、让"命得更准的锚点"排前面，理论上更合理。实测结果相反：MRR 由 0.594 掉到 0.341，Recall@3 由 0.262 掉到 0.171，候选前 5 条精度由 0.200 掉到 0.160。追查下来有两个原因。一是路径序在本题集上恰好有利：`src/main/java/...` 排在 `src/main/resources/...` 之前，而金标文件全部是后端 Java 文件，字母序无意中把后端整体提到了前面。二是检索相似度的分布集中在 0.70 至 0.94 的窄带内，二十几个锚点挤在这个区间里，区分度不足以支撑细排。这处改动已回退（代码里留了说明）。

这一处反向实验还暴露一个读数陷阱：MRR 这类"最好那个金标的位次"指标，在锚点块按路径排序时读数是 0.594 至 0.597，而它实际量到的是路径序与文件命名/目录结构的巧合。因此本节的可主张项只用 Recall@5、Recall@10 与候选前 5 条精度，不用 MRR；表6-15 里 MRR 一列照实列出，但读者应当把它当作"锚点块内部次序"的量，而不是图谱质量的量。

**结论是：共能力边抬高的是候选空间的可达性，不是答案的位次。** 这与 6.4.7 节的选择瓶颈是同一条：智能体并不是按序取用清单，而是打开文件、读、再筛（四臂每次提交 4.1 至 4.4 个文件，提交精度 59% 至 61%，远高于清单前 5 条的 20%）。图谱改良的着力点在"别让答案漏出搜索空间"这一侧，本节量到的正是这一侧的小幅改善；要动"把答案排到最前"这一侧，需要的是排序信号——哪个文件是这次改动的核心、哪些文件属于同一个改动集——这已经超出"需求—实现映射"能提供的范围，本章不给结论。

需要登记的边界有三处。第一，加入共能力边之后的正式在线对照没有重跑：表6-7 至表6-14 的在线读数全部出自补边之前构建的图谱，本节给出的在线证据只有上面那次 8 题 × 2 次的配对试点。理由是本轮上线的改动量级（Recall@10 两个多百分点、1 个金标文件）远小于在线指标的分辨力（单题金标 1 到 4 个、批次噪声 1.3 个百分点），重跑得不到可解释的读数；这一处改动因此以离线指标立论，在线只报"看不出差别"。第二，共能力边继承业务映射的精度，映射的噪声会变成"同能力"的噪声（构建统计里 25 个能力共连出 422 条边，其中一部分连接来自映射本身就不准的目标），本节没有对这部分做人工校验。第三，本章的图谱改动只做了这一处，业务—代码映射、子图裁剪、压缩序列化三个组件仍没有做开关式消融，因此不把效果分别归因于其中某一个。复现命令：`node tmp_ch6/harness/patch-sibling.js <workspace> --k <K>`（对已有图谱补边，不重建；每次先丢掉图上已有的同类边再按 K 重建，K 调小才会生效）、`node tmp_ch6/harness/sweep-sibling.js 0 2 3 5 12`（K 扫描，跑完自动还原成 K=5）、`node tmp_ch6/harness/rank.js` 与 `WPW_REACH_MODE=nav node tmp_ch6/harness/reach.js`（表6-15、表6-16 的数据）、`WPW_REACH_DEPTH`/`WPW_REACH_MAXNODES` 环境变量（表6-17 的各形态）、`node tmp_ch6/harness/pilot-cmp.js`（在线试点对照），原始输出存于数据目录的 `rank-*.txt`、`sweep-sibling.txt`、`shape-sibling.txt`、`pilot-sibling.txt`。

## 6.5 结果讨论与局限性

这一节把前面三组结果串起来看，不新增实验。

先看开发任务对比。三个任务的验收结果是一致的，十二次运行全部通过，没有出现失败或超时，因此趋势上的分歧只出现在成本而不是能不能完成。Token 上 T1 和 T3 的差异在 2% 以内（−0.44%、+1.65%），T2 上 WPW 多出 10.96%；耗时的方向则相反，T1、T3 上 WPW 更快（−15.4%、−12.9%），T2 上慢 53.4%。差异最大的是 T2，也是唯一 WPW 在两项成本上都更高的任务：它只要求在既有控制器上增加一个查询接口，任务本身很短，而六阶段流程的准备动作（写制品、推进阶段、勾选任务）不随任务规模等比缩小，于是固定开销占了较大比重。T1 和 T3 的任务量更大，涉及的文件和关联模块更多，固定开销被摊薄。这说明流程型方法在当前实现下的成本结构对小任务是偏重的，本节不对这种成本结构做褒贬，只报告它在这个规模区间里的表现。

再看上下文获取对比。总的账仍然是否定的：图谱增强组覆盖率低 1.6 个百分点，平均累计模型 Token 高 11.2%，本地查询耗时中位数约为普通检索组的 3.3 倍（表6-7）。但这一组的读数分成了三类，值得分开说。

第一类是成本，也是本组的读数对实现配置最敏感的一处。注入上下文的内容由 6.4.5 节的两项配置和扩展通路共同决定：按不含路径的压缩时，上下文里只有节点名，而定位任务的答案格式是仓库相对路径，智能体只能按包名猜位置（6.4.5.2 节）；按统一阈值、方向固定的扩展时，C 层锚点沿业务映射边向下以及"先上后下"的折向通路都走不通，可达文件少一批（6.4.5.1、6.4.5.3 节）。在 6.4.5 节的两项对照里，两段读数说明了成本来自哪里：压缩保真把平均轮次由 5.2 降到 4.3、Token 增幅由 +22.3% 降到 +3.6%、本地查询耗时中位数由 1,313 ms 降到 1,086 ms——"注入更长的上下文"本身并不必然贵，贵的是让智能体在缺信息的情况下多绕几轮，前缀与工具返回都会留在历史里逐轮重发；而把可达文件补全又让上下文变长（子图平均 86 个节点增到 194 个），Token 增幅回到 +11.2%，轮次保持在 4.1。也就是说，本章把"上下文里有正确的答案格式与完整的可达文件"定为报告配置，代价是每题的累计 Token 比普通检索组高约一成；这笔代价换来的东西在覆盖率上量不出来（表6-12、表6-13）。

第二类是能力边界。功能定位这一类上，增强组各形态高于普通检索组（0.912 对 0.925、0.926、0.929、0.929），方向在多个批次中一致；跨模块这一类上则相反，普通检索组 0.825，增强组各形态在 0.767 到 0.821 之间（表6-11）。两类之差都在批次噪声带（1.3 个百分点）附近或上下，因此本节只报方向，不报"这一类有效、那一类无效"的结论。可以确定的只有一件事：检索侧把跨模块题够得着的金标文件从 28 个补到 32 个（表6-12），覆盖率却没有跟着升上去。差的那一段不在检索侧。按三段归因统计二十题的 62 个金标文件：进入压缩文本的有 55 个，其中进过文本却一次都没被提交的有 3 个；另外 6 个文件是智能体绕开图谱自己搜到的，最终在全部运行里至少被提交过一次的有 59 个。单次运行平均只提交 53 个（0.853 × 62），与"至少提交过一次"的 59 个相比，少的那些不是每次都"没看见"，更多是看见了没提交——提交清单最多五个文件，选择本身就是一次取舍。要再往上走，要么给图谱补上"这些文件总是成组变更"这类共变关系，要么改注入方式让智能体真正用满已有信息。前一条已经在 6.4.8 节落地并单独度量：补上"同属一个能力的文件互相可达"这类边之后，可达性多出 1 个金标文件、Recall@10 升 2.5 个百分点，而候选前 5 条精度与提交清单的形态都没有变化——这与本节的判断一致，漏的那一段不在检索侧。后一条（让智能体真正用满已有信息）不在本轮改动范围内。6.4.7 节把这条缺口在四个臂上复核了一遍，结论是同一件事：四臂每次提交的清单长度（4.1 到 4.4 个文件）与清单精度（59% 到 61%）几乎相同，图谱不论取哪种形态，改变的都是智能体往哪里看，而不是它从看过的文件里挑对的那一步。

第三类是形态选择。同一套图谱设施可以做成预置上下文，也可以做成智能体按需调用的工具，还可以在提示里要求核对覆盖，还可以干脆不组织上下文、只给一张导航图。消融的结果是：工具形态与预置形态覆盖率持平而 Token 增幅高三倍多（+19.4% 对 +3.6%），因为工具调用取回的那段文本同样会留在历史里逐轮重发，而智能体往往要取两次；"核对覆盖"的提示更差，覆盖率降到 0.848、Token 增幅升到 +32.8%，代价集中在跨模块题上（表6-10、表6-11）；导航形态是四者里最彻底的改动，把"组织好的上下文"整个换成"候选路径清单"，覆盖率仍与预置形态同一水平（0.840、0.852 对 0.853），Token 增幅却最高（+34.1%、+57.9%），轮次从 4.1 升到 5.0 与 6.0（表6-14）。这一类的结论是：在上下文已经把信息给全的前提下，改注入方式、改提示语、改输出形态都换不来收益，能换来收益的只有把该给的信息给全。

不过导航形态这一条要按两个问题分开回答，不能笼统地记成"也没用"。第一个问题是端到端覆盖率有没有提高，答案是没有；第二个问题是图谱作为检索辅助件本身好不好用，答案是有明确的可离线量到的性质：它在同一张子图上用 0.73 倍的体积给出与正文形态相同的 55/62 可达路径，且每条路径附带"由什么关系够到"的解释（表6-12 第三行）。第二个问题才是本节要回答的——导航形态界定的是两件事：**图谱以什么形态介入**（不替调用方组织好上下文，而是替它缩小搜索空间），以及**什么时候介入**（只在不知道代码在哪、需要对陌生模块做一轮检索时，已有上下文则直接读）。这两层收益都只能由检索侧测量来量，本来就量不到端到端的覆盖率上。反过来说，本章这个指标测的是智能体用不用得上给定信息，而不是图谱检索的全不全，两件事不能互相代替，本节把它们分开陈述。

这件事本身值得记下来：本章的评价指标之所以同时看覆盖率和 Token，是因为只报一个数会把配置差别读反。表6-9 已经给出同一批题的两种读法：按统一阈值配置时，业务映射边一条都进不了子图，"图谱增强"实际退化成"结构图增强"，而它的 Token 低于普通检索组（−14.6%、−4.0%），只看 Token 会得出"图谱增强省了 Token"的结论；按类型阈值配置之后覆盖率缺口收窄，Token 却升到 +8.6% 至 +44.7%，只看覆盖率又读不出这笔成本。压缩一项同理：不含路径的压缩体积更小，但它迫使智能体多绕一轮，端到端的账反而更贵（表6-10）。换句话说，这个指标组测的是"用得上多少给定信息、为此付出多少"，单一指标读不出这两层之间的关系。反过来也要说清楚：换成报告配置之后覆盖率并没有变好，指标本身的分辨力（单题金标 1 到 4 个、批次波动 1.3 个百分点）不足以测出检索侧的改善，这一点记在 6.4.5.3 节。

三组结果各自说明不同层面的事情，不能互相代替。功能测试通过，说明实现能按设计运行；开发任务通过，说明两种方法配置在这个项目上都能完成预定任务；上下文获取没有改善，说明在本章的定位题集上，图谱增强环节的开销没有转化为收益。把它们合并成一句"方法全面优于基线"是不成立的，同样，也不能用功能测试通过来反推上下文环节有效。

需要登记一处执行过程中的调整。开发任务对比的首次试跑没有通过验收：智能体把步数消耗在摸索命令行用法上（反复查询帮助、反复读写流程文件），没有在步数用尽前落到实际的代码改动。据此做了两项修改——把单次运行的步数上限由 30 提到 60，并在两种方法各自的工作说明里补齐了流程命令速查——然后重新运行了全部十二次。本节报告的是调整后的十二次结果。这一调整对两种方法是对称的，但它确实改变了实验条件：表6-5 的通过率是在给出流程命令速查之后取得的，不应被读成"方法在无提示条件下也能稳定完成"，后续若要复现应以此处的说明为准。

本章的结论限定在选定的项目、固定的模型和有限的任务上。三个开发任务和二十个检索问题不足以证明方法对所有项目普遍有效，普通检索组每题两次、增强组每题八次的重复也主要用于观察运行波动，不足以支撑强统计结论。6.4.6 节做了注入形态与压缩保真的消融，但没有对业务—代码映射、子图裁剪、压缩序列化这三个组件分别做开关式消融，因此不把差异分别归因于其中某一个；也没有做长期演化实验，因此不写"知识越积累，成本必然越低"。

## 6.6 本章小结

本章围绕 WPW 的工程可行性和图谱驱动上下文工程方法的应用效果做了三组验证，三组证据分别对工程实现、实际任务表现和上下文获取环节负责。

功能测试按第 4 章的模块划分选取 12 个代表性用例，检查工作流管理、图谱构建、上下文生成、增量维护和可视化控制台是否按预期运行，判据是命令输出、状态变化和持久化文件。十二个用例全部通过，实现与第 5 章的设计一致。其中增量维护验证到的是结构层面的局部更新——改动一个源文件后节点与边各只增加一个，未修改文件的节点原样保留，图结构处理耗时在百毫秒量级；同一次运行中的向量索引是全量重建的，这与 5.5.1 节登记的折中方案一致。

开发任务对比在美食推荐系统上选取 T1 基础搭建、T2 业务核心和 T3 迭代增强三个任务，让 WPW 与 OpenSpec 从同一前置版本出发各完成两次，比较验收情况、累计模型 Token 和执行耗时。十二次运行全部通过验收。T1 与 T3 上 Token 差异在 2% 以内，T2 上 WPW 多出 10.96%（小于同一方法重复运行自身的波动），耗时的方向与之相反（T1、T3 上 WPW 更快，T2 上更慢）。可以支持的说法是：在这个项目上，两种方法配置都能完成任务，成本处于同一量级；不能支持的是一方在成本上稳定占优。

上下文获取对比在同一代码快照上提出 20 个代码定位问题，在普通检索和图谱增强两种条件下比较关键文件覆盖率和累计模型 Token。总的结论是否定的：增强组平均覆盖率低 1.6 个百分点，平均累计模型 Token 高 11.2%，本地查询耗时中位数约为普通检索组的 3.3 倍。但这个否定结论比看上去更有信息量，它由四部分构成。

一是检索侧的差别是实的，可以离线量出来。增强组的注入内容由 6.4.5 节的两项配置与扩展通路的处理方式共同决定；按报告配置运行时，二十题的 62 个金标文件里，够得着的由 50 个增到 55 个、进得了压缩文本的由 49 个增到 55 个（表6-12），注入的上下文从"漏 13 个"变成"漏 7 个"，其中跨模块一类的差别最明显（28 → 32）。这是本章对"图谱检索本身好不好"的直接测量，不受智能体行为影响。

二是覆盖率的端到端差别量不出来，这一点如实登记。两档实现配置在同一条件、同一题集上的平均覆盖率都是 0.853（表6-13），而批次波动是 1.3 个百分点、批次跨度 0.838 到 0.867。指标分辨力不足的原因是单题金标只有 1 到 4 个：漏掉一个文件就是 8 到 33 个百分点，噪声淹掉了配置差别带来的那几个文件。因此本节不写"报告配置提升了覆盖率"，只写"报告配置让上下文里的答案变对变全"，并登记代价——Token 由 +3.6% 升到 +11.2%。

三是成本侧的方向明确。压缩保真把 Token 增幅由 +22.3% 降到 +3.6%（本地查询耗时中位数 1,313 ms → 1,086 ms），因为缺路径会让智能体多绕一轮，而前缀上下文每轮重发、绕一轮比上下文本身贵；报告配置为了把可达文件补全，注入的上下文从平均 86 个节点增到 194 个，Token 增幅回到 +11.2%，轮次稳定在 4.1（普通检索组 6.4）。也就是说，增强组现在用少三分之一的轮次、多约一成的 Token 换取同一水平的覆盖率。

四是形态侧的消融给出了否定答案。把上下文由预置一次改为智能体按需调用的工具，覆盖率持平而 Token 增幅由 +3.6% 升到 +19.4%；在提示里要求核对覆盖，覆盖率降到 0.848、Token 增幅升到 +32.8%；把"组织好的上下文"整个换成"候选路径清单"的导航形态（6.4.7 节），覆盖率仍与预置形态同一水平，Token 增幅升到 +34.1% 与 +57.9%，平均轮次由 4.1 升到 5.0 与 6.0。在上下文已经把信息给全的前提下，改注入方式、改提示语或改输出形态都换不来覆盖率收益，能换来收益的只有把该给的信息给全。

导航形态的价值落在另一处，也如实登记：它作为检索辅助件，在同一张子图上用正文形态 0.67 倍的体积给出相同的 55/62 可达路径，且每条路径附带到达方式。据此本方法把图谱的使用边界固定下来——**已有上下文（任务或计划指明文件、本会话读过该模块）就直接读文件；只有在"不知道代码在哪"、需要对陌生模块做一轮检索时，才以导航形态介入**，正文形态只用于通读模块、建立全局认知的场合。这一层收益可离线测量，不受智能体行为影响，而本章的定位指标量不到它。

因此本章没有观察到图谱增强在定位环节的整体收益：检索侧确实更完整了，但这份完整性没有转成覆盖率，反而先转成了 Token。可以继续改进的位置也随之明确——按三段归因，二十题的 62 个金标文件里进得了压缩文本的有 55 个，而全部增强运行中至少被提交过一次的有 59 个，两者的差说明漏的文件不是"上下文里没有"，而是"给了没被用上"：有 3 个文件进了文本却一次都没被提交，还有若干文件只在部分运行里被提交。前者要靠注入方式的进一步设计（例如让上下文以文件形式落地、避免每轮重发的同时要求智能体按覆盖清单核对），后者要靠更大的题集把噪声压下去，都不在本轮改动范围内。

本章不预先写"显著提升""全面优于"或具体下降比例。三组结果能支持到什么程度就写到什么程度：实现与设计一致、任务在选定项目上可以完成、定位环节的开销没有下降，是三个不同层面的结论，分别陈述。第三组是否定结果，它同样是对方法的一次检验，并且指出了可以继续改进的位置。
