# 第 1 章 引言

## 1.1 研究背景

在软件工程实践中，开发者需要分析用户需求，确定系统功能，设计接口、数据结构和模块关系，再编写代码并通过测试。系统投入使用后，还需要修复缺陷、调整接口和增加功能。无论是实现新功能还是修改已有功能，开发者都需要了解业务需求、接口约定、数据结构及相关模块之间的依赖关系。然而，这些信息通常分散在需求文档、设计文档、代码文件、配置文件和测试用例中，并由不同人员在不同阶段维护，难以仅从单个文件判断一项修改会影响哪些内容。因此，开发者需要结合当前任务查找并对照这些材料，梳理需求与代码之间的对应关系，才能确定修改位置和影响范围。

在上述开发工作中，人工智能（Artificial Intelligence，AI）最初主要承担代码补全任务。早期工具根据当前文件的上下文补全下一行代码或生成单个函数，模型只需要处理光标附近的内容[29]。这种方式能够减少代码输入工作，但需求如何拆分为模块、代码如何组织以及修改会影响哪些位置，仍需开发者判断。随着代码模型能力增强，模型开始能够读取外部材料，根据自然语言查找代码，并按照计划修改多个文件[5,11,35]。相应地，开发者交给模型的任务也从编写局部代码扩展到搜索项目、修改文件和运行测试。然而，任务范围扩大后，仅提供当前文件可能遗漏接口与依赖，输入整个代码库又会带入大量无关内容。长上下文研究也表明，输入变长并不能保证模型有效利用所有信息[4]。因此，智能体执行任务前仍需检索项目文件，并筛选和组织与任务相关的内容。

围绕真实项目中的文件搜索与代码修改，SWE-bench 开始用 GitHub issue（问题报告）检验模型能否完成项目修改[16]，SWE-agent、Devin 和 OpenHands 等智能体则将文件搜索、代码编辑、测试执行和结果反馈组织为连续过程[17,32-33]。这些工作推动 AI 编程进入真实开发环境，但开发者对其输出准确性的信任仍然有限[43]。对于这类开发任务，智能体不仅需要生成代码，还需要找到正确的文件、理解业务规则，并检查修改对其他模块的影响，而这些工作都依赖任务上下文是否充分、准确。

随着智能体开始参与实际开发，其应用也受到政策层面的关注，国务院于 2025 年发布《关于深入实施“人工智能+”行动的意见》，提出推动人工智能与各领域深度融合，加快智能体等应用落地[20]。这一背景推动了对智能体实际应用的探索，而在软件开发场景中，如何让智能体理解项目并持续完成任务，仍是需要解决的具体问题。

以“支持用户收藏菜品”为例，智能体要完成这一需求，就需要同时了解用户模块、菜品模块、数据库表、接口、权限和页面状态之间的联系。熟悉项目的开发者可以借助已有经验判断这些联系，智能体则需要从需求文字、代码结构和历史修改中查找并建立它们。然而，这些判断如果只留在当前对话中，后续任务便难以直接复用，而单独保存代码文本，又难以说明代码对应哪项业务能力。因此，仅为单次任务找到相关代码还不够，还需要保存业务需求与代码实现之间的对应关系，使后续任务能够沿用已有判断。

为保留项目中的关联信息，已有工作开始将代码实体及其关系组织成图结构，用于仓库级问答与推理[64]，也有工作通过程序血缘分析业务变动会影响哪些程序[42]，或利用规范文档和任务流程约束智能体的执行过程[8-9,90]。这些研究为代码关系查询、影响分析和开发流程管理提供了支持，但从连续开发任务的需要看，还需要把一项业务由哪些代码实现、需求变化后如何更新这些关系，以及后续任务如何调用这些信息联系起来考虑。

围绕这一需要，本文以需求规格说明（Specification，Spec）描述业务能力，并将业务能力与模块、文件和函数等代码结构建立映射，形成可持续维护的项目知识模型。在此基础上，任务到来时根据任务描述选择相关知识，生成受 Token 预算约束的上下文，而在需求或代码变化后，再更新受影响的节点与关系，使已保存的知识能够继续用于后续任务。通过连接需求规格、业务能力、代码实现、演化记录和任务上下文，本文研究如何使前序任务形成的项目认识能够被后续任务复用，减少反复搜索和重新理解项目的工作。

## 1.2 研究意义

上述问题表明，智能体参与长期项目开发时，不仅需要获取当前任务的相关代码，还需要保留业务需求与代码实现之间的联系。如果这种联系能够在任务之间持续维护，前序开发形成的判断就可以成为后续任务的依据。因此，研究项目知识的组织、调用与更新方式，有助于减少智能体对临时检索和单次对话的依赖。

在知识组织方面，本文建立 Spec 驱动的能力—代码双层知识组织模型，将需求规格、业务能力和代码结构关联起来。业务能力用于说明系统提供什么功能，代码结构用于说明这些功能由哪些模块、文件和函数实现，两者之间的映射使任务可以从需求语义追溯到实现代码，也使开发者能够从代码反向查找其对应的业务范围，为修改定位和影响分析提供依据。

在上述知识模型的基础上，任务执行还需要从中选择相关内容，因此本文研究图谱驱动的任务上下文生成方法，从持续维护的知识模型中选择与当前任务相关的内容，并在 Token 预算内组织为模型输入。与每次从整个项目重新查找相比，这种方式旨在复用已有的业务与代码关系，减少重复检索和上下文整理，并在需求变更时通过增量维护更新受影响的内容，使后续任务能够继续使用这些关系。

要使上述知识组织与按需调用方式服务于实际开发，还需要将知识的构建、使用和更新纳入智能体的执行过程。因此，本文结合已有代码检索、需求追踪和仓库知识图谱研究中的相关思路，将项目知识管理与智能体的开发流程衔接，形成从项目知识构建、任务上下文生成到增量维护的完整过程。为考察这一过程能否在实际开发中运行，本文进一步实现 Web 项目开发工作流（Web Project Workflow，WPW）原型系统，并以美食推荐系统的开发任务进行验证，为长期演化项目中的上下文管理提供可供检验和复用的工程方案。

## 1.3 国内外研究现状

### 1.3.1 研究进展

围绕智能体如何理解项目并完成任务，国内外研究已从局部代码生成扩展到仓库级开发。SWE-bench 用真实 GitHub issue 检验模型的项目修改能力[16]，SWE-agent 研究智能体与计算机之间的交互接口[17]，Devin[32]、OpenHands[33] 等系统则将文件编辑、命令执行与错误修复组织为连续过程。Hou 等人对大模型软件工程（Large Language Models for Software Engineering，LLM4SE）文献的梳理显示，相关应用已覆盖需求、设计、开发、质量保障和维护等环节[1]。与上述应用范围相对应，国内学者也分别梳理了预训练模型在软件工程中的应用[85]、深度学习驱动的代码生成[89]、自动代码修复[88]、缺陷检测与修复[84]以及基于大模型的代码智能体[87]。随着应用进入真实项目，研究进一步关注编程智能体的采用情况[2]及其作为软件工程团队成员对开发方式的影响[3]。

然而，“Lost in the Middle”研究表明，长输入中信息的位置仍会影响模型对信息的利用[4]，因此任务范围的扩大也带来了上下文获取与组织的问题。现有研究分别从需求与实现的对应关系、相关代码的检索及结构表示、仓库知识的组织三个方面提供支持，下面据此讨论需求追踪与规格驱动开发方法、代码检索与结构表示方法，以及仓库知识图谱方法。

（1）需求追踪与规格驱动开发方法

智能体根据业务任务定位代码时，需要先明确需求与实现之间的对应关系。围绕这一关系，需求追踪方法主要恢复需求与代码之间的链接，规格驱动开发方法则将需求规格作为开发活动的依据。前者侧重识别已有需求对应的实现，后者侧重约束需求如何进入开发过程，代表性工作包括信息检索类追踪方法、TRIAD，以及 GitHub Spec Kit、OpenSpec 和 Superpowers 等工具。

在需求追踪研究中，Cleland-Huang 等人较早讨论了如何提高需求追踪的投入产出比[13]。为减少人工建立链接的工作，后续研究尝试利用群体智能和信息检索恢复需求文档与代码之间的对应关系[15]。Borg 等人对这一方向的系统梳理表明，信息检索已成为追踪链接恢复的重要方法[14]，为从需求文本查找相关代码提供了基础。

在自动恢复链接方面，南京大学团队提出的 TRIAD 进一步利用了文本关联与链接传递信息[41]。该方法先从文档等材料中提取共识词对，增强材料之间的语义关联，再沿已有的传递链接推导需求到代码的追踪关系，从而识别直接匹配难以发现的间接联系。不过，该方法主要回答如何恢复追踪链接，而要使恢复结果在需求变化后仍可使用，还需要结合知识管理过程设计长期维护与持续更新的方式。

与从已有材料中恢复链接不同，规格驱动开发（Spec-Driven Development，SDD）从开发过程的起点组织需求，将规格的编写、确认与实现作为连续活动。围绕这一思路，Tufano 等人对规格优先的智能体工作流进行了实证研究[61]，相关工具则分别从规范组织、变更管理和执行流程约束等方面支持智能体开发。

在规范组织方面，GitHub Spec Kit 用一组规范文档和任务产物组织智能体的开发过程[8]。项目先以 Constitution 确定总体约束，再由 Specification 描述需求，Plan 将需求转化为实现方案，最后拆分为可执行任务。这使需求与计划能够被保存和检查，智能体也有了对话之外的开发依据。然而，这套流程主要组织“要做什么”和“如何实施”，并不以持续维护业务能力与实现代码的映射、据此生成任务上下文为主要目标。

在规范随需求变化的维护方面，OpenSpec 以 Change 为单元管理需求演化[90]。每次变更包含提案、设计和任务等产物，实施完成后归档并更新既有规格，使变更过程和当前规格能够对应起来。相比只保存一次性的需求描述，这种方式提供了明确的演化记录。不过，变更记录本身并不等同于可查询的业务—代码映射，因此要沿业务关系定位代码并生成任务上下文，仍需补充关系提取与维护过程。

除了保存规范与变更，Superpowers 更强调智能体执行过程中的约束[9]。需求澄清、计划、开发、测试和审查由相应技能定义，子代理按分工执行，使各阶段的工作要求能够落实到具体步骤。这种方式为执行过程提供了规则，但流程记录与对话产物要被后续任务直接查询和调用，还需要转化为持续维护的项目知识结构。

由此可见，需求追踪方法为恢复需求与代码的联系提供了手段，规格驱动工具则为保存需求、组织变更和约束执行提供了支持。二者的关注点不同，不能将链接恢复或流程管理直接视为完整的任务上下文生成过程。本文关注的是如何将这些需求侧信息与代码结构联系起来，并在项目迭代中持续使用。考虑到 Spec Kit、OpenSpec 和 Superpowers 仍在迭代，以下比较限定于本文检索和实验采用的版本，具体环境与版本记录见附录。

（2）代码检索与结构表示方法

需求侧信息需要与具体实现关联，代码检索与结构表示方法为查找这些实现提供了基础。前者根据文本或代码相似度返回相关内容，后者保存代码实体之间的语法、数据流或依赖关系。两类方法分别回答“哪些代码与任务相关”和“这些代码如何关联”，代表性工作包括检索增强生成（Retrieval-Augmented Generation，RAG）、代码属性图、GraphCodeBERT 和 RepoHyper 等。

在内容获取方面，RAG 将外部知识检索接入生成过程，使模型可以在执行任务时读取参数之外的信息[5]。围绕这一检索与生成过程，国内研究进一步讨论了 RAG 在软件工程中的应用[86]、面向大模型的检索增强方法[75]、基于滑动窗口策略的检索增强生成系统[76]、检索增强生成的整体框架[77]、RAG 驱动的知识服务[78]及其在平行人与平行智能中的应用[79]。这些研究为按需提供外部信息提供了方法基础，但当检索主要依据文本相似度时，返回的代码片段未必同时包含其调用和依赖关系，模型仍可能需要继续搜索，才能判断修改范围。

为补充片段之外的关联信息，结构表示研究将代码实体及其关系显式保存下来。Yamaguchi 等人提出的代码属性图（Code Property Graph）将抽象语法树、控制流图和程序依赖图合并为可查询的图模型，用于漏洞挖掘[18]。沿着将结构信息纳入代码表示的思路，GraphCodeBERT 将数据流引入代码表示学习[11]，而知识图谱研究则系统总结了以实体、关系和属性组织领域知识的方式[37]，为保存和查询代码关系提供了参考。

当任务扩展到整个代码仓库后，多文件之间的联系也进入生成过程，其中 CodePlan 用计划组织仓库级修改的多个步骤[35]。在为模型提供相关实现信息时，CatCoder 将静态分析得到的类型信息与检索结果共同提供给模型，用于上下文感知的代码补全[34]，RepoHyper 则利用代码结构超图执行“搜索—扩展—精炼”[36]。

沿着结构分析与检索结合的思路，CoRAG 将抽象语法树检索与大模型结合用于代码重构[72]，叶子健将检索增强与智能体协同用于代码生成[71]。与这些方法对代码结构的利用相呼应，代码坏味检测与重构研究也体现了结构信息与多层次语义对代码理解的作用[81-83]。CodeGeeX[29] 等工具则将代码补全、解释和对话能力接入开发环境，为相关方法的应用提供模型与工具支持。

上述方法使模型能够获取相关代码，并利用代码结构补充片段之间的联系。但代码实体之间的调用或依赖，尚不能直接说明它们共同实现哪项业务需求。因此，在代码检索和结构表示的基础上，还需要引入需求语义及其与代码的映射，才能支持从业务任务出发的定位。

（3）仓库知识图谱方法

在代码结构表示的基础上，仓库知识图谱方法进一步将仓库中的文档、代码实体及其关系组织为可查询的知识结构，并将查询结果用于智能体的定位、生成和问答。面向软件仓库问答的知识图谱研究[64]体现了这一思路，即先保存仓库中的关联，再根据任务利用这些关联获取信息。

除了支持仓库问答，已保存的代码关系还可以用于分析修改影响，中国工商银行软件开发中心通过抽象语法树和字节码分析构建全链路程序血缘，用于判断交易变动会影响哪些程序[42]。与仅返回相似代码相比，程序血缘提供了沿程序关系追踪影响范围的依据。

当图结构进一步与大模型结合时，研究开始关注模型如何查询和利用其中的知识。Abedu 等人探讨了知识图谱对软件仓库问答的支持[64]，Jiang 等人则将知识图谱作为复杂智能体推理和记忆的状态空间[65]。围绕图结构与大模型的结合，国内研究也从不同角度展开探索，刘龙将增强型代理上下文工程用于网络威胁情报知识图谱构建[70]，李登飞等从基础层、核心层与应用层梳理大语言模型与知识图谱的融合范式[73]，郑艳萍等综述了大模型驱动的文本属性图学习进展[74]。通过讨论知识构建、融合方式与图学习过程，这些工作为图结构参与知识获取、推理和生成提供了参考。

仓库知识图谱由此为保存代码关系并将其提供给智能体建立了基础，但不同研究保存的知识对象和服务的任务并不相同。对于以文件、类、函数和架构依赖为中心的图谱，仍需进一步说明业务需求如何成为图中的可查询对象，以及需求变化后相关映射如何维护。其他领域的大模型与知识图谱融合研究可以提供方法参考，但其作用还需要在软件开发任务中具体检验。

### 1.3.2 综述分析

从需求侧、代码侧和仓库知识组织侧来看，上述三类研究各有侧重，需求追踪与规格驱动方法保存需求及其开发过程，代码检索与结构表示方法帮助查找和理解实现，仓库知识图谱则使实体之间的联系能够被查询和复用。因此，比较这些方法时，除了关注单次任务能否找到相关代码，还需要考察它们保存什么知识、知识如何进入后续任务，以及项目变化后如何继续维护。

按照这一思路，本文先比较代表性工作流工具维护的核心对象。Spec Kit 主要组织规范与计划，OpenSpec 主要管理变更及相关产物，Superpowers 主要约束技能调用与执行过程，而本文关注业务能力、实现代码及其演化关系。表1-1列出它们在知识对象与上下文组织方式上的区别，后文再结合检索、追踪和图谱方法分析尚需衔接的环节。

从知识对象及其维护周期看，代码检索和结构表示主要围绕文件、类、函数及其依赖展开，需求追踪与规格工具则保存需求描述、追踪链接或变更记录。这些对象分别承载了需求与实现两侧的信息，但要持续回答“一项业务由哪些代码实现”，还需要明确业务能力及其映射的表示方式。在维护周期上，CatCoder 和 TRIAD 分别侧重当次补全与链接恢复，程序血缘等方法虽然能够沿程序关系分析影响，但其主要维护对象仍与代码结构相关。因此，本文需要将业务能力纳入知识模型，使需求语义与代码结构之间的联系具有明确的记录对象。

知识被保存下来之后，还需要说明它如何进入任务，以及如何随项目变化更新。RAG 和 RepoHyper 等方法提供了按需检索与结构扩展的思路，但一次检索的结果并不会自然成为后续任务可直接使用的项目认识。Spec Kit、OpenSpec 和 Superpowers 保存了规范、变更与流程产物，但从这些记录生成受预算约束的任务上下文，仍需设计选择与组织过程。同时，OpenSpec 的变更管理为按单元记录需求演化提供了参考，而要使业务—代码关系随需求变化保持有效，还需要把需求变更与受影响节点、关系的更新衔接起来。

因此，本文围绕上述环节之间的衔接，以 Spec 及其变更为知识演化的触发单元，用业务能力连接需求语义与代码结构，并在持续维护这些联系的基础上生成受 Token 预算约束的任务上下文。本文沿用已有代码检索和图结构表示思路，重点研究需求规格、业务能力、代码实现、项目演化与任务上下文如何形成连续的知识使用过程。为说明这一研究思路与已有工作的联系，图1-1对照呈现了需求侧、代码侧研究的关注点以及本文连接业务能力与代码的方式。

## 1.4 研究内容

根据上述分析，本文围绕项目知识的表示、调用与更新开展研究。表示环节需要记录业务能力及其实现代码，调用环节需要从中选出当前任务所需的内容，更新环节则需要使已有关系随需求和代码变化而调整。这三个环节需要相互配合，因为缺少稳定的表示会使任务依赖重新检索，缺少按需调用会使保存的知识难以进入模型输入，而缺少持续更新又会使已有知识逐渐偏离当前项目。

为连接这三个环节，本文研究 Spec 驱动的能力—代码双层知识组织模型、图谱驱动的任务上下文生成方法，以及随需求迭代运行的增量知识演化机制。研究范围集中于交给模型的上下文如何组织，不改动大模型本身，也不替代智能体运行框架。

为明确知识在何时产生、使用和更新，开发过程按业务需求文档（Business Requirements Document，BRD）、产品需求文档（Product Requirements Document，PRD）、Design、Plan、Test 和 Apply 六个阶段推进，并通过阶段产出与进入条件约束调用顺序。在此基础上，本文实现 WPW 原型系统并开展验证，核心研究内容如图1-2所示，具体包括以下四个层面。

![图1-2 核心研究内容 | Figure 1-2 Core Research Content](图表/第1章/图1-2-核心研究内容.png)

图1-2 核心研究内容

Figure 1-2 Core Research Content

（1）在知识建模层面，建立业务能力与代码结构之间的对应关系。按文本或符号搜索能够找到相关片段，但要判断一项业务由哪些代码实现，还需要保存业务侧的描述及其映射依据。本文用 Spec 描述业务能力，通过多语言源码解析获得模块、文件和函数三级代码结构，再从文档、命名、语义和 Git 历史中收集映射证据，利用 noisy-OR 概率模型合成关联边，并保留证据来源。由此得到的图谱通过 JSONL 文件和本地向量索引保存，为任务查询与后续更新提供共同的数据基础。

（2）在上下文生成层面，从上述知识模型中选择当前任务所需的内容。由于任务通常只涉及项目的一部分，本文先根据任务描述选择入口节点，再沿关联边扩展任务子图，使相关业务能力与实现代码能够一并进入候选范围。随后，根据节点与入口的距离抽取代码骨架、调整保留细节，并按 Token 预算选择压缩档位。如果输出仍超出预算，则继续降低信息粒度或缩小范围，使持续维护的项目知识能够转化为当前任务可以使用的上下文。

（3）在知识演化层面，本文维护上下文生成所依赖的图谱，使其能够反映当前项目。由于需求迭代和代码修改会改变能力节点及其映射，图谱中的相关内容也需要随之调整。为使后续任务继续获得有效信息，本文以需求 Spec 及其变更触发知识更新，在新项目中结合源码扫描与需求 Spec 建立初始图谱。当已有项目接收新需求时，则先形成 Spec，再关联既有能力节点，并更新受影响的代码索引与映射关系。通过这一过程，项目知识能够随开发持续积累，无需每次重新构建完整图谱。

（4）在系统实现与方法验证层面，将上述机制整合为 WPW 系统。系统分为智能体交互层、命令行界面（CLI）层与文件存储层，实现工作流管理、图谱构建、上下文生成和增量维护四个模块，并通过可视化控制台展示流程状态、图谱结构与上下文结果。

为验证系统与方法，本文以美食推荐系统为案例，先通过功能测试检查各模块是否按预期运行，再设置基础搭建（T1）、业务核心（T2）、迭代增强（T3）和连续需求（T4）四类开发任务，共 12 个任务，让 OpenSpec 与 WPW 从相同前置版本出发完成相同任务，比较任务完成情况与模型总 Token 消耗。由于任务级总量不能单独解释上下文获取环节的作用，进一步在同一代码快照上开展检索与问答实验，分别设置 100 个信息需求和 100 个问题，比较非 KG、WPW-Map 与完整 WPW 三种条件下的文件定位质量、回答正确性及上下文开销，并据此讨论方法的作用范围。

## 1.5 论文组织结构

围绕上述研究内容，本文依次展开技术基础、方法设计、系统分析与实现，以及实验验证，共分为七章，各章安排如下。

第 1 章为引言，从软件开发中的信息获取与使用问题出发，说明研究背景与意义，分析国内外研究现状，并据此明确本文的研究内容。

第 2 章为相关技术与理论基础，为后续方法设计介绍大语言模型与 AI 编程智能体的基本原理、能力边界和执行方式，梳理上下文获取、组织、压缩与记忆方法，并说明知识图谱构建、语义匹配、图搜索及 SDD 方法等技术基础。

第 3 章为面向 AI 辅助开发的上下文工程方法，在上述技术基础上给出总体框架，依次说明项目知识如何建模、如何转化为任务上下文，以及如何随项目变化更新，最后介绍将三项机制整合进开发过程的流程约束架构。

第 4 章为系统需求分析，根据方法运行与使用的需要，明确 WPW 系统的使用者、使用场景和约束条件，分析功能需求与非功能需求，为系统设计提供依据。

第 5 章为系统设计与实现，依据需求分析，将所提出的方法落实为 WPW 系统，说明三层架构及工作流管理、图谱构建、上下文生成和增量维护四个模块的设计与实现。

第 6 章为系统测试与结果分析，以美食推荐系统为案例，交代项目规模与实验条件，通过功能测试检查系统实现，再比较 WPW 与 OpenSpec 完成开发任务的情况及模型总 Token 消耗，并通过检索与问答实验考察上下文定位与供给的表现，最后讨论结果的适用范围与局限。

第 7 章为总结与展望，总结方法设计、系统实现与实验验证的主要工作，结合现有局限提出后续研究方向。
