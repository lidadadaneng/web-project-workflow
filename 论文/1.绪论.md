# 第 1 章 引言

当 AI 编程智能体从补全代码转向承担连续的软件工程任务时，项目上下文便成了决定其能否稳定工作的关键条件。长期项目中，业务能力和代码结构往往分开存在，代码库还会不断扩大，需求迭代留下的知识也不一定能够继续使用。本文把这三种相互关联的现象统称为**项目知识失忆**。研究由一个具体问题展开：怎样把项目知识整理成智能体能够长期调用的结构化模型，并根据当前任务提供合适的上下文。围绕这一问题，本文研究面向 AI 编程智能体的软件项目知识建模与上下文生成方法，并以基于大模型的美食推荐系统作为实验载体进行验证。

## 1.1 研究背景

本节先说明开发方式的变化，再说明这种变化在长期项目中暴露出的上下文困难，随后引出软件项目知识组织和任务级上下文构建的需求，最后解释实验载体的选择。

### 1.1.1 大模型驱动的软件开发模式变化

大模型在软件工程中的角色，已经由一次性的代码补全延伸到连续任务执行。ChatGPT 主要提供通用对话能力，GitHub Copilot 面向编程补全，Claude Code 则把模型接入终端环境参与实际编程[28]。随着应用范围扩大，需求分析、设计、计划、测试和实现都开始出现 AI 辅助，能够自行规划并调用工具完成多步工作的 coding agent 由此形成。Hou 等人对 395 篇 LLM 软件工程（LLM4SE）文献的梳理表明，研究对象已从生成、补全、翻译和解释等局部任务扩展到需求工程、软件设计、开发、质量保障及维护[1]。2025 至 2026 年的实证研究还在真实开源项目中记录了 coding agent 的采用情况[2]，并系统分析了仓库中的 AI 辅助开发活动[3]。当模型需要连续完成任务时，规划、工具调用、状态保存和长程执行就成为必要环节，Agent 运行框架（Agent Harness）以及 SWE-agent 关于智能体—计算机接口的研究也因此受到关注[17]。

智能体的执行能力并不会自动消除上下文限制。一次交互能够利用的信息仍受窗口长度、注意力分布和调用成本约束；项目指令、会话状态、代码索引和持久化记忆虽然能够提供跨任务信息，但通常分散在工具内部或文档中，尚未形成一个随项目变化而维护的统一知识模型。模型因此很难把单次能力稳定迁移到长期软件项目，这正是后文要讨论的项目知识问题。

### 1.1.2 AI 编程智能体的长期项目知识问题

单个函数或文件通常不会暴露明显的上下文缺口。项目扩展到数十甚至上百个模块，并且持续发生修改后，相关困难才集中显现。本文将这些情况归为三类，统称为**项目知识失忆**。

第一类问题来自代码库的体量。真实项目常有数十万乃至百万行代码，完整塞入提示既不现实，也会使 Token 成本随输入同步上升；模型对长输入的有效利用却未必增加。即便窗口容量足够，信息所在位置仍会影响利用效果，相关位置效应被称为“Lost in the Middle”[4]。整库注入还会把无关内容和定位负担一并带入任务。已有实证表明，智能体通常通过人工搜索或整库注入取得上下文[3][10]：前者需要投入较多时间，且可能遗漏相关代码；后者则同时承担成本增加和信息稀释。

第二类问题是业务语义与代码结构彼此分离。软件项目还包括需求、设计、架构、实现和演化等知识，代码只是其中一种载体。以新增“会员积分功能”为例，智能体既要判断所属业务模块，也要找到相关文件和接口，还要弄清原有设计的依据；这些线索可能分别存在于需求文档、注释、提交历史和开发者经验中。传统代码检索能够返回与查询相似的代码，却难以说明一项业务能力由哪些代码共同实现，以及这种联系如何随需求变化而更新。因此，**代码搜索不等于软件知识**。业务与代码的映射不清，跨模块遗漏和依赖破坏便更容易发生[18]。

第三类困难在项目持续演化时显现。对话历史能够保存交互片段，却通常不能成为可持续、结构化的项目知识资产。现有工具虽有项目指令、代码索引和持久化记忆，需求迭代过程中形成的业务知识、需求关系及代码关联仍缺少统一模型，新任务往往还要从头理解项目。需求迭代、功能增加和代码重构不会停止；没有**项目级持续知识资产**，过去的演化结果就难以参与下一次上下文构造，项目理解成本也会反复发生[3][10]。

### 1.1.3 软件项目知识图谱与上下文构建需求

三类困难共同指向上下文工程（Context Engineering）。它位于模型能力和软件工程过程之间，处理的不是模型参数，而是围绕任务目标组织、筛选、压缩并提供外部知识、代码结构和执行状态[5][6]。RAG 研究已经说明，按需访问外部非参数化知识能够减轻参数化知识在访问和更新上的限制[5]；2025 至 2026 年的智能体研究则把仓库级上下文（repository-level context）和可执行反馈列为重要资源[6]。

上下文能否被有效利用，还取决于知识的组织方式。知识图谱用实体和关系显式表示领域知识[37]，为业务能力、代码结构和演化历史建立持续维护的项目知识模型提供了可行形式；再从这个模型中生成任务所需的信息，正是本文的切入点。上下文检索、压缩、记忆管理和工具调用等研究正在汇聚为上下文工程，研究关注点也从一次提示词设计或临时检索，逐步转向知识模型本身以及知识如何进入智能体。

因此，本文把研究对象限定为软件项目知识的组织方式和模型输入上下文的质量。基础模型与 Agent 运行框架（Harness）已经提供代码生成和任务执行能力，本文关注的是在长期演化的软件工程项目中，怎样构建、管理并复用高质量上下文。

### 1.1.4 基于大模型的美食推荐系统作为实验载体的需求

验证上述方法需要一个既有业务复杂度、又能完整运行的系统。美食推荐平台具备 Web 系统常见的业务形态：用户认证、内容浏览、个性化推荐、购物车、订单交易、收藏和评论等功能并存；用户、菜品、订单与评价之间存在较多关联，需求边界和需求符合度可以据此判断。系统还能够经历需求、设计、实现和迭代的完整过程，适合用来观察软件开发方法在连续任务中的表现。

系统本身采用常规推荐设计，推荐模块以用户偏好规则计算为核心，不使用大模型增强推荐。“基于大模型”指开发过程由大模型辅助完成，本文考察的也是这一过程中的上下文组织，推荐算法效果不在评价范围内。美食推荐系统因此同时承担两种角色：它是验证软件开发方法的实验载体，也是论文题目所指向的系统实现对象。系统实现和方法验证在同一 Web 载体上完成，具体定位见第 5 章。

## 1.2 研究意义

### 1.2.1 理论意义

理论上，本文把 AI 编程智能体的项目知识建模和上下文生成作为研究主线，设计能力—代码双层知识组织模型、Spec 增量知识演化机制，以及图谱驱动的任务上下文生成方法。三者共同用于分析长期演化项目中的知识如何进入智能体上下文，并为后续实验提供方法框架。

### 1.2.2 实践意义

实践上，上述设计由 wpw（Web Project Workflow）系统承载。系统以结构化知识供给、增量知识维护和上下文压缩分别应对项目知识获取、需求变化与 Token 开销，并在基于大模型的美食推荐系统中评价知识组织与上下文获取机制。增量维护的长期效益不作为本文的独立实证结论。研究问题直接来自 AI 辅助开发的工程实践。

## 1.3 国内外研究现状

与本文相关的研究并不是从 AI 编程智能体开始的。早期工作先解决需求与代码怎样建立联系、代码结构怎样表示；大模型出现后，研究重点逐步转向代码检索、仓库级生成和任务执行；当智能体开始连续参与开发，项目知识怎样保存、更新和进入任务上下文才成为直接问题。因此，本节按照这一发展过程梳理国外和国内研究，再说明现有工作与本文的差异。Spec Kit、OpenSpec、Superpowers 仍在快速迭代，本文只讨论截至 2026 年 8 月检索到的版本，并在附录实验环境表中固定版本号、发布日期和代码提交记录。

### 1.3.1 国外研究现状

2004 年前后，相关研究主要处理需求与代码之间的追踪问题。Cleland-Huang 等人研究了如何提高需求追踪的投入产出比[13]，后续工作又尝试用群体智能和信息检索恢复需求制品与代码之间的链接[15]。Borg 等人在 2014 年对这一方向进行了系统梳理[14]。同一时期，代码表示也从文件和文本逐步深入到程序结构。Yamaguchi 等人在 2014 年提出代码属性图（Code Property Graph），把抽象语法树、控制流图和程序依赖图合并为可查询的图模型[18]。这些研究分别建立了需求—代码链接和代码结构图，但当时的目标主要是追踪与静态分析，还没有面向 AI 编程智能体组织任务上下文。

2019 至 2022 年，研究开始解决模型怎样从外部信息中找到所需内容。CodeSearchNet 在 2019 年定义了自然语言—代码检索任务，并提供大规模数据集[12]。RAG 在 2020 年把外部知识检索接入生成过程，使模型可以在执行任务时读取参数之外的信息[5]。随后，GraphCodeBERT 把数据流加入代码表示学习[11]，知识图谱研究也系统总结了如何用实体、关系和属性组织领域知识[37]。这一阶段形成了两条基础路径：一条根据文本或代码相似度返回相关片段，另一条显式保存代码实体之间的结构关系。但是，检索结果通常服务于当前问题，需求语义、代码结构和项目演化仍分别保存在不同位置。

2023 年以后，大模型的代码能力提高，研究对象开始从单个函数扩展到整个代码仓库。Code Llama 等代码模型强化了代码生成与理解能力[30]，CodePlan 则用计划组织仓库级修改涉及的多个步骤[35]。同年，“Lost in the Middle”研究表明，即使模型能够接收长输入，信息所在位置仍会影响模型是否真正使用这些内容[4]。这说明扩大上下文窗口并不能代替内容选择，模型仍要先找到相关代码，再把它们组织成当前任务能够使用的输入。

到 2024 年，研究进一步从仓库级生成转向能够执行完整任务的 AI 软件工程智能体。SWE-bench 用真实 GitHub issue 检验模型能否完成项目修改[16]，SWE-agent 研究智能体与计算机之间的交互接口[17]，Devin[32]、OpenHands[33] 等系统则把文件编辑、命令执行和错误修复放进连续执行过程。Hou 等人对 LLM4SE 文献的梳理也显示，大模型在软件工程中的应用已经由代码生成、补全和解释扩展到需求、设计、开发、质量保障和维护[1]。与此同时，RepoHyper 用代码结构超图执行“搜索—扩展—精炼”[36]，GraphRAG 用实体—关系图连接检索与生成[19]。研究由此不再只问“模型能否生成代码”，而开始处理“完成一项仓库任务需要哪些上下文”。

2025 至 2026 年，仓库知识与智能体执行开始直接结合。Athale 等人使用代码仓库知识图谱增强演化代码库上的仓库级代码生成[39]。Repository Intelligence Graph 为 Claude Code、Cursor、Codex 等智能体提供确定性的仓库架构图，并在多个仓库上考察代码定位和任务完成情况[40]。同一时期，Chinthareddy 比较 AST 派生图与大模型抽取图在代码库 Graph-RAG 中的可靠性[63]，Abedu 等人研究知识图谱如何支持软件仓库问答[64]，Jiang 等人把知识图谱作为复杂 Agent 推理和记忆的状态空间[65]。真实项目研究也开始记录 coding agent 的采用情况[2]，并分析智能体重构的类型、动机和代码质量变化[10]。代码图谱已经能够服务智能体，但图中的主要对象仍是文件、类、函数、架构依赖或 Issue、PR 等仓库制品。

智能体能够连续执行任务以后，开发过程本身也需要约束。工程社区在 2025 至 2026 年间逐渐用规格、工作流和任务分解来组织智能体。Piskala 将规格驱动开发（Spec-Driven Development，SDD）概括为由“代码即事实源”（code-as-source）转向“规格即首要制品”（specification-as-primary-artifact）[7]。GitHub Spec Kit 用 Constitution、Specification、Plan 和任务分解管理项目级规范，OpenSpec 用 Action 和 artifact graph 管理变更制品，Superpowers 则用可组合技能和强制工作流约束需求澄清、计划、开发、测试和审查过程[8][9]。随后，Haeri 等人考察规格 grounding 与大模型代码测试效果之间的关系[60]，Tufano 等人对 specification-first agent workflow 进行了实证研究[61]，Saha 等人从生命周期和制品追踪角度梳理了规格驱动智能体开发[62]。这些工作让智能体执行过程更容易检查和追踪，但各自维护的核心对象不同。表1-1列出这些工具与本文方法所维护的知识对象。

### 1.3.2 国内研究现状

国内相关研究同样先从代码模型和编程工具开始。代码表示方面，GraphCodeBERT 等工作把数据流等结构信息加入模型输入，为国内后续代码模型研究提供了技术参照[11]。随着通义千问[21]、文心[22]、混元[23]、GLM[25]等平台发展，国内大模型逐步进入代码生成和编程辅助场景。CodeGeeX、通义灵码等工具把代码补全、解释和对话能力接入开发环境[29]，研究和产业实践的关注点仍主要是模型能否理解并生成代码。

2024 年前后，国内工作开始从单文件生成转向仓库级理解。DeepSeek Coder 通过代码数据和项目级训练提升代码任务表现[31]。浙江大学团队提出 CatCoder，把静态分析得到的类型信息与检索结果一起提供给模型，用于上下文感知的代码补全[34]。同年，南京大学团队提出 TRIAD，利用共识词对和制品之间的传递链接恢复需求到代码的追踪关系[41]。前两项工作帮助模型找到和理解代码，TRIAD 则尝试连接需求与实现，但这些关系主要服务于当次补全或链接恢复，还没有作为项目知识长期更新。

进入 2025 年后，研究对象进一步扩展到真实仓库和智能体任务。KGCompass 由燕山大学牵头、多家机构合作完成，它把 Issue、PR、文件、类和函数组织成仓库感知知识图谱，再用图路径帮助智能体定位修复位置，并支持图谱随仓库变化增量更新[38]。同年，中国工商银行软件开发中心利用抽象语法树和字节码分析构建全链路程序血缘，用它判断交易变动会影响哪些程序[42]。这两项工作分别来自开源仓库修复和大型企业软件维护，都说明只保存代码文本还不够，实际开发还需要持续维护代码之间以及业务变动与代码之间的联系。

国内大模型生态也在这一时期继续扩展，豆包[24]、Kimi[26]和 DeepSeek[27]等平台进入更多应用场景。国务院在 2025 年发布《关于深入实施“人工智能+”行动的意见》，提出推动人工智能与各领域融合，并加快智能体应用落地[20]。研究关注点也从工具介绍转向真实开发活动。文献[3]借助 AIDev 数据集分析真实仓库中的 AI 辅助开发，指出智能体产出与人类开发者之间仍有差距。到 2026 年，关于智能体自演化的综述开始把仓库级上下文、可执行反馈和记忆机制放在同一条发展线上讨论[6]。

从国内的发展过程看，代码模型和编程助手解决了代码生成与交互入口问题，CatCoder、TRIAD 等工作把检索范围扩展到仓库和需求制品，KGCompass 与程序血缘又开始用图结构保存仓库关系和影响范围。国内已经出现代码知识服务智能体的研究和工业实践，但把 Spec 作为需求变化的记录单元，把业务能力与代码结构连接起来，并在后续任务中继续调用这部分知识的工作仍然较少。

### 1.3.3 现有研究不足归纳

总体而言，代码语义检索、仓库级代码生成、代码知识图谱、软件制品追踪及 AI Agent 工作流已经形成一定积累。KGCompass、Repository Intelligence Graph 等研究还通过实验表明，结构化仓库知识有助于改善智能体的代码定位和任务执行[38][40]。

现有工作多以代码实体、架构依赖或 Issue/PR 等仓库制品为知识对象，重点放在代码结构、制品管理或一次任务的检索。本文所关心的是需求和规格表达的业务能力，以及业务能力与代码实现之间会随项目变化的关系。如何把 Spec/Change 作为知识演化单元，让 Capability 处在需求语义和代码结构之间，并在持续开发中维护这条联系、据此生成任务上下文，尚未形成统一的方法。本文因此不重新提出代码图谱或代码检索，而是研究 **Spec -> Capability -> Code -> Evolution -> Context** 这条长期知识链在 AI 编程智能体中的应用。

## 1.4 研究目标与研究方法

### 1.4.1 研究目标

本文的问题起点是长期项目中的**项目知识失忆**：业务能力没有和代码结构对齐，代码规模使窗口利用受限，需求演化又缺少可持续的知识积累。现有研究分别推进了代码检索、需求追踪和仓库级理解，但还没有解决业务能力、代码结构和演化信息如何在同一项目知识模型中长期维护的问题。本文不改进基础模型，也不替代 Agent 运行框架；研究范围限定为模型输入上下文的组织与供给。下面三个目标分别对应上述三类问题，并可在实验中单独检验。

总体目标是面向长期演化的软件工程项目，为 AI 编程智能体建立能够持续构建、管理和复用的项目知识模型及任务上下文生成方法，使每次开发任务取得的上下文与任务相关、Token 开销可负担，并能随项目变化积累。这个目标进一步分解为三个具体目标。

**（1）建立业务能力与代码结构的统一知识表示**。代码检索能够返回文本或符号匹配结果，却不能说明某项业务能力由哪些代码实现、这些代码为何这样组织。本文拟把业务能力、模块、文件、函数及其关联放入同一项目知识模型，使业务语义和代码结构可以显式表示、查询并维护。

**（2）建立任务相关上下文的生成方法**。大型代码库不宜全量输入，人工定位相关代码又耗时并可能遗漏。本文拟在给定 Token 预算内，从项目知识中筛出与任务高度相关且足够完成任务的上下文。

**（3）建立项目知识的持续积累机制**。对话历史往往在会话结束后失去作用，后续任务仍需重新理解项目。本文拟使项目知识随着需求迭代和代码演化增量更新，供智能体在后续任务中复用。

### 1.4.2 研究方法

针对上述目标，技术路线分为知识建模、上下文生成和增量演化三个层次，并由流程约束架构把三者放回同一开发过程。每个层次对应一个研究目标。

知识建模层形成能力—代码双层知识组织模型（第 3 章）。Spec 描述业务能力，多语言源码解析得到模块、文件和函数三级代码结构；文档提取、命名匹配、语义匹配及 Git 历史提供业务能力与代码之间的证据，再由 noisy-OR 概率模型合成为关联边。图谱使用 JSONL 文件和本地向量索引保存，无需独立数据库。

上下文生成层提出图谱驱动的任务上下文生成方法（第 3 章）。系统依据任务描述和置信度衰减权重选择锚点，再以加权双向 BFS 扩展任务子图；随后按节点与锚点的距离抽取骨架，并以多档压缩方式完成序列化。Token 预算贯穿整个过程，超出预算便降低信息粒度，保留完成任务所需的核心上下文。

增量演化层提出 Spec 增量知识演化机制（第 3 章）。新项目通过“源码扫描 + 需求 Spec”完成冷启动；存量项目引入新需求时，先形成 Spec，再关联既有能力节点并更新受影响的代码关系，不必每次全量重建图谱。

流程约束架构位于三个机制之上，包含 BRD、PRD、Design、Plan、Test、Apply 六个阶段。阶段制品和状态管理限定智能体的执行，并规定各阶段如何请求和消费上下文（第 3 章）；整体方法由 wpw 系统实现（第 4 章“wpw 系统设计与实现”）。

第 6 章采用分层实验检验上述方法。实验以第 5 章实现的美食推荐系统为载体，任务级开发实验设置基础搭建（T1）、业务核心（T2）和迭代增强（T3）任务，在共同 SDD 流程下比较 OpenSpec 与 wpw；100 个检索任务和 100 个项目场景问题分别评价相关代码定位质量以及项目理解的正确性与成本，并在相同题集内通过组件开关检验 KG、业务—代码映射和上下文生成的增量作用。评价指标和数据处理规则在实验前冻结，结论不预设方向并以实际记录为依据。

## 1.5 创新点

本文的创新集中在业务—代码关联表示、任务上下文生成和知识持续积累三个问题上，系统实现与实验验证作为第四部分说明。

### 1.5.1 面向长期软件演化的 Spec 驱动能力-代码双层知识组织模型

代码图谱主要描述代码实体的结构关系，需求追踪也多以一次性恢复需求—代码链接为目标，二者都没有把业务能力作为长期知识对象。针对这一空缺，本文提出 Spec 驱动的 Capability-Code 双层知识组织模型（第 3 章），形成 Spec -> Capability -> Code -> Evolution -> Context 知识链。C 层表示业务能力（如用户认证），L1、L2、L3 分别表示模块、文件和函数，业务能力节点由此串联代码结构。Spec 保存需求来源和内容，Capability 表达项目已有能力，代码层说明具体实现，演化机制和上下文生成方法分别负责更新关联与选择知识。

模型需要自动建立业务—代码联系。本文从文档提取、命名匹配、语义匹配和 Git 历史中收集四类启发式证据，再用 noisy-OR 概率模型合成为 business_map 关联边，并为每类证据设定权重区间与剪枝规则。关联建立不要求人工逐条标注，同时保留每条边的证据来源，便于追溯。

与 KGCompass、Repository Intelligence Graph 等以代码实体和架构依赖为主的仓库图谱相比，本模型把业务能力作为语义锚点，维护的是**需求语义与代码实现的关联**；与一次性需求追踪不同，它面向项目演化持续更新。创新点不在知识图谱这一形式，而在于为 AI 编程智能体定义 Capability-Code 结构，并让该结构随 Spec 演化。它为任务上下文提供业务语义底座，关联质量由第 6 章的上下文召回率等指标间接衡量。

### 1.5.2 图谱驱动的任务上下文生成方法

临时把检索结果拼入提示，只能完成任务眼前的信息汇集，相关性判断与 Token 花费仍未受到同一套机制约束。本文的任务上下文生成方法（第 3 章）不把“检索代码”作为终点，而是**为 Agent 生成最小充分上下文**；在给定 Token 预算内，尽量保留与任务有关的信息。

生成过程先从任务描述确定锚点。系统结合置信度衰减权重选定入口，再按边权重执行受节点数预算约束的加权双向 BFS，得到任务级子图。子图确定后，依据节点到锚点的距离抽取不同层次的骨架，删除与任务无关的细节；序列化阶段提供多档压缩输出，预算超限时切换到更低的信息粒度。

整个过程建立在持续维护的项目知识模型之上，生成的上下文不再只是一次任务的临时结果。锚点选择、子图裁剪、骨架抽取和序列化都可配置；第 6 章在同一组代码检索任务和项目场景问题上度量定位质量、上下文 Token、回答正确性和模型总 Token，并通过 KG、映射和生成管线消融分析增量作用。

### 1.5.3 Spec 增量知识演化机制

项目知识的价值要在演化中保留下来。已有仓库图谱多以代码实体或仓库制品为中心，增量维护通常服务图结构本身。本文提出的 Spec 增量知识演化机制（第 3 章）把需求 Spec/Change 设为演化触发单元，把 Capability 作为需求语义和代码结构之间的稳定中间层；每次需求实施后同步更新 Capability 与代码的关联，使知识积累跟随开发过程发生。它不是一般意义上只更新图谱节点的增量操作。

该机制分别面向新项目和存量项目。新项目以“源码扫描 + 需求 Spec”形成初始知识模型，完成冷启动；存量项目新增需求时，先将需求规格化为 Spec，再连接既有 Capability 节点，只更新受影响的代码关系，无需全量重建图谱。经过多轮演化，项目知识沿业务能力主线沉淀，后续任务即可调用。

这里的积累是工程化过程，不涉及训练数据或模型更新。与代码实体中心的仓库图谱不同，本文以 Spec 为演化单元，维护项目知识的时效性。本文实现并说明该增量维护机制，但不以单一项目中的短序列实验宣称其长期有效性。

### 1.5.4 wpw 系统实现与基于大模型的美食推荐系统的方法验证

wpw（Web Project Workflow）是上述方法的实现载体（第 4 章“wpw 系统设计与实现”）。系统分为 AI 层、CLI 层和文件系统层：前者提供 Skill 命令，CLI 处理状态和依赖，文件系统保存图谱及阶段制品；在此基础上实现工作流、图谱构建、上下文生成和增量维护四个模块。多语言源码解析、JSONL 文件和本地向量索引属于支撑技术，使系统不依赖数据库即可在普通开发环境运行。

第 6 章以第 5 章实现的美食推荐系统为实验载体，设置 T1—T3 开发任务，并新增检索定位和项目场景问答题集。实验以 OpenSpec-based SDD 为任务级开发基线，以冻结的非图检索为定位与问答基线，以 wpw 为 KG 驱动方法；信息约束和版本锁定用于保持比较公平。任务完成成本、检索定位质量、项目问答正确性和上下文供给成本对应 1.4 节的研究目标，也用于界定方法的适用条件。

四个创新点中，前三个属于方法设计，wpw 是创新点 4 所述的实现载体。第 3 章的方法总体框架和流程约束架构负责组织三项机制；noisy-OR 聚合公式、双向 BFS、JSONL 与向量存储、多语言源码解析器等内容属于支撑实现，放在对应章节说明。
