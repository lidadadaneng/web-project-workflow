# 第 5 章 实验与评估

本章通过对比实验与消融实验验证本文上下文工程方法的有效性。需要预先明确本章的验证对象与定位：本文的三个创新点（流程约束架构、能力-代码双层知识组织、图谱驱动的上下文压缩）共同服务于"面向 AI 编程智能体的上下文工程"这一主线，wpw 是该方法的实现载体。因此，本章实验验证的不是"wpw 作为工具优于其他工具"，而是：**在不同 AI 辅助开发方式的受控对比中，上下文工程方法（受控流程 + 结构化知识供给 + 预算控制）对开发成本、质量、上下文效率与流程可控性的影响，以及三项机制各自的贡献**。

本章组织如下：5.1 节给出实验设计（目标、测试任务、对比方案、评价指标、消融方案）；5.2 节描述四方案的实验过程；5.3 节给出结果与分析框架（数据以实测回填）；5.4 节从方法有效性、与现有工具比较、局限性三方面讨论。5.3 节在实验执行前给出分析框架，各项结论以实测数据回填与修正为准；若实测与预期不符，将如实报告并归因讨论。

## 5.1 实验设计

### 5.1.1 实验目标

本实验的目标是：在受控条件下对比四种 AI 辅助开发方式在开发成本、开发质量、上下文效率与流程可控性四个维度的表现，并以消融实验分离流程约束、知识组织与上下文生成三项机制的各自贡献，进而回答本文的核心研究问题：**上下文工程方法是否能够在给定资源约束下，提高 AI 编程智能体任务执行的上下文有效性、开发质量与过程可控性**。

将核心研究问题分解为三个可验证的子问题，与本文三项机制及实验的对应关系如表 5-1 所示。主实验观察完整方法的综合表现，机制层面的贡献由消融实验分离验证。

表 5-1 研究问题与实验验证关系

| 研究问题 | 对应机制 | 验证实验 |
|---|---|---|
| RQ1：AI 编程智能体如何获得稳定、可检索的项目级知识与业务-代码关联？ | 能力-代码双层知识组织 | 消融 A + 主实验 |
| RQ2：如何在 Token 预算约束下控制代码上下文膨胀并保持召回？ | 图谱驱动的上下文生成（压缩） | 消融 B + 组件级基线② |
| RQ3：如何提升智能体开发过程的可靠性与可控性？ | 流程约束架构 | 消融 C + 主实验 |
| 综合：三项机制组合的整体效果如何？ | 完整方法（wpw 载体） | 主实验（四方案对比） |

关于实验的外部效度，需明确本实验的性质边界：**本实验属于受控工程实验，而非大规模生态统计实验**，其目标在于验证方法机制的有效性，而非证明方法在所有软件项目中的普适性能。为部分缓解单一项目的外部效度问题，实验按"一个业务载体 + 多任务集"组织（见 5.1.2 节）。

### 5.1.2 测试任务设计

**（1）任务载体定位**

测试任务载体为**面向 AI 辅助开发评估的典型 Web 业务系统**，以美食推荐业务为载体。选择该业务的原因是：功能模块典型（用户认证、内容浏览、个性化推荐、交易、收藏评论覆盖 Web 系统常见需求类型）、业务语义清晰（便于定义需求边界与评估需求符合度）、技术栈主流（vue+springboot 为国内主流全栈组合，且与第 3 章图谱解析器支持范围对齐）。

需要强调：本实验的研究变量是 **AI 辅助开发过程**（流程约束、知识供给、上下文管理），而非推荐算法效果或业务系统本身的先进性。因此，系统设计以"提供典型业务复杂度"为原则，刻意排除与研究变量无关的技术复杂度（推荐算法精度、LLM 推荐效果、微服务治理能力等均不进入评估范围）。

**（2）功能模块设计**

系统由四大业务模块构成，作为四方案共同实现的需求边界：

- **管理员模块**（B 端管理平台）：系统首页、个人中心、用户管理、美食分类管理、美食信息管理、系统管理、订单管理。
- **用户模块**（C 端）：首页（推荐与资讯展示）、美食信息浏览、购物车、美食资讯、个人中心（收藏、充值、客服、订单查询）。
- **美食信息模块**：名称、分类、图片、口味、点击次数、价格六维属性。
- **订单信息模块**：订单编号、商品信息、价格体系、支付类型、订单状态、配送信息。

**（3）技术架构设计**

系统采用前后端分离架构。前端包括商家管理平台（Vue3 + Vite + Element Plus + Pinia）与用户端（Uni-app + uView UI 微信小程序）；后端基于 Spring Boot 分层实现用户、菜品、订单等业务模块，并提供**个性化业务逻辑模块（以用户偏好规则计算为核心，用于模拟真实业务场景中的复杂业务逻辑，其算法效果非研究变量）**；数据层采用 MySQL + Redis + Elasticsearch 的典型组合，服务间异步通信采用 RabbitMQ。实验按可横向对比的规模裁剪：微服务治理与监控组件按需简化，LLM 集成等非研究变量不纳入实验范围。

**（4）任务集设计**

需求集合划分为三组任务集，覆盖不同开发场景：

- **任务集 T1（基础搭建）**：用户认证、菜品信息管理--绿地搭建场景；
- **任务集 T2（业务核心）**：个性化业务接口、购物车与订单流程--存量迭代场景（在 T1 基础上扩展）；
- **任务集 T3（迭代增强）**：收藏、评论、资讯模块--存量迭代场景。

其中 T2/T3 重点用于验证 AI 编程智能体在已有代码上下文理解与增量修改场景下的能力--这正是第 3 章知识组织与上下文生成方法的主要目标场景。四方案按相同顺序执行三组任务集；消融实验在相同任务集上重复执行。

### 5.1.3 对比方案设计

实验设置四个对比方案，如表 5-2 所示。

表 5-2 对比方案设计

| 方案 | 名称 | 说明 |
|---|---|---|
| A | AI 对话式 vibe coding | 开发者直接与 AI 对话写代码，无流程约束、无规范、无阶段划分，AI 自由规划路径 |
| B | OpenSpec 驱动实现 | 采用 OpenSpec（实验版本）以变更规格为中心的 action 工作流驱动实现，规格先行、增量变更管理 |
| C | Superpowers 辅助实现 | 使用 Superpowers（实验版本）技能化工作流（brainstorming/writing-plans/subagent-driven-development/code-reviewer 等）辅助实现，注重执行纪律与子代理协作 |
| D | wpw 工作流实现 | 采用 wpw 六阶段工作流 + 知识图谱上下文 + 三层分离架构完整流程，作为本文方法的实现载体 |

**（1）实验信息约束原则**。为保证方案间比较公平，所有方案均允许访问同等的初始信息，包括：同一份需求描述、技术栈说明与任务执行时点的已有代码仓库。特别说明：wpw 方案所使用的能力规范与知识图谱**并非人工额外提供的先验知识，而是其工作流程在执行过程中从需求文档与源码自动构建产生**；该构建的完整冷启动开销--首次扫描源码、生成能力规范、建立图谱与向量索引--均计入方案 D 的时间与 Token 成本，不使用任何预构建知识库。其余方案同样可以通过手动阅读仓库获取等价信息，其检索成本计入各自方案。

**（2）主实验与消融实验的分工**。由于本文的研究目标并非比较不同工具的整体能力，而是分析上下文工程各机制的组合效果，方案 D 相对 B/C 包含更多机制（流程 + 知识组织 + 压缩）属于方法设计本身的特点；因此主实验用于观察完整方法的综合表现，各机制的单独贡献通过消融实验（5.1.5 节）进一步分离，不以主实验的组间差异直接归因于单一机制。

**（3）Spec Kit 参照说明**。Spec Kit 与 wpw 均涉及项目级流程治理，两者存在一定交叉。考虑到 Spec Kit 引入 Constitution、Workflow Engine 等完整治理体系后，其作为实验组引入的变量不仅包含流程因素，还包含生态配置成本等混杂变量，难以与本研究的目标变量分离；因此本文未将 Spec Kit 作为主要实验对象，而在 5.4.2 节对其与本文方法进行机制层面的对比讨论。此为实验变量控制的考虑，不构成对工具能力的评价。

**（4）控制变量与版本锁定**。同一需求规格、同一开发者、同一大模型、同一技术栈、同等时间预算；各工具以实验采用版本为准（版本号、发布日期与代码提交标识记录于 4.4.1 节实验环境表），避免因工具快速迭代导致比较基准漂移。

### 5.1.4 评价指标

评估指标体系分为五组，关键指标给出可操作定义，如表 5-3 所示。

表 5-3 评估指标体系

| 指标组 | 指标与定义 | 度量方式 |
|---|---|---|
| 成本 | Token 消耗量（含上下文规模 Prompt Token，含方案 D 的图谱构建冷启动成本）、API 费用、开发工时、迭代/返工次数 | 自动化统计 |
| 开发质量 | 代码缺陷率（单位有效代码缺陷数）、需求覆盖度 = 已实现需求点 / 总需求点、需求符合度（实现与需求一致性，双人交叉评审）、代码 review 通过率 | 缺陷统计 + 人工评审 |
| AI 辅助程度 | AI 贡献代码比例 = 经人工采纳进入最终版本的 AI 生成代码行数 / 最终有效代码总行数；人工修改率 = 人工修改代码行数 / AI 生成代码行数（修改以 git diff 行级变化统计）；自动化阶段覆盖率 = AI 参与的阶段数 / 需求-设计-计划-测试-编码总阶段数；人工介入次数（决策/纠偏/返工的人工操作计数） | 自动化统计 + 过程记录 |
| 流程可控性 | 流程完整度 = 实际完成阶段数 / 标准阶段总数；状态可审计率 = 具有时间戳、责任主体与输入输出记录的阶段状态数 / 总阶段状态数；可追溯性（变更可回溯程度）、文档完整度 | 人工评审 + 量表 |
| 上下文效率 | 上下文召回率 Recall = \|R∩C\| / \|R\|；Token 缩减率 Compression = 1 − Token_context / Token_full（Token_full 为全量注入基准）；压缩后信息保真度；下游任务表现（以给定上下文完成任务的成功率） | 图谱工具统计 + 人工标注 + 实测 |

其中上下文召回率的标注协议为：由两名具有开发经验的标注者依据需求描述与最终实现，独立标注任务真实涉及的代码元素集合 R（文件与函数双粒度），与实际注入上下文的集合 C 求交计算召回率；以 Cohen's kappa 系数衡量标注一致性，分歧经仲裁后形成最终标注。

为分离三项机制的各自贡献（对应表 5-1 中 RQ1-RQ3），在方案 D 基础上设置消融变体，如表 5-4 所示。

表 5-4 消融实验设计

| 消融组 | 变体设置 | 度量指标 |
|---|---|---|

## 5.2 实验过程

### 5.2.1 方案 A：AI 对话式 vibe coding

开发者直接与 AI 对话生成前端组件与后端接口，允许使用同一模型提供的代码解释、调试建议与重构建议等常规辅助能力，但不引入显式规格管理、项目知识索引与任务阶段约束--即以"无流程约束的自然语言交互开发"为对照组基线。全程记录 Token、工时、返工与缺陷。观察要点：对话过程中的状态一致性、需求遗漏情况、上下文逐轮膨胀趋势。

### 5.2.2 方案 B：OpenSpec 驱动实现

按其实验版本工作流撰写变更规格（proposal/spec/design/tasks），经 apply/sync/archive 推进实现。观察要点：规格制品与代码结构、业务知识的关联方式，变更规格到实现的衔接成本，任务级上下文以文档与手动检索为主的实际开销。

### 5.2.3 方案 C：Superpowers 辅助实现

按其实验版本技能化工作流推进：brainstorming 澄清需求、writing-plans 编写计划、subagent-driven-development 执行、code-reviewer 审查。观察要点：技能流程间的衔接与状态管理方式、子代理上下文隔离的实际效果与配置成本、任务级上下文的构造成本。

### 5.2.4 方案 D：wpw 工作流实现

完整走 BRD->PRD->（Explore 可选）->Design->Plan->Test->Apply 六阶段；图谱构建与上下文生成嵌入 apply 等环节，图谱构建成本计入该方案总成本。观察要点：阶段完整性与状态可审计性、图谱上下文的实际密度与命中率、能力归档沉淀的运转情况。

## 5.3 实验结果与分析

> **注**：本节为实验执行前的分析框架，各项结论以实测数据回填与修正为准。各维度分析关注三点：是否存在显著差异、差异的来源（上下文构造方式/流程约束/知识供给）、是否支持表 5-1 对应的研究假设；本节不预设方向性结论。

### 5.3.1 开发成本

- 比较四方案在三组任务集上的 Token 消耗（区分上下文构造与生成消耗）与 API 成本分布，重点分析上下文构造方式（对话式逐轮累积 / 手动检索 / 图谱按需注入）对成本结构的影响。
- 社区先验参照（非学术证据，仅作动机）：2026 年 6 月有用户公开对比 OpenSpec 与纯 Claude Code 的实现过程（前者多发现 3 个需求缺口，但代码量约 +50%、工时约 2 倍、API 成本约 3 倍），提示规格驱动流程可能引入额外过程成本，其价值需实验度量而非假设（单用户案例，不作为结论依据）。
- 开发工时与返工次数的组间差异及归因（数据回填）。

### 5.3.2 开发质量

- 比较四方案的缺陷率与需求覆盖度，分析流程约束机制（测试方案前置、依赖检查）与上下文质量对开发质量的各自影响路径（结合消融 C 归因）。
- 需求符合度双人评审结果与分歧仲裁记录（数据回填）。
- 代码 review 通过率对比与归因（数据回填）。

### 5.3.3 上下文效率

- 以消融 B 为主线，报告三档压缩在 Token 缩减率、上下文召回率、信息保真度与下游任务成功率上的权衡曲线，识别给定任务规模下的较优工作点。
- 对比各方案的上下文构造方式在等价任务下的上下文规模与召回率（数据回填）。
- 结合消融 A，分析知识组织（图谱供给 vs 手动检索）对上下文召回率与 Token 成本的影响。

### 5.3.4 流程可控性

- 流程完整度与状态可审计性的组间比较：wpw 以三段式契约 + 状态文件显式留痕管理项目级阶段状态；OpenSpec 以 artifact graph 跟踪变更制品状态；Superpowers 以技能工作流约束执行过程；vibe coding 无流程约束（以实测评分）。
- 变更可追溯性与文档完整度对比（数据回填）。

### 5.3.5 消融实验分析（数据回填）

- 知识组织消融（A）：以实测量化图谱供给相对手动检索在 Token 消耗、需求覆盖度、人工介入次数上的差异。
- 上下文生成消融（B）：三档压缩的权衡曲线与较优工作点；若各档差异不显著则如实归因讨论。
- 流程控制消融（C）：完整工作流相对单命令模式在流程完整度、返工次数、缺陷率上的差异。
- 组件级基线：noisy-OR 相对三种聚合基线、双向 BFS 相对三种选择策略基线的量化对比；若增益不显著则如实报告并分析原因（如任务规模、图谱密度等边界条件）。

## 5.4 讨论

### 5.4.1 方法有效性分析

结合实验数据，从三方面分析上下文工程方法的有效性及其成立条件：其一，技术栈适配性--前端 Vue3/Pinia/Uni-app 解析与后端 Java/Spring Boot 解析（类型/方法/常量节点、注解与 REST 端点元信息、包路径 import 边、业务包模块推断）使测试系统的前后端源码一致进入图谱，business_map 多源融合在前后端同等生效，多技术栈经多图谱机制隔离（按子目录构建命名图谱）；其二，三机制的贡献分解--依据消融 A/B/C 的实测结果，讨论知识组织、上下文生成与流程控制各自的作用路径与边界条件；其三，适用边界--依据分组任务集（绿地/存量迭代）的分组结果，讨论方法在不同开发场景下的表现差异。若实测与预期不符，如实归因讨论。

### 5.4.2 与现有工具比较

本文方法与现有工具的差异属于**设计取舍**而非能力高下，具体体现在三方面：

其一，相对 Spec Kit 的项目级规范治理体系（Constitution + 质量门禁 + Workflow Engine/扩展生态），wpw 选择更轻的起点：零配置开箱即用（项目类型自动嗅探、模块自动推断、纯 Node.js 单运行时、图谱本地构建、CLI 层无需 API Key），以治理强度（无全局规范宪法与一致性检查，见 5.4.3）换取更低的采用与维护成本。

其二，相对 OpenSpec 的变更制品管理（artifact graph + action 工作流），wpw 将变更之外的项目级知识纳入统一基础设施：能力规范随归档持续沉淀、代码结构以双层图谱建模、业务-代码关联多源融合；命令级解耦支持按需组合，图谱增量更新控制功能增量的边际成本。

其三，相对现有工具的上下文机制（Superpowers 的子代理上下文隔离与工作区隔离等，主要作用于 prompt/工作流/扩展层），wpw 的差异化在代码侧上下文的结构化供给：知识沉淀为图谱后，经锚点检索 -> 子图裁剪 -> 骨架抽取 -> 压缩序列化按需生成任务上下文。需区分"规避"与"解决"：wpw 未从技术上解决规则膨胀导致的失真（规则侧靠分阶段轻量加载规避），技术上解决的是同构的代码上下文膨胀问题。

表 5-5 基于各工具公开机制描述，给出其在本文关注维度上的功能归类对比（**仅为本文基于官方机制的结构性归类，非官方能力评级，也不代表工具当前完整能力边界；"非设计目标"不代表工具能力不足，仅指该维度非其设计重心**）：

表 5-5 各工具功能关注维度对比

| 能力维度 | Spec Kit | OpenSpec | Superpowers | wpw |
|---|---|---|---|---|
| 项目级规范治理 | ● | ◐ | ◐ | ◐（规则轻量） |
| 变更级规格管理 | ● | ●（重点） | ◐ | ● |
| 工作流编排 | ●（重点） | ● | ● | ● |
| Agent 执行纪律（Skill/子代理） | ◐（扩展） | ◐（生态） | ●（重点） | ◐（可选） |
| 代码知识图谱 | ○ | ○ | ○ | ◉（本文重点） |
| 业务-代码映射 | ○ | ○ | ○ | ◉（本文重点） |

### 5.4.3 局限性分析

- **实验规模与性质边界**：本实验为受控工程实验，以单一业务载体的三组任务集组织，属个案层面的机制验证，结论向其他项目类型、其他规模与团队场景的外推需进一步研究；人工评审维度存在主观性，以双人交叉评审与标注仲裁缓解。
- **后端语言覆盖**：Java/Spring Boot 解析器已实现但落地验证规模有限，首版不做依赖注入边与 JPA 关联边；Go/Python 等后端语言尚未覆盖。
- **冷启动**：能力规范缺失时退化为纯结构检索。
- **规则治理**：缺少全局规则治理能力，规则随项目与团队规模膨胀时面临同类失真风险，分阶段轻量加载缓解但未根治。

## 5.5 本章小结

本章给出了上下文工程方法的实验验证设计：以美食推荐业务为载体的典型 Web 系统、三组任务集上组织四方案（vibe coding / OpenSpec / Superpowers / wpw）受控对比，以成本、开发质量、AI 辅助程度、流程可控性与上下文效率五组可操作定义的指标度量；消融实验分离知识组织、上下文生成与流程控制三项机制的贡献，组件级基线支撑第 3 章的方法选择。实验明确定位为受控工程实验，验证机制有效性而非普适性能；结果分析以实测数据回填，并从方法有效性、与现有工具的机制对比与局限性三方面讨论。
