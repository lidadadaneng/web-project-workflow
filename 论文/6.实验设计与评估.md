# 第 6 章 实验设计与评估

本章检验第三章提出的项目知识组织与任务上下文生成方法。实验不把不同 AI 工具作为竞赛对象，而是在规格驱动开发（Specification-Driven Development，SDD）作为共同基础的条件下，比较 OpenSpec 基线与加入知识图谱（Knowledge Graph，KG）驱动上下文工程的 wpw 方法，考察 KG 对上下文构造和下游软件任务的增量作用。

## 6.1 实验目标、研究问题与假设

### 6.1.1 实验目标

已有研究表明，规格 grounding 和 specification-first workflow 能够为 AI 软件开发提供更明确的任务约束[7][60][61][62]。另一方面，代码库中的代码实体、接口、数据表及其依赖关系适合用图结构组织[38][39][40]；AST 派生图、Repository KG 和 KG-Agent 研究分别从代码库可靠性、仓库问答和 Agent 推理记忆角度说明了关系化知识的价值[63][64][65]。因此，本章将 SDD 作为共同开发基础，把“是否使用 KG 驱动的项目知识组织和上下文生成”作为主要实验变量。

实验目标包括：

1. 比较 OpenSpec 与 wpw 在相同 SDD 任务下的上下文构造效率和任务实现效果；
2. 分离知识图谱、业务—代码映射和图谱驱动上下文生成各自的作用；
3. 观察项目知识在多轮需求演化中的复用、成本变化和召回稳定性。

本章不评价美食推荐算法的准确率，不比较基础模型能力，也不据此建立 AI 工具排行榜。实验结论限定在当前系统、任务集、模型版本和受控开发条件内。

### 6.1.2 研究问题

- **RQ1：** 在相同 SDD 流程下，KG 驱动的项目知识组织是否能够提高任务相关代码的召回质量？
- **RQ2：** KG 驱动的任务上下文生成是否能够在保持必要信息的同时减少上下文构造时间和 Token 消耗？
- **RQ3：** 在连续需求演化中，Spec 增量知识机制是否能够降低后续任务的边际开发成本并保持稳定的上下文召回？

### 6.1.3 研究假设

- **H1（效率假设）：** 与 OpenSpec 基线相比，wpw 的上下文构造时间和上下文 Token 消耗更低。
- **H2（相关性假设）：** 在相同任务和预算条件下，wpw 的任务相关代码召回率更高；Context Precision 作为补充指标报告。
- **H3（任务效果假设）：** wpw 能够缩短任务完成时间、提高验收通过率或减少返工次数。
- **H4（演化假设）：** 随着 T4 知识增量更新，wpw 的后续轮次成本增长低于初始冷启动成本，且 Context Recall 不出现持续下降。

以上假设是待检验命题。若数据不支持某一假设，仍如实报告非显著结果和失败案例。

## 6.2 实验对象与任务集

### 6.2.1 实验对象

实验对象是第五章的美食推荐系统软件开发过程。实验单元定义为“某一种方法完成某一个可独立验收任务的一次运行”，而不是将整个系统作为一个不可重复的样本。

任务不等同于单个代码模块。一个任务可以同时涉及多个模块、接口、数据表和页面。例如，购物车与订单流程同时涉及购物车、订单、地址和结算页面。

### 6.2.2 任务集与开发场景

| 任务集 | 场景 | 任务内容 | 用途 |
|---|---|---|---|
| T1 | 基础搭建 | 用户认证、美食分类和美食信息管理 | 主实验与消融 |
| T2 | 业务核心 | 个性化推荐、购物车和订单流程 | 主实验与消融 |
| T3 | 迭代增强 | 收藏、评论、美食资讯和个人中心 | 扩展验证 |
| T4 | 长期演化 | 会员积分、优惠券、会员等级和配送规则 | 连续演化 |

核心任务进一步拆分为：

- T1-1 用户注册与登录；
- T1-2 美食分类和美食信息管理；
- T2-1 个性化推荐接口；
- T2-2 购物车与订单流程。

T3 的扩展功能记录完成情况、耗时和返工次数，不对每项功能设置复杂的独立统计模型。T4 依次执行四轮需求，每轮从上一轮的代码、规格和知识状态继续。

### 6.2.3 任务规模与验收标准

每个任务在执行前记录需求点数量、涉及文件数、函数或接口数、业务模块数、数据表数、前端页面数和测试用例数。每个核心任务配备固定验收清单，例如：

- 注册成功后能够登录，失败时返回正确提示；
- 美食分类和美食信息能够完成新增、修改、删除和查询；
- 推荐接口能够根据既定规则返回结果；
- 购物车能够增加、修改和删除商品；
- 订单能够提交，并完成规定的状态流转。

任务规模和验收清单在实验开始前冻结，不因某一方法的实现结果而修改。

## 6.3 对比方法与实验控制

### 6.3.1 OpenSpec 基线

OpenSpec 作为代表性 SDD 基线，使用 proposal、spec、design 和 tasks 等规格制品组织变更，并按既定阶段推进实现。为保证比较公平，实验为两种方法规定等价的需求澄清、设计、计划、测试和实施阶段；OpenSpec 的制品映射到这些阶段后，基线可以读取规格制品和按统一规则选取的相关文件，但不使用本文的项目 KG、业务—代码映射和图谱驱动子图生成。

如果实验采用对 OpenSpec 流程的复现而不是官方程序，应在实验环境表中标明“OpenSpec-based SDD baseline”，同时记录复现脚本版本和提交标识，避免将自定义复现误称为官方工具。

### 6.3.2 wpw 方法

wpw 与 OpenSpec 共享需求输入、任务划分、阶段目标和验收标准，并在等价的 SDD 制品层基础上增加：

- Capability-Code 双层知识模型；
- 业务能力与代码元素的显式映射；
- 图谱驱动的锚点选择和子图裁剪；
- 骨架抽取、序列化和 Token 预算控制；
- Spec 驱动的知识增量更新。

因此，主实验的比较对象不是“有流程”与“无流程”，而是“传统 SDD 上下文组织”与“KG 驱动上下文组织”。若具体制品名称或阶段实现无法完全对齐，结果解释为两种 SDD 方法的综合差异，不单独归因于 KG。

### 6.3.3 其他方法的处理

普通对话式开发缺少稳定的 SDD 制品和阶段流程，不作为主要实证基线。Superpowers 主要作为技能化 Agent 工作流的相关方法参照，在第一章和第二章说明其定位，不纳入本章独立统计。本文不据此推断 OpenSpec、Superpowers 或普通对话式开发的绝对优劣。

### 6.3.4 控制变量与重复规则

固定以下条件：

- 相同需求说明、任务划分和验收清单；
- 相同初始代码快照、技术栈和基础模型及版本；
- 相同开发者、时间预算和工具调用权限；
- 相同测试环境和代码提交规则；
- OpenSpec 与 wpw 使用独立分支，不共享对方生成的代码或知识制品。

所有实验统一遵循“当前对话是唯一 Agent，Token 取当前对话”的最高执行原则。每次运行由当前 Codex 对话直接完成规格、实现、测试、验收、数据清理和事件记录，不得启动、嵌套或委派第二个 Agent；模型 Token 只能取该当前对话中执行本实验任务的 `task_started`—`task_complete` 回合，不得混入子 Agent、其他对话或后续分类与文档维护回合的用量。`sdd-eval` 只承担工作区与记录管理、验收、计算和落盘，不作为第二个执行 Agent。

任务执行顺序随机化，工具版本、模型参数、随机种子和提交标识在附录中记录。wpw 首次源码扫描、能力规范生成、图谱构建和索引建立的冷启动时间与 Token 计入成本。

受当前实验资源约束，每个核心任务和方法运行 1 次，共形成 4 个核心任务 × 2 种方法的 8 次主实验运行。每次运行保存需求输入、规格制品、上下文内容、模型日志、代码提交或候选版本哈希、测试结果和人工修改记录。单次运行结果用于任务级描述与后续跨任务配对，不据此估计同一任务内的运行波动；样本不足时仅报告描述性和探索性证据。

### 6.3.5 sdd-eval 的系统结构与工作原理

为统一实验执行与数据采集，本文实现了独立的 **SDD 开发实验执行与评估工具** `sdd-eval`（Node.js/TypeScript 命令行工具）。系统采用“配置—任务—执行—采集—评价—报告”的分层结构：

1. **配置层**：读取 `eval.config.json/yaml`，冻结项目源目录或快照、当前对话执行标识、超时时间、重复次数和 Token 统计方式；正式实验不配置二次 Agent 启动命令；
2. **任务层**：从内置任务集或 `tasks.yaml` 读取任务说明、场景、Gold 代码元素和验收检查项；
3. **工作区与调度层**：从同一源快照创建隔离工作区，过滤 `.git`、`node_modules`、`results` 和 `evaluator-private`，执行可选初始化命令，并为当前对话登记指定方法和运行编号，不再调度其他 Agent；
4. **方法适配层**：`OpenSpecAdapter` 对仓库进行确定性上下文扫描；`WpwAdapter` 优先读取 wpw 输出的 `.wpw-context.json` 或 `wpw-context.json`，先记录 `anchors`、`subgraph` 和 `compressedText` 作为知识导航层，再沿子图文件边界展开任务说明、导航摘要和源码内容，形成综合上下文观测；缺少该文件时使用受限的源码扫描作为回退。综合上下文观测作为当前对话这一唯一 Agent 的实际输入边界记录；
5. **验收与指标层**：执行任务中声明的命令或评测侧私有脚本，依据 Gold 元素和统一分词器计算上下文 Token、压缩率、Recall、Precision、任务时间、验收通过率和返工代理值；
6. **结果层**：将每次运行的 `RunRecord`、标准输出、错误输出、事件日志和工作区索引保存到 `results/`，并由 `report` 命令按方法、任务或场景筛选汇总。

在实现上，`config.ts` 和 `tasks.ts` 负责配置与任务加载，`workspace.ts` 负责工作区复制和外部命令执行，`adapters.ts` 负责方法接入，`runner.ts` 编排单次运行和验收，`metrics.ts` 负责指标计算与汇总，`index.ts` 提供命令行入口。模块之间通过任务对象、上下文观测和 `RunRecord` 传递数据，保持评测器与被测方法解耦。

一次运行的基本流程为：

```text
冻结任务与版本 → 创建隔离工作区 → 接入 OpenSpec 或 wpw
        → 当前对话这一唯一 Agent 执行并记录事件 → 执行统一测试与验收
        → 汇总指标 → 生成可复现的结果文件
```

其核心原理是“同一输入、同一约束、仅替换方法适配器”。`sdd-eval` 为每次运行生成唯一 `run_id`，创建独立工作区并记录运行状态，但不再启动或嵌套另一个 Agent；任务总时间由评测器从当前对话开始执行计至其完成统一验收，而不是由被测方法自行报告。这样可以在不改变 wpw 或 OpenSpec 内部开发逻辑的情况下，使用同一工作区隔离、超时、验收和指标计算规则进行比较。

为允许开发过程中的自主探索，执行器向 Agent 提供运行专属的上下文文件和事件文件路径（环境变量 `SDD_EVAL_CONTEXT_FILE`、`SDD_EVAL_EVENTS_FILE`、`SDD_EVAL_WORKSPACE`）。OpenSpec 和 wpw 均可在开发过程中自主追加搜索、图谱查询和源码读取，并按 JSONL 事件记录 `search`、`graph_query`、`source_read`、`context_append` 和 `model_call`。执行器只汇总 Agent 实际声明的探索轨迹和模型输入/输出 Token，不根据私有 Gold 推断遗漏文件、自动补齐上下文，也不以 Gold 命中作为停止条件。初始导航指标与全过程累计上下文指标分开保存；Gold 仅在运行结束后用于计算 Recall 和 Precision。由 Codex 当前对话直接执行的实验，其模型 Token 统一取执行该任务的当次对话回合：以匹配的 `task_started` 为起点，以 `task_complete` 为终点，读取终点前最后一条 `event_msg/token_count.total_token_usage`。后续分类、文档维护或讨论回合不计入先前任务；缓存输入和推理输出仅作诊断字段，不重复加入总 Token。

`sdd-eval` 不属于 OpenSpec 或 wpw 的内部模块，不实现被测的上下文生成方法，也不作为新的开发方法参与比较。wpw 仅输出必要的结构化上下文文件和过程日志；跨方法的时间、Token、Recall、Precision 和验收结果均由 `sdd-eval` 统一计算。评测侧的 Gold 标注和私有验收脚本不复制到 Agent 工作区。工具支持 `init`、`tasks`、`run`、`report` 和 `clean` 命令，其中 `--mock` 仅用于检查调度和数据链路，不作为正式实验结果。该工具作为支撑本章实验的本地命令行工程，不构成本文的独立方法创新。

## 6.4 评价指标与数据采集

### 6.4.1 上下文构造效率

记录：

- 上下文构造时间；
- 综合上下文 Token 数（任务说明、导航摘要和实际注入的源码/规格内容）；
- KG 导航摘要 Token 数（仅作过程诊断，不作为最终上下文效果判定）；
- 模型输入和输出的总 Token 数；
- wpw 冷启动时间和冷启动 Token；
- 上下文 Token 缩减率。

上下文 Token 缩减率定义为：

$$\mathrm{Compression} = 1 - \frac{T_c}{T_f} \tag{6-1}$$

其中 $T_c$ 为全过程累计综合上下文 Token 数，$T_f$ 为按统一规则构造的全量上下文基准。综合上下文包括初始任务/导航内容以及 Agent 在开发过程中通过搜索、图谱查询和源码读取自主追加的内容；OpenSpec 和 wpw 使用同一任务、同一代码快照和同一分词器计算 Token。KG 导航摘要单独记为初始过程变量，不与累计 $T_c$ 混用。

### 6.4.2 上下文相关性

对每个任务预先标注真实涉及的代码元素集合 $R$，并记录综合上下文实际提供的元素集合 $C_{ctx}$。Recall 和 Precision 只在 $C_{ctx}$ 上计算；KG 导航得到的锚点集合 $C_{nav}$ 仅报告为导航诊断指标，不作为最终结果判断依据。正式比较先检查 Recall 和 Precision 是否达到预设下限，再比较满足质量约束的综合上下文 Token。

$$\mathrm{Recall}_{ctx} = \frac{|R \cap C_{ctx}|}{|R|} \tag{6-2}$$

Context Precision：

$$\mathrm{Precision}_{ctx} = \frac{|R \cap C_{ctx}|}{|C_{ctx}|} \tag{6-3}$$

Recall 作为主指标，Precision 作为补充指标；$\mathrm{Recall}_{nav}$ 和 $\mathrm{Precision}_{nav}$ 只用于诊断 KG 是否成功定位候选范围。标注可在文件和函数两个粒度进行；若有两名标注者，报告 Cohen's kappa，否则报告标注规则、抽样复核过程和争议处理方式。

### 6.4.3 Agent 任务效果

记录：

- 实际任务完成时间；
- 需求验收通过率或需求覆盖度；
- 返工次数；
- 任务失败或中断情况。

验收由固定清单判断，返工定义为已提交实现因测试失败、验收不通过或需求遗漏而产生的再次修改。若没有独立缺陷登记，不额外构造单位代码缺陷率。

未配置可执行命令或脚本的验收项标记为“未执行”并判为不合格，不再自动计为通过；正式任务必须提供可运行的验收命令或评测侧私有脚本。

在当前 `sdd-eval` 实现中，`reworkCount` 记录未通过的验收检查项数，作为返工的可观测代理指标；正式实验若补充 Git 提交或事件级修改记录，则以实际再次修改次数替换该代理值，并在结果表中注明统计口径。

### 6.4.4 长期演化指标

T4 不新增一套指标，而是观察前述指标随轮次的变化：

- 单轮和累计探索/上下文构造时间；
- 单轮和累计综合上下文 Token，以及模型输入/输出 Token；
- 每轮 Context Recall；
- 每轮返工次数；
- 新增知识节点、更新关联和复用知识节点数量。

### 6.4.5 sdd-eval 的数据采集与结果文件

正式运行前，使用 `sdd-eval init` 写入评估配置并创建结果目录，使用 `sdd-eval tasks` 检查冻结任务集；随后通过 `sdd-eval run --task <任务编号> --method <openspec|wpw> --repetitions <次数>` 执行重复实验。每次运行生成唯一运行编号，并在 `results/` 下保存一条 JSON 记录及对应的标准输出、错误输出和事件日志；隔离工作区保存在 `results/workspaces/`。`sdd-eval report` 可按方法、任务或场景筛选记录并输出汇总 JSON；当前命令提供运行级记录和分组均值，汇总时只对实际存在的数值求均值，整组缺失的指标保留为 `null` 而不转换为 0。论文要求的中位数、四分位距、配对检验和统计图表在此基础上由后处理脚本生成。

单次运行记录至少包含任务编号、方法、重复编号、运行状态、初始导航观测、探索事件序列、累计上下文观测、模型输入/输出用量、验收明细、各项指标、日志路径和运行环境元数据。运行状态区分 `passed`、`failed`、`timeout`、`interrupted` 和 `error`；失败或超时记录保留在原始数据中，不通过删除异常运行改善结果。当前实现使用空白分词或长度近似法统一估计上下文 Token，正式报告中记录所选模式及其版本；模型 Token 不使用该估算器，而是读取当次任务对话的精确 `token_count`。由于 `task_complete` 在任务回复结束后写入，允许在下一回合从会话日志回填，但必须保存会话标识、任务起止时间和来源事件，并将其标记为实测值而非估算值。

## 6.5 主实验：OpenSpec 与 wpw 对比

### 6.5.1 实验流程

1. 在 `sdd-eval` 中冻结同一代码快照、任务配置、验收清单、当前对话唯一 Agent 规则、超时和重复次数；
2. 从该快照为每次运行创建独立工作区，并执行必要的环境初始化；
3. 通过 `OpenSpecAdapter` 或 `WpwAdapter` 获取对应方法的任务上下文，并将其提供给当前对话这一唯一 Agent，不启动或委派第二个 Agent；
4. 由当前对话直接完成开发并记录输出、错误、事件和代码工作区，直至任务完成、失败或超时；
5. 在评测侧执行任务声明的验收命令或私有验收脚本，计算验收通过率并保留每项检查结果；
6. 当前任务回复完成后，读取同一对话对应 `task_complete` 前的精确模型 Token，由 `sdd-eval` 写入运行级 JSON 记录，再按任务、方法和轮次汇总成本、上下文相关性和任务效果指标。

### 6.5.2 核心比较

主结果重点报告：

- 任务验收通过率和失败情况；
- 当前对话执行本任务的全过程模型输入/输出 Token 与累计综合上下文 Token；
- 从运行开始到验收完成的总耗时；
- 初始导航 Token、搜索/图谱查询/源码读取次数；
- Context Recall 及补充的 Precision，用于解释差异来源；
- 返工次数。

结果按核心任务和任务集分组展示，并同时报告绝对差值和相对变化率。

### 6.5.3 结果解释边界

若 wpw 表现更好，结论只能表述为：在本系统、指定任务、模型版本和控制条件下，KG 驱动上下文组织相对于 OpenSpec 基线表现出相应差异。结果不能直接推广到所有项目，也不能据此声称 wpw 一定优于 OpenSpec 或 Superpowers。

## 6.6 KG 机制消融实验

消融实验在 wpw 内部进行，目的是定位增量收益来源，而不是重新比较工具。

### 6.6.1 WPW-KG：关闭项目知识图谱

保留 SDD 流程和基本任务执行，关闭 Capability-Code 知识模型与图谱检索，改为直接读取原始文件。该组用于检验项目知识组织是否带来上下文和任务效果的变化。

### 6.6.2 WPW-Map：关闭业务—代码映射

保留代码结构图和基本检索，移除业务能力到代码元素的显式映射。该组用于检验 Capability 作为语义锚点的作用。

### 6.6.3 WPW-Gen：关闭图谱驱动上下文生成

保留项目 KG，但关闭子图裁剪、骨架抽取和预算控制，改为直接拼接较大范围的相关文件。该组用于检验任务级上下文生成管线对 Token 和上下文相关性的影响。

### 6.6.4 消融指标与规模

消融组统一记录上下文构造时间、上下文 Token、Recall、任务完成时间、验收通过率和返工次数。优先完成完整 wpw 与 WPW-KG、WPW-Map、WPW-Gen 的配对比较；不默认开展完整 $2\times2\times2$ 全因子实验，以避免在小样本条件下估计不稳定的高阶交互作用。

- 哪些需求仍然需要人工补充或重新定位。

## 6.8 数据处理与统计分析

### 6.8.1 数据清洗

预先规定运行失败、中断、超时和缺失日志的处理方式，保留原始记录，不以删除异常运行的方式改善结果。所有 Token 使用同一分词器和统计口径，时间统一从任务开始记录到验收完成。暂计正式样本使用估算值时，结果文件同时保存参照样本、估算公式和舍入口径，并在最终分析中分别报告纳入与排除估算值的敏感性结果。

### 6.8.2 描述性统计

按方法、任务和轮次报告样本量、均值、中位数、标准差或四分位距、最小值、最大值及缺失情况。主表优先呈现中位数和四分位距，避免小样本下单一均值掩盖波动。

### 6.8.3 配对比较与效应量

由于同一任务由两种方法分别完成，分析以配对差值为主。样本量较小时采用 Wilcoxon 符号秩检验；多任务总体趋势可采用 Friedman 检验。报告绝对差值、相对变化率、适当的效应量和 95% 置信区间，不以单一 $p$ 值作为结论依据。若数据不足以支持稳定的显著性检验，则仅报告描述性和探索性证据。

### 6.8.4 标注一致性与可复现性

上下文相关性标注在实验前冻结规则。两名标注者独立标注时报告 Cohen's kappa；存在分歧时保留原始标注、讨论记录和最终仲裁结果。分析脚本、数据清洗规则、随机种子、模型配置和工具提交标识一并保存。

## 6.10 本章小结

本章以 SDD 为共同基础，设置 OpenSpec 基线与 wpw+KG 方法的受控对比，进一步通过 KG、业务—代码映射和任务上下文生成消融定位方法增量，并以 T4 多轮需求演化检验知识积累的长期作用。独立的 `sdd-eval` 负责冻结配置、创建隔离工作区、调度重复运行、统一验收和保存运行级记录；评价指标收缩为上下文构造成本、上下文相关性和任务实现效果，统计分析采用小样本下的配对比较和效应量报告。所有结论均限定在当前美食推荐系统、任务集和实验配置范围内。
