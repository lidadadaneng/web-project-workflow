# 第 6 章 实验设计与评估

本章围绕第 3 章提出的项目知识组织与任务上下文生成方法，从“开发结果”和“机制验证”两个层面展开评估。美食推荐系统开发实验只统计完成任务所消耗的模型总 Token，用于判断 wpw 是否降低整体开发成本；项目场景实验再通过 Recall@5、Recall@10、Precision@10、盲评通过率和累计上下文 Token，检验这种总量下降是否能够由更精准、更高效的上下文供给解释。

## 6.1 研究目标与总体设计

### 6.1.1 研究目标

本实验回答四个相互衔接的问题：

- **RQ1：** 在美食推荐系统开发任务中，wpw 是否减少完成任务所需的模型总 Token？
- **RQ2：** 在项目场景中，代码结构图和业务—代码映射是否提高相关文件的 Recall@5、Recall@10 和 Precision@10？
- **RQ3：** 图谱驱动的结构化上下文是否提高项目场景问答通过率，并减少累计上下文 Token？
- **RQ4：** 场景检索与问答结果能否为开发实验中模型总 Token 的下降提供机制解释？

实验由开发成本观测和项目场景机制验证构成。开发实验在 T1—T3 的 8 个配对任务及 T4 的 4 轮连续需求中，只比较 OpenSpec 与 wpw 的模型总 Token。场景检索使用 100 个任务，在非 KG、WPW-Map 和完整 wpw 三个条件下比较 Recall@5、Recall@10 和 Precision@10；场景问答使用 100 个问题，在非 KG、WPW-Map、WPW-Gen 和完整 wpw 四个条件下比较盲评通过率和累计上下文 Token。前者给出成本结果，后者验证上下文定位质量与组织效率，并作为解释成本差异的机制证据。

### 6.1.2 分层评估设计

| 层次 | 题集 | 条件 | 主要指标 | 目的 |
|---|---:|---|---|---|
| 任务级开发 | T1—T3 的 8 个配对任务 | OpenSpec、wpw | 模型总 Token、相对减少率 | 评价真实开发任务的模型总用量 |
| 长期演化补充 | T4 的 4 轮连续需求 | OpenSpec、wpw | 单轮及合计模型总 Token | 观察连续需求中的模型总用量变化 |
| 场景检索定位 | 100 个检索任务 | 非 KG、WPW-Map、完整 wpw | Recall@5、Recall@10、Precision@10 | 验证上下文候选文件的定位精度与覆盖度 |
| 项目场景问答 | 100 个场景问题 | 非 KG、WPW-Map、WPW-Gen、完整 wpw | 盲评通过率、累计上下文 Token | 验证上下文的有效性与供给效率 |
| 机制解释 | 关联开发与场景结果 | 开发成本结果与场景验证结果 | 方向一致性与消融差值 | 解释模型总 Token 下降的上下文机制 |

开发实验与场景实验采用不同统计口径：前者不计算 Recall 或 Precision，只统计模型总 Token；后者固定 Gold、问题族和评分规则，专门评价上下文定位与组织效果。两层结果不合并为同一统计量，而是通过方向一致的证据构成“开发成本下降—上下文机制验证”的解释链。

### 6.2.3 题集构成与执行规则

## 6.4 项目场景问答评估（一）：检索定位

本节评价场景问答在生成答案之前能否准确找到相关代码文件。Recall@5、Recall@10 和 Precision@10 属于场景验证指标，其作用是检验 wpw 是否以更少的无关候选覆盖更多必要证据，并为第 6.3 节观察到的模型总 Token 下降提供机制解释。

### 6.4.1 Gold 标注与文件粒度

Gold 根据冻结源码、规格和测试证据人工标注，不由任何被测条件返回结果反向定义。主指标统一采用文件粒度：同一文件中命中的多个函数或图节点只计为一个结果。相关性判断依据文件是否满足查询背后的信息需求，而不是是否机械包含查询词。Gold 集合、可接受替代文件和排除项均在执行前固定。

### 6.4.2 指标定义

对于查询 q，令 Rq 为人工标注的相关文件集合，令 Cq,k 为排序结果前 k 个去重文件，则：

$$
\mathrm{Recall@}k(q)=\frac{|R_q\cap C_{q,k}|}{|R_q|},
$$

$$
\mathrm{Precision@}k(q)=\frac{|R_q\cap C_{q,k}|}{|C_{q,k}|}.
$$

主报告使用 Recall@5、Recall@10 和 Precision@10，并同时记录 Recall@10 为 0 的任务数和查询时间中位数。结果不足 k 个时按实际返回数量计算 Precision，不自动补齐仓库文件；Gold 非空但没有命中时 Recall 和 Precision 均记为 0。

### 6.4.5 配对统计

检索指标以同一查询下的三个条件为配对观测，先采用 Friedman 检验，再对计划内条件差异进行配对 Wilcoxon 符号秩检验，并在同一指标的三组比较内采用 Holm 校正。问题族聚合后，完整 wpw 相对非 KG 的 Recall@5、Recall@10 和 Precision@10 均显著更高，校正后的 p 分别为 0.0020、0.00050 和 0.00028；配对秩二列相关绝对值分别为 0.750、0.842 和 0.866。完整 wpw 与 WPW-Map 的三项差异均不显著。

由此，场景检索实验支持“图谱增强检索相对 BM25 提高当前题集的文件定位质量”，但不支持把总体增益进一步归因于业务—代码映射。更高的召回率和精确率意味着后续问答更容易获得必要文件，并减少在无关文件上的搜索与阅读，这为开发实验中的模型总 Token 下降提供了第一层机制证据。

## 6.5 项目场景问答评估（二）：回答质量与上下文效率

### 6.5.1 回答格式与盲评

每条回答统一输出结论、关键事实、实际证据路径和不确定性说明。四个条件的回答在评分前按固定随机种子打乱并标记为 A—D，评分器不知道条件名称。通过条件要求主要机制覆盖度达到预设标准、关键结论至少有一条源码证据支持，且不存在与问题有关的重大事实错误。路径存在本身不等于语义证据成立，评分必须检查证据是否支撑回答。

评分材料包括必答事实、支撑证据、可接受替代证据、重大错误定义和通过条件。自动规则只用于路径和格式敏感性检查，不能替代盲法语义评分。

### 6.5.2 问答指标

问答主指标为盲评通过率，并报告规则通过率作为敏感性对照。上下文指标只统计实际供给的导航、图谱摘要、源码片段和规格内容，报告累计上下文 Token 的中位数、四分位距和合计值；同时记录自主搜索或源码读取次数。上下文减少不能单独代表质量提高，必须与检索 Recall、Precision 和盲评通过率结合，才能作为“上下文更精准、更高效”的证据。

### 6.5.3 总体结果

### 6.5.5 正确性与上下文规模的解释

完整 wpw 取得最高总体通过率。上下文规模方面，完整 wpw 相对 WPW-Gen 减少 40.49% 的累计上下文 Token，说明图谱摘要和相关行窗口可以减少冗余源码输入。结合第 6.4 节完整 wpw 更高的 Recall@5、Recall@10 和 Precision@10，可以形成完整的机制解释：图谱检索先提高必要代码的命中率，结构化生成再压缩无关内容，在保持较高问答通过率的同时减少模型需要处理的上下文，因此美食推荐系统开发任务的模型总 Token 随之下降。该解释由独立场景实验支持，不是在开发任务上重复计算 Recall 或 Precision。

## 6.6 场景机制消融与开发成本解释

机制消融只在场景检索与问答题集上进行，复用相同的 Gold、评分规则和代码快照，并只切换一个组件。这样可以分别观察结构图、业务映射和上下文生成对定位质量、回答正确性及上下文规模的影响；这些场景结果随后用于解释开发实验中的模型总 Token 差异。

综合来看，代码结构图是当前题集上最清晰的检索增益来源；业务—代码映射能够改变候选排序，但尚未显示稳定的额外收益；结构化上下文生成明显降低上下文规模，并伴随更高的观察通过率。场景检索的定位增益与场景问答的上下文缩减方向一致，共同说明 wpw 能够减少无关代码搜索和冗余上下文处理。因此，第 6.3 节中开发模型总 Token 的减少可以解释为更精准、更高效的上下文供给所带来的结果，而不是在开发任务上另行计算 Recall 或 Precision。

## 6.7 统计分析与报告口径

开发专项以同一任务的 OpenSpec 与 wpw 为配对观测，只报告模型总 Token 的绝对值、相对变化和精确 Wilcoxon 符号秩检验。Recall@5、Recall@10 和 Precision@10 只用于场景问答前置检索，以同一查询下的三个条件为配对观测，使用 Friedman 检验、计划内 Wilcoxon 符号秩检验、Holm 多重比较校正和配对秩二列相关。问答通过率属于同题四条件配对二元结果，设计上采用 Cochran's Q 和 McNemar 检验；正文以盲评通过率和累计上下文 Token 为主要报告内容，不把规则命中替代语义正确性。

开发实验不报告上下文规模或检索指标。场景实验使用均值、中位数和四分位距进行描述，检索结果同时报告零召回任务数，上下文规模同时报告中位数[IQR]与合计值。由于问题和查询按功能族组织，敏感性分析以问题族为聚类单位。未显著结果只表示当前题集缺少差异证据，不解释为条件等效。

正式记录、题集、评分结果和统计脚本保存在关键词召回实验数据_v4目录中，主要文件包括：manifest.json、retrieval_tasks.json、retrieval_runs.json、qa_tasks.json、qa_runs_autonomous_scored.json、statistics.json 和 build.json。结果稿与数据目录采用同一快照标识，便于复核题目、条件开关和指标计算。

## 6.8 有效性限制

本实验存在以下边界：

- 题目和源码均来自同一个 Spring Boot 项目，结论不能直接外推到其他仓库。
- 检索和问答结果依赖冻结的题集、Gold 和查询聚焦策略；这些设置适合当前评测，不等于未见项目上的泛化结果。
- 每题每条件只运行一次，无法估计生成模型在同一问题上的随机波动。
- Gold 和盲评由评测流程建立，尚未完成第二名人工标注者的全面一致性检验。
- 问答问题按功能族组织，类别结果只能作方向性解释；不能将比例化展示规模理解为新增独立样本。
- 图谱和文本索引的首次构建成本未纳入查询阶段的上下文统计；本章评价的是预构建后的使用阶段。
- 非 KG 是本实验实现的 BM25 文本基线，不代表 OpenSpec 或其他官方检索能力。
- 开发专项部分任务存在起点不一致、续跑和 Token 估算口径；相关数据只用于模型总 Token 的任务级用量描述。
- 场景实验为开发成本下降提供机制证据，但两套实验不是同一观测单元，因此“更精准、更高效的上下文导致 Token 下降”应限定在当前项目和实验条件内。

## 6.9 本章小结

本章采用“开发成本结果—场景机制验证”的两层证据设计。美食推荐系统开发实验只统计模型总 Token：T1—T3 的 8 个配对任务中，OpenSpec 与 wpw 的合计用量分别为 71,141,143 和 42,422,522，wpw 减少 40.37%；加上 T4 后，12 个任务的合计用量分别为 111,473,455 和 68,155,152，整体减少 38.86%。开发部分不计算 Recall@5、Recall@10 或 Precision@10。

Recall@5、Recall@10 和 Precision@10 仅在场景问答的检索验证中统计。完整 wpw 的三项指标分别为 0.692、0.815 和 0.185，均高于非 KG；在场景问答中，完整 wpw 的盲评通过率为 91%，并将相对 WPW-Gen 的累计上下文 Token 降低 40.49%。定位更准、上下文更少且回答通过率更高，这组结果从机制上说明，wpw 在开发实验中的模型总 Token 下降主要来自更精准、更高效的上下文供给。
