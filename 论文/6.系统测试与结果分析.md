# 第 6 章 系统测试与结果分析

## 6.1 系统功能测试

功能测试在美食推荐系统上执行，不调用大模型判断回答质量。测试方式是运行 CLI 命令、查看状态文件和图谱元数据、打开控制台页面，用例的判据是命令输出、状态转换、持久化结果或页面呈现。测试用例按第 5 章 5.2—5.6 的 15 个实现小节组织，共 34 条；每条用例在表6-3 的“对应实现小节”列中标出它覆盖的实现位置。

### 6.1.1 测试对象与业务规模

功能测试用美食推荐系统来整体串流程，它同时也是后面两组实验的数据来源。系统用 Spring Boot、Vue 和 Uni-app 编写：用户端是 Uni-app 页面，管理端是 Vue 组件，后端是 Spring Boot 的控制器、服务、数据访问层和 Mapper XML。用户登录后进入首页，系统根据浏览和收藏这类行为生成个性化推荐；用户从详情页收藏、评论、加入购物车或直接下单；订单在待付款、待发货、配送中和已完成之间流转，完成后的评价又回到偏好计算，影响下一轮推荐。管理员负责维护用户、美食分类、美食信息和订单。

选择这个项目的理由，是它的业务从推荐、下单到订单流转形成了完整闭环，多个功能模块并存，需求也经历了多轮迭代。这样的条件让 wpw 的各个环节都有真实的材料可考验：多语言源码供图谱构建解析，真实存在的业务功能供业务—代码映射标注，足够大的代码规模让上下文的裁剪和压缩有实际意义。按图谱构建的口径，项目有 12 个模块、393 个源文件和 1,369 个代码元素；完整实验图谱另有 25 个能力节点和 300 条业务—代码映射边。表6-1 汇总这些规模。

### 6.1.2 测试方式

### 6.2.3 场景检索：能不能用更少的候选找到必要文件

#### 6.2.3.1 Gold 标注与文件粒度

检索实验先看文件定位。Gold 根据冻结源码、规格和测试证据人工标注，不由任何被测条件返回的结果反向定义。主指标采用文件粒度：同一文件里命中多个函数或节点只算一个结果；相关性看文件是否满足查询背后的信息需求，不看它是否机械包含查询词。

#### 6.2.3.2 指标定义

对于查询 q，令 $R_q$ 为人工标注的相关文件集合，$C_{q,k}$ 为排序结果前 k 个去重文件，则：

$$
\mathrm{Recall@}k(q)=\frac{|R_q\cap C_{q,k}|}{|R_q|}, \tag{6-2}
$$

$$
\mathrm{Precision@}k(q)=\frac{|R_q\cap C_{q,k}|}{|C_{q,k}|}. \tag{6-3}
$$

主报告用 Recall@5、Recall@10 和 Precision@10，同时记录 Recall@10 为 0 的任务数和查询时间中位数[67]。结果不足 k 个时按实际返回数量计算 Precision，不自动补齐仓库文件；Gold 非空但没有命中时，Recall 和 Precision 都记 0。

#### 6.2.3.5 配对统计

检索指标以同一查询下的三个条件为配对观测。先做 Friedman 检验，再对计划内条件差异做配对 Wilcoxon 符号秩检验，并在同一指标的三组比较内用 Holm 校正。问题族聚合后，完整 wpw 相对非 KG 的 Recall@5、Recall@10 和 Precision@10 都显著更高，校正后的 p 分别为 0.0023、0.00033 和 0.00045；配对秩二列相关的绝对值分别为 0.729、0.844 和 0.846。完整 wpw 与 WPW-Map 的三项差异都不显著。

这组结果支持“图谱增强检索相对非图检索提高了当前题集的文件定位质量”，但不支持把总体增益进一步归因于业务—代码映射。更高的召回率和精确率意味着后面的问答更容易拿到必要文件，也少读一些无关文件；这是解释开发实验 Token 下降的第一层证据。

### 6.2.4 场景问答：上下文少了，回答是否还准

#### 6.2.4.1 回答格式与盲评

回答统一输出结论、关键事实、实际证据路径和不确定性说明。三个条件的回答在评分前按固定随机种子打乱并标成 A—C，评分器不知道条件名称。通过条件要求主要机制覆盖度达到预设标准、关键结论至少有一条源码证据支持，并且没有与问题有关的重大事实错误。路径存在不等于语义证据成立，评分要检查证据是否真的支撑回答。评分材料包括必答事实、支撑证据、可接受替代证据、重大错误定义和通过条件；自动规则只做路径和格式敏感性检查，不能替代盲法语义评分[68]。

#### 6.2.4.2 问答指标

问答主指标是盲评通过率，同时报告规则通过率作为敏感性对照。上下文指标只统计实际供给的导航、图谱摘要、源码片段和规格内容，报告累计上下文 Token 的中位数、四分位距（IQR）和均值，并记录自主搜索或源码读取次数。上下文减少不能单独代表质量提高，要和检索 Recall、Precision 以及盲评通过率一起看。

## 6.3 方法有效性分析

6.2 节的结果说明 wpw 在开发任务上总 Token 更低，在场景检索和问答上也有更好的观察值。接下来要回答两个问题。这些差异主要来自哪一部分机制，现有数据又能支持到什么程度。

### 6.3.1 机制消融：增益来自哪里

机制消融在场景题集上做，复用相同的 Gold、评分规则和代码快照，每次只切换一个组件，分别看代码结构图和业务—代码映射对文件定位质量的影响。

### 6.3.2 统计口径与有效性限制

#### 6.3.2.1 统计分析与报告口径

开发实验以同一任务的 OpenSpec 和 wpw 为配对观测，只报告模型总 Token 的绝对值、相对变化和精确 Wilcoxon 符号秩检验。检索指标以同一查询下的三个条件为配对观测，使用 Friedman 检验、计划内 Wilcoxon 符号秩检验、Holm 多重比较校正和配对秩二列相关。问答通过率是同题三条件配对的二元结果，设计上采用 Cochran's Q 和 McNemar 检验；正文以盲评通过率和累计上下文 Token 为主，不把规则命中当成语义正确。

开发实验不报告上下文规模或检索指标。场景实验用均值、中位数和四分位距描述，检索结果同时报告零召回任务数，上下文规模同时报告中位数[IQR]和均值。问题和查询按功能族组织，敏感性分析以问题族为聚类单位。未显著结果只表示当前题集缺少差异证据，不解释为条件等效。

#### 6.3.2.2 有效性限制

本实验的结论受以下边界限制：

- 题目和源码都来自同一个 Spring Boot 项目，不能直接外推到其他仓库。
- 检索和问答依赖冻结的题集、Gold 和查询聚焦策略；这些设置适合当前评测，不等于未见项目上的泛化结果。
- 每题每条件只运行一次，无法估计生成模型在同一问题上的随机波动；分类别结果只作方向性解释。
- Gold 和盲评由评测流程建立，尚未完成第二名人工标注者的全面一致性检验。
- 图谱和文本索引的首次构建成本没有计入查询阶段的上下文统计；本章评价的是预构建后的使用阶段。
- 非 KG 是本实验实现的 BM25 文本基线，不代表 OpenSpec 或其他官方检索能力。
- 开发专项部分任务存在起点不一致、续跑和 Token 估算口径，T3 和 T4 的部分数值缺少完整原始记录；相关数据只用于模型总 Token 的任务级用量描述。
- 场景实验为开发成本下降提供机制证据，但这一解释应限定在当前项目和实验条件内。
- 系统功能测试发现两处实现缺口：能力规范变更后 `wpw graph update` 未重算 `business_map` 边，多图谱布局下 `wpw archive` 也未触发图谱更新。二者不影响 6.2.3、6.2.4 的固定图谱实验，但使 6.2.1 连续开发中的归档后知识同步必须依赖显式 update 或 rebuild，长期运行会积累偏差；后续需要分别补上映射重算和归档路径检查。

## 6.4 本章小结

本章先检查 wpw 的实现，再用两组实验看方法效果。功能测试按第 5 章的 15 个实现小节组织了 34 条用例，全部通过；其中能力规范变更后的业务映射重算和多图谱布局下的归档触发更新两处行为需要显式执行 rebuild 或 update 才能生效，已在 6.1.3 说明。

开发实验中，T1—T3 的 8 个配对任务让 wpw 的模型总 Token 比 OpenSpec 少 40.37%；加上 T4 的 12 个任务，整体少 38.86%。这个结果只说明总用量更低，不能直接说明原因。场景检索中，完整 wpw 的 Recall@5、Recall@10 和 Precision@10 分别为 0.692、0.815 和 0.185，均高于非 KG；场景问答中，完整 wpw 的盲评通过率为 91%，累计上下文 Token 均值相对非 KG 减少 35.30%。机制消融显示，主要检索增益来自代码结构图，业务—代码映射尚未显示稳定的额外收益。把这些结果放在一起，可以把开发实验的 Token 下降解释为更准的文件定位和更少的上下文供给，但这一解释受同一项目、冻结题集和单次运行等条件限制。
