## 6.1 系统功能测试

本章先说明测试载体与实验条件，再按第 5 章 5.2 至 5.6 节的模块与小节划分开展功能测试，共 34 个用例。每个实现小节都有对应用例，用例与 5.x.y 的对应关系见表6-3 的“对应实现小节”列。测试以命令输出、状态文件、图谱元数据和页面呈现为判据，不以模型回答质量作为通过条件；测试于 2026-08-23 首次执行，2026-10-17 在提交 `a5ee173`（CLI 与图谱）和 `1285f4c`（可视化控制台）上复跑。功能测试只回答"实现是否符合预期"，6.2 节的数据统计与 6.3 节的方法有效性分析才回答"方法是否有效"，两者在评价对象上相互独立。

### 6.1.1 测试载体与业务规模

本章实验统一使用一个美食推荐系统作为实验载体。系统参考 Spring Boot 与 Vue 协同过滤美食推荐小程序的业务设计，采用前后端分离架构，包含普通用户和管理员两类角色。普通用户可以注册登录、浏览或搜索美食、查看详情、接收个性化推荐、使用购物车下单，也可以维护收货地址、收藏美食、发表评论和浏览资讯；管理员负责用户、美食分类、美食信息、资讯和订单的维护。主要业务流程为：用户注册登录后进入首页，系统根据用户行为和美食信息生成推荐结果；用户浏览详情后选择收藏、评论、加入购物车或直接购买；订单在待付款、待发货、配送中和已完成等状态之间流转，完成后的评价行为作为后续偏好计算的输入。

需要说明的是，系统中的协同过滤算法只用于实现个性化推荐这一业务功能。本章研究的是 AI 辅助开发过程中的流程约束、项目知识组织和任务上下文生成机制，不比较推荐算法本身的准确率；推荐算法在此仅用于构成真实的开发任务和业务场景。

### 6.1.2 测试载体的代码规模

## 6.2 数据统计

本节给出方法评估所依据的实验设计与统计数据，包括开发任务的模型总 Token、场景检索的 Recall@5、Recall@10、Precision@10，以及场景问答的盲评通过率和累计上下文 Token。各实验使用同一冻结快照、同一 Gold 和预先固定的参数；这里报告数据与统计结果，对结果的机制解释和有效性讨论放在 6.3 节。

### 6.2.1 实验设计与评价指标

#### 6.2.1.1 研究目标

方法评估回答四个相互衔接的问题：

- **RQ1：** 在美食推荐系统开发任务中，wpw 是否减少完成任务所需的模型总 Token？
- **RQ2：** 在项目场景中，代码结构图和业务—代码映射是否提高相关文件的 Recall@5、Recall@10 和 Precision@10？
- **RQ3：** 图谱驱动的结构化上下文是否提高项目场景问答通过率，并减少累计上下文 Token？
- **RQ4：** 场景检索与问答结果能否为开发实验中模型总 Token 的下降提供机制解释？

实验由开发成本观测和项目场景机制验证构成。开发实验在 T1—T3 的 8 个配对任务及 T4 的 4 轮连续需求中，只比较 OpenSpec 与 wpw 的模型总 Token。场景检索使用 100 个任务，在非 KG、WPW-Map 和完整 wpw 三个条件下比较 Recall@5、Recall@10 和 Precision@10；场景问答使用 100 个问题，在非 KG、WPW-Map、WPW-Gen 和完整 wpw 四个条件下比较盲评通过率和累计上下文 Token。前者给出成本结果，后者验证上下文定位质量与组织效率，并作为解释成本差异的机制证据。

### 6.2.3 代码检索结果统计

本节评价场景问答在生成答案之前能否准确找到相关代码文件。Recall@5、Recall@10 和 Precision@10 属于场景验证指标，其作用是检验 wpw 是否以更少的无关候选覆盖更多必要证据，并为开发成本实验中观察到的模型总 Token 下降提供机制解释。

#### 6.2.3.1 Gold 标注与文件粒度

Gold 根据冻结源码、规格和测试证据人工标注，不由任何被测条件返回结果反向定义。主指标统一采用文件粒度：同一文件中命中的多个函数或图节点只计为一个结果。相关性判断依据文件是否满足查询背后的信息需求，而不是是否机械包含查询词。Gold 集合、可接受替代文件和排除项均在执行前固定。

#### 6.2.3.2 指标定义

对于查询 q，令 Rq 为人工标注的相关文件集合，令 Cq,k 为排序结果前 k 个去重文件，则：

$$
\mathrm{Recall@}k(q)=\frac{|R_q\cap C_{q,k}|}{|R_q|}, \tag{6-2}
$$

$$
\mathrm{Precision@}k(q)=\frac{|R_q\cap C_{q,k}|}{|C_{q,k}|}. \tag{6-3}
$$

主报告使用 Recall@5、Recall@10 和 Precision@10，并同时记录 Recall@10 为 0 的任务数和查询时间中位数[67]。结果不足 k 个时按实际返回数量计算 Precision，不自动补齐仓库文件；Gold 非空但没有命中时 Recall 和 Precision 均记为 0。

### 6.2.4 项目场景问答结果统计

#### 6.2.4.1 回答格式与盲评

每条回答统一输出结论、关键事实、实际证据路径和不确定性说明。四个条件的回答在评分前按固定随机种子打乱并标记为 A—D，评分器不知道条件名称。通过条件要求主要机制覆盖度达到预设标准、关键结论至少有一条源码证据支持，且不存在与问题有关的重大事实错误。路径存在本身不等于语义证据成立，评分必须检查证据是否支撑回答。

评分材料包括必答事实、支撑证据、可接受替代证据、重大错误定义和通过条件。自动规则只用于路径和格式敏感性检查，不能替代盲法语义评分[68]。

#### 6.2.4.2 问答指标

问答主指标为盲评通过率，并报告规则通过率作为敏感性对照。上下文指标只统计实际供给的导航、图谱摘要、源码片段和规格内容，报告累计上下文 Token 的中位数、四分位距和合计值；同时记录自主搜索或源码读取次数。上下文减少不能单独代表质量提高，必须与检索 Recall、Precision 和盲评通过率结合，才能作为"上下文更精准、更高效"的证据。

综合来看，代码结构图是当前题集上最清晰的检索增益来源；业务—代码映射能够改变候选排序，但尚未显示稳定的额外收益；结构化上下文生成明显降低上下文规模，并伴随更高的观察通过率。场景检索的定位增益与场景问答的上下文缩减方向一致，共同说明 wpw 能够减少无关代码搜索和冗余上下文处理。因此，开发成本实验中模型总 Token 的减少可以解释为更精准、更高效的上下文供给所带来的结果，而不是在开发任务上另行计算 Recall 或 Precision。

### 6.3.2 统计口径与有效性限制

#### 6.3.2.1 统计分析与报告口径

开发专项以同一任务的 OpenSpec 与 wpw 为配对观测，只报告模型总 Token 的绝对值、相对变化和精确 Wilcoxon 符号秩检验。Recall@5、Recall@10 和 Precision@10 只用于场景问答前置检索，以同一查询下的三个条件为配对观测，使用 Friedman 检验、计划内 Wilcoxon 符号秩检验、Holm 多重比较校正和配对秩二列相关。问答通过率属于同题四条件配对二元结果，设计上采用 Cochran's Q 和 McNemar 检验；正文以盲评通过率和累计上下文 Token 为主要报告内容，不把规则命中替代语义正确性。

开发实验不报告上下文规模或检索指标。场景实验使用均值、中位数和四分位距进行描述，检索结果同时报告零召回任务数，上下文规模同时报告中位数[IQR]与合计值。由于问题和查询按功能族组织，敏感性分析以问题族为聚类单位。未显著结果只表示当前题集缺少差异证据，不解释为条件等效。

#### 6.3.2.2 有效性限制

本实验存在以下边界：

- 题目和源码均来自同一个 Spring Boot 项目，结论不能直接外推到其他仓库。
- 检索和问答结果依赖冻结的题集、Gold 和查询聚焦策略；这些设置适合当前评测，不等于未见项目上的泛化结果。
- 每题每条件只运行一次，无法估计生成模型在同一问题上的随机波动。
- Gold 和盲评由评测流程建立，尚未完成第二名人工标注者的全面一致性检验。
- 问答问题按功能族组织，类别结果只能作方向性解释；不能将比例化展示规模理解为新增独立样本。
- 图谱和文本索引的首次构建成本未纳入查询阶段的上下文统计；本章评价的是预构建后的使用阶段。
- 非 KG 是本实验实现的 BM25 文本基线，不代表 OpenSpec 或其他官方检索能力。
- 开发专项部分任务存在起点不一致、续跑和 Token 估算口径；相关数据只用于模型总 Token 的任务级用量描述。
- 场景实验为开发成本下降提供机制证据，但两套实验不是同一观测单元，因此"更精准、更高效的上下文导致 Token 下降"应限定在当前项目和实验条件内。
- 系统功能测试发现两处实现缺口：能力规范变更后 `wpw graph update` 未重算 `business_map` 边，多图谱布局下 `wpw archive` 也未触发图谱更新。二者不影响 6.2.3、6.2.4 的固定图谱实验，但使 6.2.2 连续开发中的归档后知识同步必须依赖显式 update 或 rebuild，长期运行时也会积累偏差；后续需分别补上映射重算和归档路径检查。

## 6.4 本章小结

本章先说明了测试载体与实验条件，并对 wpw 进行了系统功能测试：工作流门禁、图谱构建与查询、上下文生成与预算约束、增量更新与降级行为基本符合预期，34 个分模块用例中 32 个通过、2 个部分通过；偏差集中在能力规范变更后的业务映射重算和多图谱布局下的归档触发更新，实现与第 5 章的设计在其余部分一致。随后在 6.2 节统计"开发成本结果—场景机制验证"的两层数据，并在 6.3 节分析其方法有效性。美食推荐系统开发实验只统计模型总 Token：T1—T3 的 8 个配对任务中，OpenSpec 与 wpw 的合计用量分别为 71,141,143 和 42,422,522，wpw 减少 40.37%；加上 T4 后，12 个任务的合计用量分别为 111,473,455 和 68,155,152，整体减少 38.86%。开发部分不计算 Recall@5、Recall@10 或 Precision@10。

Recall@5、Recall@10 和 Precision@10 仅在场景问答的检索验证中统计。完整 wpw 的三项指标分别为 0.692、0.815 和 0.185，均高于非 KG；在场景问答中，完整 wpw 的盲评通过率为 91%，并将相对 WPW-Gen 的累计上下文 Token 降低 40.49%。定位更准、上下文更少且回答通过率更高，这组结果从机制上说明，wpw 在开发实验中的模型总 Token 下降主要来自更精准、更高效的上下文供给。
