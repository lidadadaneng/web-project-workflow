# 第 7 章 总结与展望

## 7.1 全文结论

本文针对 AI 辅助开发中项目知识分散、业务语义与代码结构脱节以及长周期开发过程中上下文重复获取的问题，提出并实现了 wpw 图谱驱动上下文工程方法。该方法并不替代规格驱动开发（Specification-Driven Development，SDD），而是在 SDD 流程基础上增加项目知识的结构化组织与按任务供给能力。本文以 Spec 作为知识演化单元，以 Capability 作为业务语义与代码实现之间的稳定锚点，构建 C-L1-L2-L3 能力—代码双层知识模型，并通过 `business_map` 维护业务能力与模块、文件及函数之间的关联。在任务执行阶段，系统利用锚点选择、加权双向 BFS、骨架抽取和预算约束生成任务相关上下文；在需求变化后，再根据 Spec 和源码差异增量更新项目知识。

在方法基础上，本文实现了 wpw 系统，将六阶段流程约束、规格制品管理、代码图谱构建、业务—代码映射、混合检索、上下文压缩和知识增量维护集成到统一工具链中。随后以美食推荐系统开发实验和项目场景检索实验分别评价模型资源消耗与代码定位质量。两类实验从不同侧面得到以下结论。

第一，**wpw 图谱驱动模式相较不使用图谱的 SDD 基线消耗更少的模型总 Token**。在美食推荐系统 T1—T4 的 12 个开发任务中，OpenSpec SDD 基线的模型总 Token 合计为 111,473,455，wpw 为 68,155,152，整体减少 38.86%。其中，T1—T3 的 8 个开发任务由 71,141,143 降至 42,422,522，减少 40.37%；T4 四轮连续需求由 40,332,312 降至 25,732,630，减少 36.20%。这说明，在当前项目和实验条件下，图谱驱动的项目知识组织能够降低智能体完成软件开发任务所需的模型用量。

第二，**wpw 图谱驱动模式相较不使用图谱的 SDD 上下文基线取得了更好的代码检索效果**。在 100 个项目场景检索任务中，完整 wpw 的 Recall@5、Recall@10 和 Precision@10 分别为 0.692、0.815 和 0.185，非 KG 基线分别为 0.483、0.617 和 0.126，对应提高 0.209、0.198 和 0.059；Recall@10 为 0 的任务数也由 12 个减少到 3 个。三项指标在问题族聚合后仍显著，表明图谱增强检索能够覆盖更多任务相关文件，并减少无关候选。WPW-Map 已取得接近完整 wpw 的结果，说明当前定位增益主要来自代码结构图与混合检索，业务—代码映射的独立增量仍不稳定。

两类证据共同回答了本文的核心问题。美食推荐系统开发实验直接证明 wpw 能够减少模型总 Token，场景检索实验则证明图谱驱动模式能够以更高的 Recall@5、Recall@10 和 Precision@10 定位任务相关代码。结合完整 wpw 在场景问答中取得最高盲评通过率、相对 WPW-Gen 减少 40.49% 累计上下文 Token 的结果，可以认为 wpw 的资源优势来自更精准的代码定位和更紧凑的上下文组织：智能体能够更早获得必要证据，减少对无关文件和冗余代码的反复读取，进而降低完成开发任务所需的模型总 Token。

因此，本文的总体结论是：在共同的 SDD 流程基础上，引入面向业务能力和代码结构的项目知识图谱，并据此生成任务上下文，可以同时改善代码定位质量和模型资源效率。wpw 的主要价值不是改变基础模型能力，而是改进模型获得项目知识的方式，使有限上下文优先承载与当前任务相关的代码和业务信息。该结论目前限定于本文的美食推荐系统、冻结题集、模型配置和实验流程，尚不能直接外推到所有软件项目。

## 7.2 研究展望

后续工作可以从四个方面展开。第一，扩展源码解析范围，在现有 Java、Mapper XML 和前端代码基础上支持更多编程语言、构建配置与运行时依赖，提高跨语言项目的图谱完整性。第二，继续改进业务—代码映射，引入测试、Issue、提交评审和运行轨迹等证据，提升 `business_map` 的稳定增量。第三，在更多规模、领域和技术栈的项目中开展重复实验，并增加不同模型、人工盲评和多次运行，以检验结论的泛化性。第四，将项目知识更新和上下文供给进一步接入 IDE、代码评审和 CI 流程，同时统计图谱构建、更新与查询的全生命周期成本，评价其在真实团队长期开发中的收益。
