## ABSTRACT

- 研究背景：大模型推动 AI Agent 参与软件开发，但长期项目开发面临上下文瓶颈：代码库规模增长超出窗口有效范围、业务知识与代码结构割裂、项目演化缺少持续知识积累机制。
- 研究内容（四个层面，原四个创新点表述）：① 面向长期软件演化的能力-代码双层知识组织模型（Spec -> Capability -> Code，C-L1-L2-L3）；② 图谱驱动的任务上下文生成方法（面向 Agent 的任务级子图生成，最小充分上下文）；③ Spec 增量知识演化机制（工程化知识积累，不单独宣称长期效益）；④ WPW 系统实现与基于大模型的美食推荐系统验证。
- 系统实现：WPW 系统（CLI 层 TypeScript + AI 层 Claude Code Skill，14 个 /wpw 命令 + 文件系统层；多语言源码解析、本地 Embedding、零数据库、图谱增量更新）。
- 实验验证：先对 WPW 做系统功能测试；再在统一配置下比较 OpenSpec 与 WPW 完成相同开发任务的效果与成本；最后在同一代码快照上比较普通检索与图谱增强两种条件的代码定位覆盖与开销，回答 RQ1-RQ3；不评价推荐算法准确率。
- 关键词（英）：Large Language Model；Context Engineering；AI-Assisted Software Development；Code Knowledge Graph（与 `0.摘要.md` 一致；Recommendation System 已随题目调整删除）

## 盲审/答辩防御要点（写作时内化到对应章节，不单独成节）

1. **"为什么比 GPT/Claude/DeepSeek 强？"** -> 本文不改变基础模型能力，研究对象是模型输入上下文的质量与组织方式（1.1（3）研究对象限定段）。
2. **"为什么不用 Agent 运行框架（Harness）？"** -> 本文不替代 Harness，在智能体已具备执行能力之后研究软件工程项目的高质量上下文构造（1.1（3）研究对象限定段）。
3. **"为什么不直接使用长上下文？"** -> 长上下文解决容量问题，本文关注相关上下文的选择问题（1.1（2）其一 Lost in the Middle + 5.4.3）。
4. **"为什么不和所有工具比较？"** -> OpenSpec 作为主要 SDD 基线，Superpowers 和 Spec Kit 作为相关方法参照；研究目的是分析 KG 驱动上下文组织的增量作用，非工具排行榜（第 6 章任务级开发成本结果分析）。
5. **"RIG/KGCompass 已经做了仓库图谱服务 Agent，你的创新在哪？"** -> 它们的知识对象是代码实体/架构依赖/Issue-PR 制品，回答"项目架构是什么"；本文以业务能力为长期语义锚点，回答"项目有哪些业务能力、由什么代码实现、如何随需求演化、如何进入任务上下文"，即 Spec->Capability->Code->Context 知识链（1.3.2 综述分析定位段 + 第 3 章表3-4 对比）。
6. **"图谱技术不是你的创新吧？"** -> 创新不在知识图谱形式，而在 Capability-Code 知识结构设计与随 Spec 演化的组织机制（第 3 章 3.3.4 与相关工作的区别）。
