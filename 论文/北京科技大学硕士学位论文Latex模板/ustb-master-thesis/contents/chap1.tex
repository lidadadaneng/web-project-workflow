\chapter{引言}


\section{研究背景}
在软件工程实践中，开发者需要分析用户需求，确定系统功能，设计接口、数据结构和模块关系，编写代码并通过测试，在系统投入使用后，还要处理缺陷、调整接口、增加功能，并检查修改是否影响已有模块。通常一个功能的实现同时涉及需求文档、接口定义、数据模型、配置文件和多个代码模块，这些内容可能由不同人员在不同阶段维护，分别记录在需求文档、设计文档、代码文件、配置文件和测试用例中。开发者需要把它们对照起来，才能确定修改位置和影响范围。

AI（人工智能）参与编程是从代码补全开始的。早期工具根据当前文件的上下文补全下一行代码或生成单个函数，模型只需要处理光标附近的内容[29][30]。这种方式节省了敲代码的时间，但需求怎么拆分成模块、代码按什么思路组织、改动会影响哪些地方，仍要开发者自己梳理和判断，整体效率的提升有限。随着代码模型能力增强，模型已经可以读取外部材料，根据自然语言查找代码，并按照计划修改多个文件[5][11-12][30][35]。开发者不再只向工具询问某个函数怎么写，也可以让它搜索项目、修改代码和运行测试。但是模型面对的是一整个代码库。把全部文件交给模型，会带入大量与当前任务无关的内容；只提供当前文件，又可能漏掉接口和依赖。长上下文研究也表明，输入变长并不能保证模型有效利用所有信息[4]。所以实际执行任务时，智能体仍要先搜索项目，再判断哪些内容需要保留。

后来，SWE-bench 开始用真实的 GitHub issue（问题报告）检验模型能否完成项目修改[16]，SWE-agent、Devin 和 OpenHands 等智能体让模型自己搜索文件、编辑代码、执行测试，再根据结果继续修改[17][32-33]。AI 编程已经进入真实开发环境，但开发者对输出准确性的信任仍然有限[43]。一次修改能否完成，不只取决于代码能否生成。智能体还要找到正确的文件，理解业务规则，并检查修改对其他模块的影响。

以“支持用户收藏菜品”为例，这个需求可能同时涉及用户模块、菜品模块、数据库表、接口、权限和页面状态。熟悉项目的开发者凭经验就能找到这些联系，智能体却要从需求文字、代码结构和历史修改中重新建立它们。如果这些判断只留在对话中，下一次任务还要重新搜索；如果只保存代码文本，又很难说明这些代码对应哪项业务能力。需求与代码之间缺少稳定的联系，智能体就难以在连续任务中沿用已有的判断。

为了不每次都重新搜索，已有工作开始把项目中的关系保存下来。一类做法把 Issue、PR（Pull Request，拉取请求）、文件、类和函数组织成仓库知识图谱，并随仓库变化更新[38][39]；也有工作用程序血缘分析业务变动会影响哪些程序[42]；还有工作用规范文档和任务流程约束智能体的执行过程[8-9]。这些方法分别保存了代码结构、仓库关系或执行过程。但是一项业务由哪些代码实现，需求变化会影响哪些代码，以及这些判断怎样留给后续任务使用，这三个问题通常没有被同时回答。

需求文档描述业务目标，代码文件记录实现细节，接口、数据结构和模块调用把两者连接起来。本文把 Spec（需求规格说明）、业务能力、模块、文件和函数放入同一个项目知识模型，先记录一项业务由哪些代码实现；任务到来时，再根据任务描述选择相关内容，生成受 Token 预算约束的上下文；需求或代码发生变化后，只更新受影响的关系。这样就把需求规格、业务能力、代码实现、演化记录和任务上下文连成了一条知识链，可以减少智能体在连续任务中反复搜索和重新理解项目的工作。


\section{研究意义}
从代码补全到智能体执行完整的开发任务，AI 编程的能力快速提升，但智能体面对整个代码库时，仍要自己搜索项目、判断哪些内容与当前任务相关。需求与代码之间缺少稳定的联系，智能体在连续任务中只能反复搜索和重新理解项目，开发效率的提升因此受到限制。

本文围绕这一问题，建立 Spec 驱动的能力—代码双层知识组织模型，把需求规格、业务能力和代码结构放入同一个项目知识模型持续维护；在此基础上提出图谱驱动的任务上下文生成方法和 Spec 增量知识演化机制，并实现 wpw 原型系统，使智能体在连续任务中能够复用已有的项目认识。

在长期演化项目中引入这种知识组织方式具有以下实践意义：智能体不再每次临时搜索整个项目，减少了定位相关代码的时间，需求变更时也只需更新受影响的联系；智能体从同一份业务—代码知识出发定位任务内容，减少因搜索路径和任务写法不同带来的修改质量波动；开发者还可以反方向追溯一段代码对应哪项业务，确认一次修改涉及的业务范围，更好地保障项目的可维护性。

本研究的意义主要体现在工程应用与实践创新层面。针对智能体在连续任务中反复搜索、项目开发中已有的积累难以被有效利用的问题，本文将知识图谱与上下文工程方法同智能体开发流程相结合，在已有代码检索、需求追踪和仓库知识图谱研究的基础上，搭建了项目知识构建、任务上下文生成与增量维护的完整体系，并结合美食推荐系统的实际开发任务验证方法的可行性，形成了可复用、可落地的解决方案。该工作有助于推动上下文工程在 AI 辅助开发中的工程化落地，对长期演化项目中的智能体开发具有参考价值。


\section{国内外研究现状}

\subsection{研究进展}
大模型出现以后，模型开始从辅助编程走向执行完整的软件工程任务。2024 年提出的 SWE-bench 用真实 GitHub issue 检验模型能否完成项目修改[16]，SWE-agent 研究智能体与计算机之间的交互接口[17]，Devin[32]、OpenHands[33] 等系统把文件编辑、命令执行和错误修复放进连续执行过程。Hou 等人对 LLM4SE 文献的梳理也显示，大模型在软件工程中的应用已经由代码生成、补全和解释扩展到需求、设计、开发、质量保障和维护[1]。真实项目研究开始记录编程智能体的采用情况[2]，分析智能体产出与人类开发者之间的差距[3]，并考察智能体重构的类型、动机和代码质量变化[10]。与此同时，“Lost in the Middle”研究表明，即使模型能够接收长输入，信息所在位置仍会影响模型是否真正使用这些内容[4]，智能体要为任务找到并组织相关内容，不能只依赖扩大上下文窗口。针对智能体怎样获得并组织任务相关内容，现有研究大体可以分为三类：需求追踪与规格驱动开发方法、代码检索与结构表示方法、仓库知识图谱方法。下面按类别归纳、比较与评价。

（1）需求追踪与规格驱动开发方法

这类方法从需求侧入手，要么恢复需求与代码之间的追踪链接，要么把需求规格作为开发过程的核心制品来约束智能体。典型代表包括信息检索类追踪方法、TRIAD，以及 GitHub Spec Kit、OpenSpec、Superpowers 等规格驱动工具。

需求追踪研究关注需求与实现、验证这些需求的代码之间怎样建立对应关系。Cleland-Huang 等人在 2004 年前后研究了如何提高需求追踪的投入产出比[13]，后续工作尝试用群体智能和信息检索自动恢复需求制品与代码之间的链接[15]，Borg 等人在 2014 年对这一方向进行了系统梳理，信息检索由此成为恢复追踪链接的主流方法[14]。

TRIAD 是南京大学团队在大模型时代提出的追踪恢复方法[41]。它先从制品文本中提取共识词对，增强制品之间的语义关联，再沿制品间的传递链接推导，恢复需求到代码的追踪关系。这种方法不需要人工预先标注链接，能够恢复出直接匹配难以发现的间接追踪关系。但恢复出的链接服务当次追踪任务，链接本身不作为项目知识长期维护，需求变化后也不会随之更新。

规格驱动开发把需求规格作为开发过程的核心制品。Piskala 将规格驱动开发（Spec-Driven Development，SDD）概括为由“代码即事实源”（code-as-source）转向“规格即首要制品”（specification-as-primary-artifact）[7]。Haeri 等人考察了规格约束与大模型代码测试效果之间的关系[60]，Tufano 等人对规格优先的智能体工作流进行了实证研究[61]，Saha 等人从生命周期和制品追踪角度梳理了规格驱动智能体开发[62]。

GitHub Spec Kit 用一组规范制品组织智能体的开发过程[8][9]。项目先以 Constitution 确定总体约束，再由 Specification 描述需求，Plan 把需求分解为实现方案，最后拆成任务交给智能体执行。这套制品让规范成为可检查的一等制品，智能体不再只凭对话中的临时指示工作。但规范记录的是“要做什么”，不记录“哪项业务由哪些代码实现”，规范与代码之间的对应关系并不在这套制品中。

OpenSpec 以 Change 为单元管理需求演化[8][9]。每次变更包含提案、设计、任务等制品，实施完成后归档并更新既有规格，变更的状态因此可以追踪。这种机制让需求演化有了明确的记录单元。但变更制品与代码之间的关联依靠流程和人工维护，业务—代码关系不会随变更自动建立，也不直接用于生成任务上下文。

Superpowers 用可组合技能和强制工作流约束智能体的执行过程[9]。需求澄清、计划、开发、测试和审查各阶段由相应技能定义，子代理按分工执行，执行纪律因此得到保证。但过程产物停留在流程记录与对话产物中，没有沉淀为可以查询的项目知识结构，后续任务无法直接复用。

总结下来，这类方法保存了需求与规格信息，让开发过程更容易检查和追踪，但追踪结果服务当次分析，规格制品面向流程管理，需求与代码的对应关系既不自动建立，也不直接用于生成任务上下文。Spec Kit、OpenSpec、Superpowers 仍在快速迭代，本文只讨论截至 2026 年 8 月检索到的版本，并在附录实验环境表中固定版本号、发布日期和代码提交记录。

（2）代码检索与结构表示方法

这类方法从代码侧入手，要么按文本或代码相似度检索相关片段，要么把代码实体之间的结构关系显式保存下来。典型代表包括 CodeSearchNet、RAG、代码属性图、GraphCodeBERT，以及 RepoHyper、GraphRAG 等。

代码检索研究根据文本或代码相似度返回相关片段。CodeSearchNet 在 2019 年定义了自然语言—代码检索任务，并提供大规模数据集[12]；RAG 在 2020 年把外部知识检索接入生成过程，使模型可以在执行任务时读取参数之外的信息[5]。这类方法能在任务到来时快速汇集相关内容，但检索结果按相似度拼合，不说明代码之间的结构关系，知识也不在任务之间传递。

结构表示研究把代码实体之间的关系显式保存下来。Yamaguchi 等人在 2014 年提出代码属性图（Code Property Graph），把抽象语法树、控制流图和程序依赖图合并为可查询的图模型，用于漏洞挖掘[18]；GraphCodeBERT 把数据流加入代码表示学习[11]，知识图谱研究也系统总结了如何用实体、关系和属性组织领域知识[37]。随着代码模型能力提高，研究对象从单个函数扩展到整个代码仓库：Code Llama 等模型强化了代码生成与理解能力[30]，DeepSeek Coder 通过代码数据和项目级训练提升代码任务表现[31]，CodePlan 用计划组织仓库级修改涉及的多个步骤[35]；浙江大学团队提出 CatCoder，把静态分析得到的类型信息与检索结果一起提供给模型，用于上下文感知的代码补全[34]。结构信息也开始直接服务检索与生成，RepoHyper 用代码结构超图执行“搜索—扩展—精炼”[36]，GraphRAG 用实体—关系图连接检索与生成[19]。同一时期，国内大模型平台开始发展，通义千问[21]、文心[22]、混元[23]、GLM[25] 等平台相继开放，CodeGeeX、通义灵码等工具把代码补全、解释和对话能力接入开发环境[29]，为这类方法提供了模型与工具基础。

总结下来，这类方法改善了模型对仓库级代码的理解，但检索结果按相似度拼合，结构信息描述的是代码实体自身，需求语义不在其中。

（3）仓库知识图谱方法

近两年，代码结构知识与智能体执行开始直接结合，形成仓库知识图谱类方法。这类方法把仓库中的制品和代码实体组织成图，用图结构为智能体的定位、生成和问答提供仓库知识。典型代表包括 KGCompass、Repository Intelligence Graph 等。

Athale 等人使用代码仓库知识图谱增强演化代码库上的仓库级代码生成[39]；中国工商银行软件开发中心利用抽象语法树和字节码分析构建全链路程序血缘，用它判断交易变动会影响哪些程序[42]。

KGCompass 由燕山大学牵头、多家机构合作完成，面向仓库级缺陷修复构建仓库感知知识图谱[38]。它从仓库中提取 Issue、PR、文件、类和函数等节点及它们之间的关系，智能体修复缺陷时从 Issue 出发，沿图路径逐步扩展到相关文件和函数，修复完成后图谱随仓库提交增量更新。这项工作在真实仓库修复任务上验证了图结构对定位修复位置的帮助，增量更新也让图谱能够跟随仓库演化。但图中的节点是 Issue、PR 和代码实体，需求规格与业务能力不在其中，业务语义与代码的关联不是它的维护对象。

Repository Intelligence Graph 为代码助手提供确定性的仓库架构图[40]。它通过静态分析从仓库生成架构图，同一仓库生成的结果固定，不依赖模型的即时推断，Claude Code、Cursor、Codex 等智能体可以把它作为稳定的架构层上下文使用，并在多个仓库上考察了代码定位和任务完成情况。确定性的生成方式保证了结果可复现，但架构图描述的是模块与依赖等结构信息，需要语义理解才能建立的业务—代码联系不在其中。

在此基础上，Chinthareddy 比较了 AST 派生图与大模型抽取图在代码库 Graph-RAG 中的可靠性[63]，Abedu 等人研究了知识图谱如何支持软件仓库问答[64]，Jiang 等人把知识图谱作为复杂智能体推理和记忆的状态空间[65]。

总结下来，这类方法已经把结构知识带入智能体的执行过程，部分还支持随仓库变化增量维护，但图中的主要对象仍是文件、类、函数、架构依赖等代码实体与制品，需求语义与代码实现之间的联系不在其中。

国内大模型生态也在这一时期继续扩展，豆包[24]、Kimi[26] 和 DeepSeek[27] 等平台进入更多应用场景。国务院在 2025 年发布《关于深入实施“人工智能+”行动的意见》，提出推动人工智能与各领域融合，并加快智能体应用落地[20]。到 2026 年，关于智能体自演化的综述开始把仓库级上下文、可执行反馈和记忆机制放在同一条发展线上讨论[6]。


\subsection{综述分析}
从这三类方法的发展过程可以看到，国内外研究先建立代码检索、结构表示和需求追踪方法，然后把这些方法用于仓库级生成和智能体执行，近两年又开始用规格约束开发过程、用图结构提供仓库上下文。研究关心的问题也随之变化：早期关注一次查询能否找到相关代码，现在还要考虑任务结束后形成的知识能否保留下来，以及需求变化后业务语义与代码结构的联系能否继续使用。

现有方法已经覆盖这条链路的多个局部环节，代码语义检索、仓库级代码生成、代码知识图谱、软件制品追踪和智能体工作流都形成了一定积累。KGCompass、Repository Intelligence Graph 等工作还通过实验表明，结构化仓库知识有助于改善智能体的代码定位和任务执行[38][40]；Spec Kit、OpenSpec、Superpowers 等工具也在工程实践中积累了各自的规范与变更制品。不过这些方法维护的核心对象不同，表 1-1 列出代表性工作流工具与本文方法所维护的知识对象。

从知识对象看，现有工作多以代码实体、架构依赖或 Issue/PR 等仓库制品为中心。需求追踪和规格制品保存了需求侧的信息，但业务能力本身没有成为独立的知识对象，需求语义与代码实现之间的联系也就缺少稳定的挂靠点。从知识的生命周期看，CatCoder、TRIAD 等检索与追踪方法主要服务当次补全或链接恢复，任务结束后结果便不再维护；KGCompass、Repository Intelligence Graph 和程序血缘虽然持续维护图结构，维护的仍是代码实体与制品之间的关系。

从上下文进入任务的方式看，RAG、RepoHyper 等方法在任务到来时检索并拼接相关片段，每个任务重新进行，知识不在任务之间传递；Spec Kit、OpenSpec、Superpowers 用规格和变更制品约束开发过程，积累了项目认识，但这些积累主要面向流程检查与追踪，没有直接用于生成任务上下文。从对项目演化的响应看，OpenSpec 以 Change 管理制品演化，KGCompass 支持图谱随仓库增量更新，但二者互不相连：规格变化不会触发代码关系的更新，图谱更新也不以需求为单元。

综合这几个角度可以看到，如何把 Spec/Change 作为知识演化单元，让业务能力处在需求语义和代码结构之间，在持续开发中维护这条联系，并据此生成受 Token 预算约束的任务上下文，目前还没有形成统一的方法。本文因此不重新提出代码图谱或代码检索，而是研究需求规格、业务能力、代码结构、项目演化和任务上下文这条长期知识链在 AI 编程智能体中的应用。

\section{研究内容}
智能体参与长期项目开发时，每次任务到来都要先在项目中搜索相关文件，把找到的内容组织成当前任务所需的上下文。上下文窗口放不下整个项目，搜索和组织就要分多轮进行；对话变长以后，早期找到的内容被挤出窗口，下一个任务又得重新搜索一遍。一项业务由哪些代码实现、上次为什么这么改，这些判断只留在当次对话里，任务结束就丢了。智能体始终在用临时搜索的结果干活，项目做得越久，重复搜索和重新理解的成本越高。

本文要解决的，就是让这些判断留下来，并且能直接被后续任务使用。围绕这一问题，研究目标定为三件事：把业务能力和实现它的代码放进同一份项目知识里，可以随时查询和更新；任务到来时，从这份知识里选出与当前任务相关的部分，在 Token 预算内组织成上下文；需求或代码发生变化后，只更新受影响的部分，不用从头再来。本文不改动大模型本身，也不替代智能体的运行框架，只研究交给模型的上下文如何组织。开发过程按 BRD、PRD、Design、Plan、Test、Apply 六个阶段推进，每个阶段产出固定的文档，前一阶段完成后才能进入下一阶段；上下文在哪些阶段产生、哪些阶段使用，也随流程固定下来。本文核心研究内容如图1-2所示，涵盖以下四个层面。

（1）在知识建模层面，把业务能力和代码放进同一个项目知识模型。按文本或符号搜索代码，能找到相似的片段，却说不出一项业务由哪些代码实现、这些代码为什么这样组织。本文用 Spec 描述业务能力，用多语言源码解析得到模块、文件和函数三级代码结构，再从文档、命名、语义和 Git 历史四个方面收集业务与代码之间可能有关的证据，用 noisy-OR 概率模型把多份证据合成一条关联边，每条边都能回看它来自哪类证据。图谱用 JSONL 文件和本地向量索引保存，不需要单独部署数据库。后面的上下文生成和知识更新都建立在这份模型上。

（2）在上下文生成层面，按任务从图谱中取出够用的上下文。把整个代码库交给模型会带入大量无关内容，只靠人工挑选又慢又容易漏。本文先按任务描述在图谱中选定入口节点，再沿关联边向外扩展，取出与任务相关的一片子图；随后按节点离入口的远近决定保留多少细节，离得远的只留梗概；最后按预算选择压缩档位输出，放不下就再降一档，保住完成任务必须的内容。这样得到的上下文来自持续维护的项目知识，而不是一次任务的临时拼接。

（3）在知识演化层面，让项目知识跟着需求一轮轮更新。图谱如果只在项目开始时建一次，几轮需求之后就过时了。本文把需求 Spec 作为更新的触发单元：新项目先扫描源码、结合需求 Spec 建立初始图谱；已有项目来了新需求，先把需求写成 Spec，再把它和已有能力关联起来，只更新受影响的代码关系，不用每次重建整个图谱。项目知识就这样随开发过程沉淀下来，后续任务可以直接调用。

（4）在系统实现与方法验证层面，把上述做法做成 wpw 系统，并在真实开发任务中检验。wpw 分为 AI 层、CLI（命令行界面）层和文件系统层，实现工作流、图谱构建、上下文生成和增量维护四个模块。验证借助一套用 AI 辅助开发完成的美食推荐系统：设置基础搭建（T1）、业务核心（T2）和迭代增强（T3）三组开发任务，在相同的规格驱动流程下比较 OpenSpec 与 wpw；另设 100 个检索任务和 100 个项目场景问题，分别检查相关代码找得准不准、项目问题答得对不对、上下文花得多不多，并在同一套题里分别关掉图谱、业务—代码映射和上下文生成组件，看每一项带来的变化。评价指标和数据处理方式在实验前固定，结论以实际记录为准。


\section{论文组织结构}
本文共分为七章，各章内容安排如下。

第 1 章，引言。介绍研究背景与意义，梳理国内外研究现状，说明本文的研究内容。

第 2 章，相关技术与理论基础。围绕后续方法需要用到的技术，介绍大语言模型与 AI 编程智能体、软件工程上下文工程、软件知识图谱与代码结构分析、Spec 驱动开发方法，以及推荐系统与 Web 架构背景。

第 3 章，面向 AI 辅助开发的上下文工程方法。给出方法的总体框架，然后依次阐述六阶段流程约束架构、能力-代码双层知识模型、Spec 增量知识演化机制和图谱驱动的任务上下文生成方法。

第 4 章，系统需求分析。分析 wpw 系统的功能需求与非功能需求，明确系统的使用者、使用场景和约束条件。

第 5 章，系统设计与实现。说明方法如何落地为 wpw 系统，包括三层架构以及工作流、图谱构建、上下文生成和增量维护四个模块的设计与实现。

第 6 章，系统测试与结果分析。以美食推荐系统为统一实验载体，说明其业务规模、代码规模和实验条件；对 wpw 系统进行系统功能测试，并分析任务级开发成本、检索定位与项目问答的实验结果以及机制消融的表现，讨论方法的适用条件与局限。

第 7 章，总结与展望。总结全文工作，展望后续研究方向。
