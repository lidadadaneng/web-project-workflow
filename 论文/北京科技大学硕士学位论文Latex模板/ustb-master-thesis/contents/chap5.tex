\chapter{实验与评估}

本章以基于大模型的美食推荐系统为实验载体，通过对比实验与消融实验验证本文提出的上下文工程方法的有效性。需预先明确本章定位：\textbf{本实验并非验证 wpw 工具相较其他工具的绝对优势，而是验证上下文工程方法中流程约束、知识组织和上下文生成机制对 AI 辅助开发效果的影响}。同时明确实验对象边界：\textbf{本章实验对象为美食推荐系统的软件实现过程。由于本文重点研究大模型辅助软件开发中的上下文组织问题，实验并不评价推荐算法准确率，而是在统一业务系统实现任务下，分析不同大模型辅助开发方式对系统开发成本、质量和可维护性的影响}。

本章的验证对象是第 3 章提出的上下文工程方法：其三项核心机制（流程约束、知识组织、上下文生成）共同服务于"面向 AI 编程智能体的上下文工程"这一主线，wpw 是该方法的实现载体（第 4 章），美食推荐系统是实验载体（1.1.2 节）。因此，本章比较的是\textbf{不同方法在关注维度上的差异}，而非工具高下：在受控对比中分析上下文工程方法（受控流程 + 结构化知识供给 + 预算控制）对开发成本、质量、上下文效率与流程可控性的影响，以及三项机制各自的贡献。

本章组织如下：5.1 节给出实验设计（目标与研究问题、测试系统设计与任务定义、AI 辅助开发方案、评价指标、消融方案）；5.2 节描述实验环境、统一流程与四方案的实现过程，其中方案 D 给出美食推荐系统的完整实现与运行效果展示；5.3 节给出结果与分析框架（数据以实测回填）；5.4 节从方法有效性、与现有 AI 开发方法比较、局限性三方面讨论。5.3 节在实验执行前给出分析框架，各项结论以实测数据回填与修正为准；若实测与预期不符，将如实报告并归因讨论。


\section{实验设计}

\subsection{实验目标与研究问题}
本实验的目标是：\textbf{验证本文提出的上下文工程方法在 AI 辅助软件开发过程中的有效性，而非验证 wpw 工具相较其他工具的优势}。具体地，在受控条件下对比四种上下文管理范式在开发成本、开发质量、上下文效率、长期演化与流程可控性维度的表现，以消融实验分离知识组织、上下文生成与流程约束机制的各自贡献，以多轮需求演化任务（T4）考察方法对项目长期演化的支持能力，进而回答第 1 章提出的三个研究问题（RQ1-RQ3）。研究问题与实验验证方式的对应关系如表5-1所示：主实验观察完整方法与代表性范式的综合差异，机制层面的贡献由消融实验分离验证，长期演化能力由 T4 任务考察。

关于实验的外部效度，需明确本实验的性质边界：\textbf{本实验属于受控工程实验，而非大规模生态统计实验}，其目标在于验证方法机制的有效性，而非证明方法在所有软件项目中的普适性能。为部分缓解单一项目的外部效度问题，实验按"一个业务载体 + 多任务集"组织（见 5.1.2 节）。


\subsection{测试系统设计与任务定义}
\textbf{（1）任务载体定位}

测试任务载体为\textbf{面向 AI 辅助开发评估的典型 Web 业务系统}，以美食推荐业务为载体（本节给出该实验系统的完整设计与任务定义，作为四方案共同实现的对象）。选择该业务的原因是：功能模块典型（用户认证、内容浏览、个性化推荐、交易、收藏评论覆盖 Web 系统常见需求类型）、业务语义清晰（便于定义需求边界与评估需求符合度）、技术栈主流（vue+springboot 为国内主流全栈组合，且与第 3 章图谱解析器支持范围对齐）。

需要强调：本实验的研究变量是 \textbf{AI 辅助开发过程}（流程约束、知识供给、上下文管理），而非推荐算法效果或业务系统本身的先进性。因此，系统设计以"提供典型业务复杂度"为原则，刻意排除与研究变量无关的技术复杂度（推荐算法精度、LLM 推荐效果、微服务治理能力等均不进入评估范围）。

\textbf{（2）系统需求分析}

系统涉及两类角色：\textbf{管理员}（B 端管理平台）与\textbf{普通用户}（C 端用户端）。核心业务流程为：用户登录 -> 浏览美食 -> 推荐生成 -> 加入购物车 -> 订单提交 -> 评价反馈（收藏 / 评论）；管理端覆盖用户管理、美食分类管理、美食信息管理、订单管理与系统管理。非功能需求（响应性能、数据一致性、可扩展性）按典型 Web 系统常规标准设定，不引入与研究变量无关的特殊约束。

\textbf{（3）系统总体设计}

系统采用前后端分离架构，总体架构如图5-1所示。前端包括商家管理平台（Vue3 + Vite + Element Plus + Pinia）与用户端（Uni-app + uView UI 微信小程序）；后端基于 Spring Boot 分层实现用户、菜品、订单等业务模块，并提供\textbf{个性化业务逻辑模块（以用户偏好规则计算为核心，用于模拟真实业务场景中的复杂业务逻辑，其算法效果非研究变量）}；数据层采用 MySQL + Redis + Elasticsearch 的典型组合，服务间异步通信采用 RabbitMQ。推荐模块采用以用户偏好规则计算为核心的常规推荐系统设计，不涉及大模型增强推荐，推荐算法效果非研究变量、不进入本章评估范围；实验按可横向对比的规模裁剪，微服务治理与监控组件按需简化。

\textbf{（4）系统功能设计}

系统由四大业务模块构成（功能模块结构如图5-2所示），作为四方案共同实现的需求边界：

\begin{itemize}
\item \textbf{管理员模块}（B 端管理平台）：系统首页、个人中心、用户管理、美食分类管理、美食信息管理、系统管理、订单管理。
\item \textbf{用户模块}（C 端）：首页（推荐与资讯展示）、美食信息浏览、购物车、美食资讯、个人中心（收藏、充值、客服、订单查询）。
\item \textbf{美食信息模块}：名称、分类、图片、口味、点击次数、价格六维属性。
\item \textbf{订单信息模块}：订单编号、商品信息、价格体系、支付类型、订单状态、配送信息。
\end{itemize}

\textbf{（6）任务集设计}

需求集合划分为四组任务集，覆盖不同开发场景：

\begin{itemize}
\item \textbf{任务集 T1（基础搭建）}：用户认证、菜品信息管理--绿地搭建场景；
\item \textbf{任务集 T2（业务核心）}：个性化业务接口、购物车与订单流程--存量迭代场景（在 T1 基础上扩展）；
\item \textbf{任务集 T3（迭代增强）}：收藏、评论、资讯模块--存量迭代场景；
\item \textbf{任务集 T4（多轮需求演化）}：连续新增会员积分、优惠券、会员等级、配送规则四轮需求，每轮在上一轮结果基础上进行--长期演化场景，对应 RQ3。
\end{itemize}
其中 T2/T3 重点用于验证 AI 编程智能体在已有代码上下文理解与增量修改场景下的能力--这正是第 3 章知识组织与上下文生成方法的主要目标场景；T4 重点考察方法在项目长期演化过程中的上下文积累效果：比较初始阶段与多轮需求之后的上下文构建时间、Token 消耗与上下文召回率变化。四方案按相同顺序执行各组任务集；消融实验在相同任务集上重复执行；T4 演化实验以方案 D 为主要观察对象，并以方案 B（规格驱动）作为演化方式对照。

\textbf{（1）实验信息约束原则}。为保证方案间比较公平，所有方案均允许访问同等的初始信息，包括：同一份需求描述、技术栈说明与任务执行时点的已有代码仓库。特别说明：方案 D 所使用的能力规范与知识图谱\textbf{并非人工额外提供的先验知识，而是其工作流程在执行过程中从需求文档与源码自动构建产生}；该构建的完整冷启动开销--首次扫描源码、生成能力规范、建立图谱与向量索引--均计入方案 D 的时间与 Token 成本，不使用任何预构建知识库。其余方案同样可以通过手动阅读仓库获取等价信息，其检索成本计入各自方案。

\textbf{（2）主实验与消融实验的分工}。由于本文的研究目标并非比较不同工具的整体能力，而是分析上下文工程各机制的组合效果，方案 D 相对 B/C 包含更多机制（流程 + 知识组织 + 压缩）属于方法设计本身的特点；因此主实验用于观察完整方法的综合表现，各机制的单独贡献通过消融实验（5.1.5 节）进一步分离，不以主实验的组间差异直接归因于单一机制。

\textbf{（3）Spec Kit 参照说明}。Spec Kit 侧重项目级规范治理（Constitution + 质量门禁 + Workflow Engine 等完整治理体系），而本文关注代码侧的上下文工程（项目知识结构化与任务级上下文生成），两者研究目标不同；且引入其治理体系后，实验组间差异将混入生态配置成本等混杂变量，难以与本研究的目标变量分离。因此本文未将 Spec Kit 纳入主实验组，而在 1.2 节研究现状与 5.4.2 节讨论中与其进行机制层面的对比。此为研究目标定位与变量控制的考虑，不构成对工具能力的评价。

\textbf{（4）控制变量与版本锁定}。同一需求规格、同一开发者、同一大模型、同一技术栈、同等时间预算；各工具以实验采用版本为准（版本号、发布日期与代码提交标识记录于 5.2.1 节实验环境表），避免因工具快速迭代导致比较基准漂移。

\section{实验过程}

\subsection{实验环境和统一流程}
实验硬件、操作系统、Node.js 运行时、大模型及 API 版本、各对比工具的版本记录（版本号、发布日期与代码提交标识）汇总于本节实验环境表（成稿时回填；工具快速迭代，以实验采用版本为比较基准）。统一流程为：四方案在同一需求规格、同一技术栈、同一开发者与同等时间预算下，按相同顺序执行 T1/T2/T3 三组任务集；全程以统一模板记录 Token 消耗、工时、迭代/返工事件与人工介入事件，作为 5.3 节各指标的度量来源。


\subsection{方案 A/B/C 实现过程}
\textbf{（1）方案 A：传统对话式大模型辅助开发（vibe coding）}

开发者直接与 AI 对话生成前端组件与后端接口，允许使用同一模型提供的代码解释、调试建议与重构建议等常规辅助能力，但不引入显式规格管理、项目知识索引与任务阶段约束--即以"无流程约束的自然语言交互开发"为对照组基线。全程记录 Token、工时、返工与缺陷。观察要点：对话过程中的状态一致性、需求遗漏情况、上下文逐轮膨胀趋势。

\textbf{（2）方案 B：规格驱动的大模型辅助开发（OpenSpec）}

按其实验版本工作流撰写变更规格（proposal/spec/design/tasks），经 apply/sync/archive 推进实现。观察要点：规格制品与代码结构、业务知识的关联方式，变更规格到实现的衔接成本，任务级上下文以文档与手动检索为主的实际开销。

\textbf{（3）方案 C：技能化 Agent 工作流辅助开发（Superpowers）}

按其实验版本技能化工作流推进：brainstorming 澄清需求、writing-plans 编写计划、subagent-driven-development 执行、code-reviewer 审查。观察要点：技能流程间的衔接与状态管理方式、子代理上下文隔离的实际效果与配置成本、任务级上下文的构造成本。


\subsection{方案 D：基于 wpw 的美食推荐系统实现过程}
方案 D 采用本文上下文工程方法（wpw 载体）完整实现美食推荐系统；该实现过程与运行效果同时构成题目中"美食推荐系统设计与实现"的实物落点。方案 D 完整走 BRD->PRD->（Explore 可选）->Design->Plan->Test->Apply 六阶段；图谱构建与上下文生成嵌入 apply 等环节，图谱构建成本计入该方案总成本。

\textbf{（1）需求阶段}：BRD / PRD 阶段产物展示（业务需求文档与产品需求文档的关键条目、需求点清单，成稿时截选回填）。

\textbf{（2）设计阶段}：Design / Plan 阶段产物展示（系统架构设计、模块划分、任务计划与前置测试方案，成稿时回填）。

\textbf{（3）实现阶段}：Apply 阶段生成的用户、菜品、推荐、订单等模块代码与结构（结合图谱上下文注入记录，展示各模块实现与关键功能）。

\textbf{（4）运行效果}：系统首页、推荐页面、管理后台、订单页面等运行截图（图5-3，成稿时回填），作为系统实现完整性的直观证据。

观察要点：阶段完整性与状态可审计性、图谱上下文的实际密度与命中率、能力归档沉淀的运转情况。

\section{讨论}

\subsection{本文方法对大模型辅助系统开发的影响}
结合实验数据，从三方面分析上下文工程方法的有效性及其成立条件：其一，技术栈适配性--前端 Vue3/Pinia/Uni-app 解析与后端 Java/Spring Boot 解析（类型/方法/常量节点、注解与 REST 端点元信息、包路径 import 边、业务包模块推断）使测试系统的前后端源码一致进入图谱，business\_map 多源融合在前后端同等生效，多技术栈经多图谱机制隔离（按子目录构建命名图谱）；其二，三机制的贡献分解--依据消融 A/B/C 的实测结果，讨论知识组织、上下文生成与流程控制各自的作用路径与边界条件；其三，适用边界--依据分组任务集（绿地/存量迭代）的分组结果，讨论方法在不同开发场景下的表现差异。若实测与预期不符，如实归因讨论。


\subsection{与现有 AI 开发方法比较}
本文方法与现有方法（工具）的差异属于\textbf{设计取舍}而非能力高下，具体体现在三方面：

其一，相对 Spec Kit 的项目级规范治理体系（Constitution + 质量门禁 + Workflow Engine/扩展生态），二者关注重点不同：Spec Kit 侧重通过规范体系和工作流约束保证 Agent 执行一致性；本文方法侧重通过项目知识结构化和任务上下文生成降低 AI 获取代码知识的成本，可以形成互补关系。设计上，本文方法选择更轻的起点：零配置开箱即用（项目类型自动嗅探、模块自动推断、纯 Node.js 单运行时、图谱本地构建、CLI 层无需 API Key），以治理强度（无全局规范宪法与一致性检查，见 5.4.3）换取更低的采用与维护成本。

其二，相对 OpenSpec 的变更制品管理（artifact graph + action 工作流），本文方法将变更之外的项目级知识纳入统一基础设施：能力规范随归档持续沉淀、代码结构以双层图谱建模、业务-代码关联多源融合；命令级解耦支持按需组合，图谱增量更新控制功能增量的边际成本。

其三，相对现有方法的上下文机制（Superpowers 的子代理上下文隔离与工作区隔离等，主要作用于 prompt/工作流/扩展层），本文方法的差异化在代码侧上下文的结构化供给：知识沉淀为图谱后，经锚点检索 -> 子图裁剪 -> 骨架抽取 -> 压缩序列化按需生成任务上下文。需区分"规避"与"解决"：本文方法未从技术上解决规则膨胀导致的失真（规则侧靠分阶段轻量加载规避），技术上解决的是同构的代码上下文膨胀问题。

\subsection{局限性分析}
\begin{itemize}
\item \textbf{实验规模与性质边界}：本实验为受控工程实验，以单一业务载体的三组任务集组织，属个案层面的机制验证，结论向其他项目类型、其他规模与团队场景的外推需进一步研究；人工评审维度存在主观性，以双人交叉评审与标注仲裁缓解。
\item \textbf{后端语言覆盖}：Java/Spring Boot 解析器已实现但落地验证规模有限，首版不做依赖注入边与 JPA 关联边；Go/Python 等后端语言尚未覆盖。
\item \textbf{冷启动}：能力规范缺失时退化为纯结构检索。
\item \textbf{规则治理}：缺少全局规则治理能力，规则随项目与团队规模膨胀时面临同类失真风险，分阶段轻量加载缓解但未根治。
\end{itemize}

\section{本章小结}
本章给出了上下文工程方法的实验验证设计：以基于大模型的美食推荐系统实现任务为载体，在四组任务集（T1 绿地 / T2、T3 存量迭代 / T4 多轮需求演化）上组织四种上下文管理范式（无上下文工程 / 规格驱动 OpenSpec / Agent 流程 Superpowers / 本文方法（wpw 载体））的受控对比，以成本、开发质量、AI 辅助程度、流程可控性与上下文效率五组可操作定义的指标度量；消融实验分离知识组织、上下文生成与流程控制三项机制的贡献（RQ1/RQ2），T4 演化实验考察方法对项目长期演化过程中上下文积累的支持能力（RQ3），组件级基线支撑第 3 章的方法选择。5.1.2 节给出测试系统的完整设计（需求、架构、功能、数据库），5.2.3 节给出方案 D 的完整实现过程与运行效果，共同承载题目中"美食推荐系统设计与实现"的落点。实验明确定位为受控工程实验：实验对象为系统的软件实现过程而非推荐算法效果，比较的是上下文管理范式而非工具高下，验证机制有效性而非普适性能；结果分析以实测数据回填，并从方法有效性、与现有 AI 开发方法的机制对比与局限性三方面讨论。
