# SDD 实验测评 SOP（单次运行）

> **最高执行原则——单对话、唯一 Agent、同源 Token**：当前对话就是本次实验的唯一执行 Agent，必须直接完成规格、实现、测试、验收、清理和事件记录；不得启动、嵌套或委派第二个 Agent。模型 Token 只能取当前对话中执行该实验任务的对应 `task_started`—`task_complete` 回合，不得取子 Agent、其他对话或后续维护回合的用量。`sdd-eval` 只负责工作区与记录管理、后置指标计算、统一验收和结果落盘，不再启动 Agent。一次对话只选择“任务 A：OpenSpec”或“任务 B：wpw”中的一个，不得切换方法或读取另一方法的工作区与结果。

### 0.1 状态口径

| 状态 | 判定标准 |
|---|---|
| 已完成 | 已满足冻结快照、当前对话直接执行、完整探索事件、统一验收和结果落盘要求，并已从执行该实验任务的当次 Codex 对话回合中取得精确 `token_count`，可以纳入正式统计 |
| 暂计正式 | 功能与验收结果已落盘，但存在协议例外、指标缺失或估算值；经实验操作者明确决定后暂时计入进度，必须标明实测/估算口径、保留例外原因和原验证记录，等待后续单独处理 |
| 验证中 | 已完成 mock、人工 Agent、后置评分或协议验证，但仍缺少正式运行条件，不纳入主实验统计 |
| 待执行 | 尚未形成可用实验记录 |

“已完成”运行直接计入正式样本量；“暂计正式”运行按实验操作者的当前决策计入进度，但在数据清洗时必须单列并重新审计。第 6 章已经记录的 T1-1 mock、旧起点 Agent 运行、修正后人工 Agent 运行和无探索协议重放仍属于工具或流程验证。

## 1. 目的与基本原则

本 SOP 将一次实验定义为“当前对话作为唯一执行 Agent，使用一个方法完成一个任务，并由 `sdd-eval` 统计和落盘的一次独立运行”。OpenSpec 固定使用 `F:\project\springboot-openspec`，wpw 固定使用 `F:\project\springboot-wpw`。两者从同一冻结起点生成，但不共享项目目录、代码修改、规格/知识制品或模型会话。

测评遵循以下原则：

1. 两种方法均从同一个功能未实现的起点快照生成独立项目；
2. 当前对话中的 Agent 在开发过程中可以自主搜索、查询图谱和读取源码，也可以多次追加上下文；
3. wpw 的 KG 输出是初始导航和结构化知识来源，不要求第一次输出包含全部相关源码；
4. 执行器只记录 Agent 实际发生的探索和模型用量，不根据 Gold 文件补齐上下文；
5. Gold 标注只在运行结束后计算 Recall 和 Precision，不用于运行时决策、停止或提示遗漏文件；
6. 主要结果是任务验收、全过程 Token 和总耗时；搜索、读取、导航指标、Recall 和 Precision 用于解释差异来源。

## 2. 当前对话与 sdd-eval 采集协议

开始开发前，当前对话先固定任务、方法、持久独立项目、起始时间、run_id 和事件文件。当前对话本身就是执行 Agent；`sdd-eval` 不再嵌套启动 Agent，只接收本对话实际产生的事件与验收结果并计算指标。运行记录使用以下字段：

- `SDD_EVAL_CONTEXT_FILE`：任务和初始上下文文件；
- `SDD_EVAL_EVENTS_FILE`：本次运行专属的 JSONL 事件文件；
- `SDD_EVAL_WORKSPACE`：本次方法对应的独立项目；
- `SDD_EVAL_METHOD`、`SDD_EVAL_TASK_ID`：运行身份。

当前对话应将实际发生的探索事件追加到 `SDD_EVAL_EVENTS_FILE`，例如：

```json
{"type":"search","query":"YonghuController login","text":"实际返回的搜索结果"}
{"type":"graph_query","query":"用户登录认证调用链","text":"实际返回的图谱结果"}
{"type":"source_read","path":"src/main/java/com/controller/YonghuController.java","text":"Agent 实际读到的源码"}
{"type":"context_append","text":"实际追加给模型的上下文"}
```

`source_read` 如果只记录路径而不记录内容，只计一次读取行为，不计入上下文 Token。每次实验必须由一个独立的 Codex 任务对话回合执行。模型 Token 统一取该任务回合从匹配的 `task_started` 到 `task_complete` 的完整用量，以 `task_complete` 前最后一条 `event_msg/token_count.total_token_usage` 为准，并只追加一次汇总 `model_call`：

```json
{"type":"model_call","inputTokens":4321304,"outputTokens":20410,"totalTokens":4341714,"metadata":{"scope":"current Codex task turn from task_started through task_complete","taskStartedAt":"任务回合开始时间","taskCompletedAt":"任务回合完成时间","cachedInputTokens":4206720,"reasoningOutputTokens":5379,"source":"session JSONL token_count immediately preceding task_complete"}}
```

`totalTokens = inputTokens + outputTokens`；缓存输入已包含在输入 Token 中，推理输出已包含在输出 Token 中，均不得再次相加。同一线程存在多个用户回合时，按各自的 `task_started`—`task_complete` 边界分别统计，后续分类、文档维护或讨论回合不得计入先前实验。由于 `task_complete` 在任务回复结束后才写入，会话用量允许在下一回合从本地 session JSONL 精确回填；这属于实测值补录，不属于估算，必须保存会话 ID、任务起止时间和来源事件。无法找到匹配边界或精确 `token_count` 时，模型 Token 保持缺失。执行器不会使用 Gold 自动补齐内容。完整字段说明见 `F:\project\sdd-eval\EXPLORATION_PROTOCOL.md`。

职责边界固定如下：当前对话只提供真实原始事件、测试/验收输出；任务结束后由 `sdd-eval` 从对应的当次对话回合读取精确会话用量，并按统一分词器和 `RunRecord` 口径计算 `totalTokens`、累计上下文 Token、Recall、Precision、探索次数、验收率、返工和总耗时。若用量在下一回合回填，必须保留来源、边界和订正历史，不得用其他对话或估算值冒充当次对话实测值。

### 6.4 回填规则与结论边界

- 只抄录结果 JSON 和可核验日志中的数值，不从终端印象、对话摘要或预计值反推指标；
- 通常只有同时满足冻结起点、当前对话直接执行、完整实时事件、统一验收和隔离要求，并能从执行该任务的当次对话 `task_started`—`task_complete` 边界取得精确 `token_count` 的记录，才增加正式样本数；
- 若实验操作者明确决定先纳入、后处理，可将功能与验收证据完整的记录标为 `provisional-formal` 并暂计正式；不得修改原始事件，所有协议例外和缺失指标必须同时写入结果 JSON、台账和第 6 章，原验证记录必须保留；
- mock、静态验收重放、嵌套 Agent 和纯后置补造记录仍不得纳入；暂计正式记录可以填写有明确参照、公式和审计轨迹的估算值，但必须使用“≈”或“估算”标记，不得冒充实测值，最终分析应对包含与排除估算值两种口径进行敏感性复核；
- 缺失或未执行的指标保持空白并说明原因，不以 `0`、`100%` 或其他默认值代替；
- `failed`、`timeout`、`interrupted` 和 `error` 记录原样保留，并同步反映在任务状态与失败说明中；
- 初始导航指标只解释定位过程，不能替代全过程累计上下文的 Recall、Precision 或 Token；缓存输入 Token 已包含在模型输入 Token 中，不得再次计入模型总 Token；
- 只有同一任务的 OpenSpec 与 wpw 正式样本均完成后，才能写任务级配对差异；只有证据规模满足分析要求后，才能更新 H1～H4 和 RQ1～RQ3 的比较结论；
- 本文件与第 6 章中的正式样本数、任务状态、验收率、Token、耗时、Recall、Precision、返工次数、哈希和证据路径必须一致；如需订正原始记录，应另存订正版并保留原因和旧记录，不直接覆盖原始证据。
